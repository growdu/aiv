# 层间接口与内容坐标系

## 一、意图与边界

顶层架构（草稿箱 → 两条流水线 → 六个平台）已经在
[`2026-11-18-顶层设计与目录调整.md`](2026-11-18-顶层设计与目录调整.md) 里定完。
现在缺的是**层与层之间传什么、谁负责校验**。

这份文档做两件事：

1. **定坐标系**：一个内容从选题到落地，坐标是哪些维度，每一维的真相在哪；
2. **定接口**：每两条层边界上，传递物是什么、校验规则是什么、哪一层拥有规则。

它**不**重新设计顶层架构，也**不**重新设计三档的内容规格——那部分已经在
[`publish/spec/09-长视频三档.md`](../../publish/spec/09-长视频三档.md) 里定死，
本文只把它接到坐标和平台上。

### 平台是什么

这个仓库不是文章仓库，是一个**内容生成平台**。它同时是：

- 一个**持续学习、持续成长**的技术体系——`docs/` 是一条有先后的学习路径，
  不是一堆按主题堆起来的文章；
- 一个**个人 IP** 的生产装置——观众要的不是母稿，是被嚼过的结论。

这两件事各自对应一条流水线，但共用**一份母稿**。母稿唯一，是这个平台的地基。

### 四个研究方向

| 方向 | 现状 | 说明 |
| --- | --- | --- |
| PostgreSQL | 已有 8 个系列 | 进度最快 |
| Linux | 已有 5 个系列 | |
| DPDK / VPP | 已有 4 个系列 | |
| Ceph | **筹备中** | 现在开空壳，站点显式标注 |

这四条是**源码方向**。仓库里另外几条学习赛道（分布式与架构、AI 工具链、
工程与语言、人生、平台元数据）**不是源码方向**，不在本文的坐标系里，
它们不参与「合集 / 系列」这套分层。

> **注意**：源码方向与学习赛道**不是一一对应**。
> `docs/engineering/` 下有 6 个系列目录（foundations / cheatsheets /
> engineering-practice / containers / observability / web-and-frontend），
> 而 `engineering` 赛道只有 4 个阶段；`docs/distributed/` 同样是 6 个目录、4 个阶段。
> 所以下面 §2.4 那条「阶段 = 系列目录」的不变量**只对源码方向成立**，
> 不是全站通则。这一点在验收里必须写死范围，否则守卫一开就是红的。

## 二、坐标系：四个维度

一个视频内容单元在系统里的完整坐标是四元组：

```
(方向 direction, 系列 series, 期号 episode, 档位 tier)
```

### 2.1 四维各自的真相在哪

| 维度 | 取值形态 | 真相在哪 | 性质 |
| --- | --- | --- | --- |
| 方向 | `postgresql` / `linux` / `dpdk` / `ceph` | `docs/source-tracks/<dir>/` 的**目录名** | 目录派生 |
| 系列 | 方向下的目录 slug | `docs/source-tracks/<dir>/<series>/` 的**目录名** | 目录派生 |
| 期号 | 全局唯一 slug | 母稿 front matter 的 `episode:` | 声明式 |
| 档位 | `short` / `mid` / `full` | **产物文件名**的 `-<tier>` 后缀 | 命名派生 |

### 2.2 方向与系列**不写进 front matter**

这是沿用信息架构那条已经定过的规矩：**层级由目录结构表达，不靠 front matter 补字段**。

- 文档母稿：`docs/source-tracks/postgresql/logical-replication/<slug>/index.md`
  —— 方向和系列就在路径里，一眼看得见，不需要再抄一遍到 front matter；
- 视频内容单元：`source/_posts/video/<ep>-<tier>.md` —— 路径里**没有**方向和系列，
  所以由构建期从母稿继承（见 §3.3）。

也就是说：**同一件事只写一遍**。母稿的 front matter 里不会出现 `direction:`，
文档母稿也不会出现 `series_slug:`。

### 2.3 系列 slug **不全局唯一**

`getting-started` 在 `postgresql` 和 `dpdk` 下各有一个。

所以系列的**全局标识是二元组** `<direction>/<series>`，不是系列目录名本身。
站点 URL 也是按二元组展开的：`/videos/postgresql/logical-replication/`。

> **这是我做的一个判断，不是讨论出来的。**
> 讨论里确定的是「合集 = 研究方向」「系列 = 方向下的连续专题」，
> 二元组这件事是撞上重名之后必须收的口。

### 2.4 系列 = 目录 = 学习阶段（**仅限源码方向**）

`data/learning-path.json` 里 `db-internals` 赛道的 L1–L8，
与 `docs/source-tracks/postgresql/` 下的 8 个系列目录**恰好一一对应**：

| 阶段 | 系列目录 |
| --- | --- |
| L1 | `getting-started` |
| L2 | `storage-engine` |
| L3 | `index-and-query` |
| L4 | `transaction-mvcc` |
| L5 | `wal-and-recovery` |
| L6 | `replication-ha` |
| L7 | `logical-replication` |
| L8 | `extensions-perf` |

`linux`（L1–L5）、`dpdk`（L1–L4）同样是 1:1。

**这是源码方向的一条不变量**：学习路径的阶段 = 系列的目录。
所以「系列」不需要另发明一张表——它就是 `learning-path.json` 里的阶段，
加上一条「源码方向的阶段必须正好对应一个系列目录」的守卫。

这条不变量带来一个直接好处：**教学顺序**和**系列划分**天生一致。
「循序渐进」不需要额外维护，它就是目录的顺序。

> 守卫的适用范围必须是**源码方向赛道**。写成全站通则，
> `engineering`（6 目录 / 4 阶段）、`distributed`（6 / 4）当场就红。

### 2.5 「季」这个说法废止

存量六期的字幕稿（`video/字幕-*.md`）里的「第一季 / 第二季」，
核对下来是：

- 第一季 = EP01–EP05 = `logical-replication/` 目录；
- 第二季第一期 = EP06 = `transaction-mvcc/` 目录。

**季就是系列**，只是叫法不同。统一叫「系列」，新写的口播稿用新措辞。

> **这段核对的是已清空的存量。** 视频线这一轮清空重来，六期的字幕稿
> 都不在仓库里了，所以这条结论现在只剩「**新写的稿子一律叫系列**」这一半在起作用。
> 结论本身不变：新坐标的第一层就叫系列，不叫季。

存量字幕稿里「季」字的出现范围比想象中小——`字幕-行锁.md` 里同时有
「第一季」（承接 EP05）和「第二季第一期」（自称），`字幕-并行解码.md`（EP01）
里一个「季」字都没有。所以改名不是「六个文件全改」，是**新写的稿子用新措辞，
存量稿子不动**（见 §七 M5）。

## 三、层与层之间传什么

### 3.1 层与边界总表

```
  L0 草稿箱  drafts/                      新内容的入口
       │  选题条目 + 口径
       ▼
  L1 总审核  review/                      内容本身能不能进流水线
       │  母稿（唯一真相）
       ▼
  L2 母稿层  docs/ ──────┐
             video/ ─────┤
       │  内容契约（19 → 22 字段白名单）   ← 文档流
       │  讲稿骨架（video/episodes/<系列>/<合集>/<文档>/skeleton.yaml）← 视频流
       ▼
  L3 内容单元  content/units/              平台无关的内容仓库（见 §3.2）
       │                                   文档流：编译产物，一个内容单元一个 URL
       │                                   视频流：三档产物（口播稿/字幕表/视觉契约/成片/平台文案）
       ├──────────────┐
       ▼              ▼
  发布调度器        站点适配步骤
  publishkit/      → platforms/blog/site/source/_posts/
  → 微信/头条            │
                         ▼
                    hexo → public/
       ▼
  L4 平台层  platforms/<plat>/            一个平台一个目录，一套 adapter
       │  outbox 快照
       ▼
  L5 展示层  站点 public/ + 第三方平台上的页面
```

坐标系只在 L2 之下有意义——**期号和档位在 L3 之后仍然是坐标的一部分**，
因为一个内容单元会同时出现在站点和多个平台上。

### 3.2 内容单元的家：内容仓库与站点工作区分离

**这一节是本次新增的一层划分，也是对顶层设计 D9 / D10 的一处修正。**

`source/_posts/` 现在同时扮演两个角色：

| 角色 | 谁在用 | 平台无关吗 |
| --- | --- | --- |
| **内容单元仓库** | 发布调度器 `publish/publishkit/schedule.py`、内容契约闸门 `tools/check-content-contract.py`、学习路径 `tools/build-learning-path.py`、发布索引 `tools/build-publish-index.py` | **是**——契约是所有平台共用的 |
| **hexo 的渲染输入** | hexo 自己 | **否**——hexo 是站点这一个平台的渲染器 |

而 D9 要把 `source/` 整个搬进 `platforms/blog/site/`。搬完之后，
**留在根、平台无关的 `check-content-contract.py` 与 `publish/publishkit/schedule.py`
要去博客平台的目录里读内容单元**——共用的契约，产物住进了其中一个平台。

**收口：内容单元搬出 hexo 的目录，站点变成它的消费者。**

```
docs/  ──内容单元编译（平台无关）──▶  content/units/
                                          │
              ┌───────────────────────────┴──────────────────────────┐
              ▼                                                      ▼
   publishkit 调度器                                         站点适配步骤
   → 微信 / 头条                                     → platforms/blog/site/source/_posts/
                                                               │
                                                               ▼
                                                          hexo → public/
```

**关键性质：相对布局原样保留。** 内容单元在仓库里的相对路径
（`source-tracks/postgresql/.../index.md`、`video/row-lock-short.md`）
与它在 `source/_posts/` 下的相对路径**完全一样**。所以：

- **`content_id` 的定义只改基准目录，不改值**：从「相对 `source/_posts/` 的路径」
  改成「相对 `content/units/` 的路径」，`video/row-lock-short` 仍然是
  `video/row-lock-short`。所有已有的 content_id、站点 URL、快照名**一个都不变**；
- **站点 URL 不变**：hexo 的 URL 是 `:year/:month/:day/:title/`，
  `:title` 是相对 `_posts/` 的路径。站点适配步骤搬运时必须
  **原样保留相对布局**，否则 URL 会变。

**`content/units/` 是构建产物**，跟今天的 `/source/` 一样进 `.gitignore`，
每次构建重建。

#### 拆分边界：哪一步归谁

`tools/sync-hexo.py` 今天 3032 行，把两件事混在一起。拆成两半：

| 归平台无关（母稿 → 内容单元） | 归站点（内容单元 → hexo） |
| --- | --- |
| `read_section_categories` / `read_cascade_categories` / `resolve_post_categories` | `copy_images`（图片拷进 hexo 的 `source/images/`） |
| `infer_topics` / `git_date` / `extract_title` / `fallback_title` | `create_theme_pages` / `create_database_landing_page` / `create_projects_page` |
| `split_fm` / `has_fm_title` / `yaml_escape` / `passthrough_block` | `read_matery_about_config` / `build_about_markdown` |
| `rewrite_links` / `rewrite_images` / `_resolve_link_target` | `write_redirects` / `write_category_redirects` |
| `process` / `process_html` | `copy_view_counts_snapshot` |
| `collect_index_posts` | |

**链接与图片的重写留在平台无关那一半**，理由有两条：

1. **发布层今天读的就是重写后的正文**——微信与头条的既有产物里，
   站内链接是绝对 permalink。改了正文形态就动了它们的产物；
2. permalink 是从 `content_id` 派生的（`tools/site_root.py` 的
   `permalink(date, content_id)`），而 `content_id` 是平台无关的。
   所以「把相对链接解析成 permalink」这件事本身可以留在平台无关那一侧，
   只有**目标 URL 的挂载点**（`growdu.cn` 的 `/` 与 GitHub Pages 镜像的 `/blog`）
   是站点特有的——那一份由 `site_root.py` 处理。

#### 连带要动的工具

真正跨界的只有**四个读内容单元的地方**，改动量都不大：

| 工具 | 现在 | 拆完 |
| --- | --- | --- |
| `publish/publishkit/schedule.py` | 默认 `root / "source" / "_posts"` | 默认 `root / "content" / "units"` |
| `tools/check-content-contract.py` | 默认 `source/_posts` | 默认 `content/units` |
| `tools/build-learning-path.py` | `POSTS_DIR = source/_posts` | `content/units` |
| `tools/build-publish-index.py` | 读 `source/_posts/` | 读 `content/units/` |

写内容单元的两个脚本要**两边都写**（或者拆成两个）：

| 工具 | 现在 | 拆完 |
| --- | --- | --- |
| `tools/sync-hexo.py` | 母稿 → 内容单元 → hexo source（一次做完） | 内容单元编译（留根，平台无关）+ 站点适配（进 `platforms/blog/site/tools/`） |
| `tools/build-video-pages.py` | 写 `source/_posts/video/` | 写 `content/units/video/`；站点的那一份由站点适配步骤搬 |

**站点脚本读共享的内容单元仓库是对的**——它们是消费者，不是所有者。
所以 `build-learning-path.py`、`build-publish-index.py`、`build-podcast-index.py`、
`build-series-page.py` 按 D10 搬进 `platforms/blog/site/tools/` 之后，
读 `content/units/` 而不是 `platforms/blog/site/source/_posts/`——
**它们的输入变了，但行为一字不变**。

#### CI 的顺序要跟着改

```
1. 内容单元编译（平台无关）      docs/            → content/units/
2. 视频内容单元（平台无关）      video/           → content/units/video/
3. 站点适配                      content/units/   → platforms/blog/site/source/_posts/ + hexo 私有文件
4. 学习路径分类（平台无关）
5. 站点建页                      → platforms/blog/site/source/learning/**, videos/**, _data/**
6. hexo generate
```

#### 这是一次真搬移，不是登记

跟 D9 / D10 一样，**这次也是搬移不是登记**：`.gitignore` 的规则、
CI 的工作目录与步骤顺序、`.github/workflows/` 里二十几处路径、
根 `tests/` 里的引用，全部要跟着改。

**纪律不变：只改路径，不改逻辑。**

### 3.3 I-1：母稿 → 内容单元（文档流）

**传递物**：内容契约。母稿的 front matter 是**源**，内容单元的 front matter 是**编译结果**。

字段分三类，这是现有契约已经定好的：

| 类别 | 含义 | 视频内容单元的例子 |
| --- | --- | --- |
| 推导 | 构建期算出来，不许手写 | `direction`、`series_slug` |
| 透传 | 从母稿原样搬过来 | `episode_hook`、`episode_license`、`episode_sources` |
| 契约固定 | 内容单元本身决定的 | `kind`、`title`、`date` |

**新增三个字段（白名单 19 → 22）**，只对视频内容单元有效：

| 字段 | 类型 | 性质 | 来源 |
| --- | --- | --- | --- |
| `tier` | str | **推导** | 产物文件名 `-<tier>` 后缀 |
| `direction` | str | **推导** | 母稿路径的 `source-tracks/<dir>/` |
| `series_slug` | str | **推导** | 母稿路径的 `<dir>/<series>/` |

推导链：

```
视频内容单元 source/_posts/video/<ep>-<tier>.md
  │  episode
  ▼
母稿 docs/source-tracks/<direction>/<series>/<slug>/index.md
  │  路径
  ▼
direction = <direction>,  series_slug = <series>
```

**这一步目前没人做。** `tools/build-video-pages.py` 是写内容单元 front matter 的那个工具，
它**从不打开 `docs/`**——没有 `DOCS` 常量，没有任何 docs 引用。
它的期号映射来自 `video/pipeline/Makefile` 的 `ifeq ($(EP),<ep>)` + `SCRIPT :=`。
所以要推导 `direction` / `series_slug`，必须**新引入一条「期号 → 母稿路径」的查找**
（扫 `docs/source-tracks/*/*/*/index.md` 找 front matter 的 `episode:`）。

这条查找的权威必须是**母稿的 `episode:` 字段**，不是 Makefile。
Makefile 登记的是「这一期用哪份口播稿」，跟「这一期的母稿在哪」是两件事。

**母稿 ↔ 期号一对一。** 这条已经是既成事实（六个母稿各带一个 `episode:`），
现在把它写成规则并加守卫：一期一号，一号一期，重复即红。

### 3.4 I-2：母稿 → 讲稿骨架 → 三档（视频流）

三档的内容规格在 `publish/spec/09-长视频三档.md` 里定死了，这里只定接线：

```
docs/<母稿>.md
   │ ①母稿解析（机器）
   ▼
video/episodes/<系列>/<合集>/<文档>/skeleton.yaml
                          讲稿骨架，segment 带 role 标签（**一篇文档一份，三档共用**）
   │ ②骨架 → 三档（机器，纯函数）
   ├──▶ short  精简版   hook + conclusion
   ├──▶ mid    进阶版   + mechanism + evidence
   └──▶ full   完整版   + aside
   │ ③出片（机器，现有流水线）
   ▼
video/out/<压平期路径>.mp4
```

**档位在路径里，不再靠文件名后缀。** 一期 = 一个档位目录，
期路径 = `系列/合集/文档/档位`，相对 `video/episodes/`。
产物名用**压平后的期路径**（斜杠换连字符）：

```
postgresql/getting-started/postgresql基操/short
→ video/out/postgresql-getting-started-postgresql基操-short.mp4
```

所以流水线里**没有 `TIER=` 变量**：命令是
`make EP=<期路径> align|all|nobrand|vertical|review-text|review-video|review-frames|persona`，
档位是坐标的一段。

**「不做自动裁剪」这句话要读准。** 09 §4.2 把 ② 写成**机器（纯函数）**；
09 §5.2 说「不做自动裁剪」指的是**段数或字数落不进区间时，守卫报红，
改 `role` 标记即可——自动裁剪会「悄悄删段」，与本仓库「不静默截断」的纪律冲突」。

所以准确的说法是：

- **按 role 选段是机械的**（机器做的，09 §4.2）；
- **「删段凑字数」是禁止的**（落不进区间就报红，改 role 标记，不悄悄截断）。

**骨架是手写的，role 标签是人的判断。** 09 §5.1 已经把
`video/episodes/<系列>/<合集>/<文档>/skeleton.yaml`
定为「这篇文档口播与画面的唯一真相」——role 标签本来就带着人的判断，
自动给段落分角色会出错。所以本文**不再重开**「手写还是生成」这个问题：
骨架手写，裁剪机器。

**真相归属要理顺。** 现在有两处都自称「唯一真相」：

| 文件 | 自称 | 改造后 |
| --- | --- | --- |
| `video/episodes/<系列>/<合集>/<文档>/skeleton.yaml` | 09 §5.1：「这篇文档口播与画面的唯一真相」 | **是**（骨架，一篇文档一份，三档共用） |
| 期目录的 `口播稿.md` | `tools/build-video-pages.py` docstring：「这条线入库的唯一真相」 | **不是**——它是骨架裁出来的产物；骨架才是唯一真相 |

**存量六期不存在迁移。** 视频线这一轮是**清空重来**，
六期（EP01~EP06）的成片、旁白、字幕稿、契约与发布元数据全部删除。
所以「改造后 short 档与现有字幕逐字节一致」这条硬验收**没有对象**——
新坐标下的第一期从骨架直接出片，没有存量可比。
（逐字节验收这条口径本身仍然有效：它约束的是「骨架裁出来的 short 档
与手工写出来的 short 档不许有差别」，等真有存量时再启用。）

### 3.5 I-3：内容单元 → 平台（**两条通道，不是一条**）

这里必须纠正一个容易想当然的地方：**视频平台不走 `publishkit.Manifest`**。

| | 文档流 | 视频流 |
| --- | --- | --- |
| 传递物 | `publishkit.Manifest`（冻结 dataclass，拒绝未知字段） | `video/publish/<EP>.json` → `pyv.epmeta.EpisodeMeta` |
| content_id | 相对 `source/_posts/` 的路径 | **裸期号 slug**（`row-lock`） |
| 快照文件名 | `<压平content_id>__<plat>.json` | `<期号>__<plat>.json` |
| 调度器 | `schedule.py` 驱动 `kind == "document"` 的平台 | **不经调度器** |
| 谁在管 | `publish/publishkit/` | `video/pipeline/pyv/` + 各平台 adapter |

证据：`schedule.py` 的 `target_platforms()` 明写「这一期只驱动文档类平台」，
`publish/spec/07-视频发布契约.md` 写明视频 adapter「不依赖尚未实现的
`publish/publishkit/`」；18 个现存视频快照的 `content_id` 都是裸期号
（`platforms/bilibili/outbox/row-lock__bilibili.json` 里是 `"content_id": "row-lock"`）。

站点侧的内容单元 content_id 才是 `video/row-lock`，
它跟视频发布侧的裸期号靠 `build-publish-index.py` 的 **basename 兜底**桥接。

**加档位后，两条通道的键各自变成：**

| 通道 | 加档位前 | 加档位后 |
| --- | --- | --- |
| 站点侧内容单元 | `video/row-lock` | `video/row-lock-short` |
| 视频发布侧产物 | `row-lock` | `row-lock-short` |
| 视频快照文件名 | `row-lock__bilibili.json` | `row-lock-short__bilibili.json` |

basename 兜底**仍然成立**（两边都变成 `row-lock-short`），这条桥不用改。

**为什么档位必须进键，不能当一个附加字段。** 三档是三个产物：
三份口播稿、三份字幕表、三份视觉契约、三条成片、三份平台文案。
一个内容单元对应一个产物——三档对应三个内容单元，就该是三个键。
否则一期三档投三个平台 = 9 个发布物撞进 6 个 content_id，幂等键失效。

> 「内容单元 = 编译产物、平台产物 = 派生物」这个三层模型在
> `review/specs/platform/content-model/content-unit-and-contract.md` 里。
> 但那篇**没有**「一个内容单元就是一个产物」这句原话——
> 是本文从那个模型推出来的结论。

### 3.6 I-4：档位 → 平台（能力声明）

**规则写在各平台自己的 `capability.toml` 里**，新增一个 `tiers` 键：

```toml
# platforms/bilibili/capability.toml
id = "bilibili"
kind = "video"
tiers = ["short", "mid", "full"]
```

```toml
# platforms/douyin/capability.toml
id = "douyin"
kind = "video"
tiers = ["short"]
```

**契约层新增 `Capability.tiers: tuple[str, ...]`。**

- `capability.py` 的 `_TOP_KEYS` 目前**拒绝未知顶层键**，
  所以加 `tiers` 必须同时扩 `_TOP_KEYS`；`Capability` 是 frozen dataclass
  且有 `to_dict()`，加字段要同步；
- **`tiers` 是可选的**：缺省即 `()`，表示这个平台不收任何档。
  文档类平台（wechat / toutiao / blog）**不写这个键**——
  写 `tiers = []` 和不写是同一个意思，不写少一处要同步的东西。

**为什么不用一张中心矩阵表。** `platforms/README.md` §五那条规矩是
「加平台只动 `platforms/`」。矩阵表放在中心，加一个平台就要改中心，
规矩就破了。规则写在平台自己家里，加平台就还是加平台。

### 3.7 I-5：平台 → 展示层

**传递物**：`outbox/<content_id>__<plat>.json` 快照（状态）
+ `source/_data/publish_index.json`（站点渲染要的东西）。

一期三档投三个平台 = 9 个发布物 = 9 个键 = 9 份快照，不撞。

## 五、YouTube 与「加平台只动 `platforms/`」

### 5.1 现状：这条承诺对视频平台**不成立**

`video/pipeline/pyv/epmeta.py` 把三个视频平台**写死**了：

```python
PLATFORM_SPECS = {"channels": ..., "bilibili": ..., "douyin": ...}

@dataclass
class EpisodeMeta:
    channels: dict | None = None
    bilibili: dict | None = None
    douyin: dict | None = None
```

每平台的文案（「一期一份」）住在期目录的 `publish.json` 里
（`video/episodes/<系列>/<合集>/<文档>/<档位>/publish.json`），
由 adapter 调 `meta.platform("bilibili")` 取。

所以**按现状加 YouTube，要动 `video/`**——`epmeta.py` 加一个平台、
期目录的 `publish.json` 加一段文案。
这跟 `platforms/README.md` §一那句「上游一个字都不用改」直接冲突。

### 5.2 决定：搬进平台侧

**已定：把「每平台的规格与文案」搬进 `platforms/`，让「加平台只动 `platforms/`」
对视频平台也成立。**

| 现在 | 搬到 |
| --- | --- |
| `pyv/epmeta.py` 的 `PLATFORM_SPECS` | `platforms/<plat>/publish-spec.json`（或同级的等价文件） |
| `pyv/epmeta.py` 的 `EpisodeMeta` 三个写死属性 | 通用加载器，按 `platforms/*/` 动态装配 |
| 期目录 `publish.json` 里的平台段 | **留在期目录里**，但挪进 `platforms[<plat>]` 段（见下面的订正） |

> **订正（2026-11-23，实施时改的）**：原文写的是把平台段搬去
> `platforms/<plat>/publish/<压平期路径>.json`。**那一层最终没有建**——
> 平台文案**跟着期走**（期目录的 `publish.json`），因为文案是**这一期的事实**
> （跟口播稿、契约、旁白一样入库），把它拆到平台目录里等于把一份事实
> 拆成两处（期目录说「这一期是什么」，平台目录说「这一期怎么自我介绍」），
> 两处各改一半就对不上。
>
> **搬进平台侧的是「形状」，不是「文案」**：一个平台要哪些字段、
> 限额键叫什么，写在 `platforms/<plat>/publish-spec.json`；
> 这一期的具体文案，仍然写在期目录的 `publish.json` 的 `platforms[<plat>]` 段里。
> 平台段**挪进 `platforms` 下面**（不摊在顶层）：顶层摊开的话
> 「哪些键是平台」就又变回一份写死的清单，而那份清单住在上游。

**好消息：`load_limits()` 已经是「能力即数据」的。** 它现在就是从
`platforms/<plat>/capability.toml` 读限额的（`epmeta.py:173`）。
写死的那部分只是**文案形状**——每个平台要哪些字段、字段叫什么、
怎么量（抖音那套三段拼一个 `text`、B站的 `tags`/`tid`/`copyright`/`no_reprint`）。
所以 M7 不是从零建机制，是**把「能力即数据」从限额扩到形状**。

改完之后：

- `epmeta` 变成**通用加载器**——它仍然住在 `video/pipeline/pyv/`，
  但它不再认识任何平台名，只按目录扫 `platforms/`；
- **平台的文案归平台自己**：一个平台的文案形状（抖音那套单字段 `text`、
  B站的 `tags`/`tid`/`copyright`/`no_reprint`）跟着它自己的规格走；
- 每平台每期每档一份文案 → 期目录的 `publish.json` 的 `platforms[<plat>]` 段；
- 加 YouTube = 建 `platforms/youtube/` + 写规格 + 写它的 adapter，
  **`video/` 一个字都不用改**（文案进期目录，那是内容，不是框架）。

**档位校验落在通用加载器里**：出某个平台的发布物之前，查该平台
`capability.toml` 的 `tiers` 是否含这一档。加载器直接复用
`publishkit.capability.list_capabilities()` 读声明——**不新增第二套能力模型**，
契约层仍然不认识任何平台名。

**「一期一份」的文件在改造后变成「一期一档一份」。** 受影响的不止文案：

| 文件 | 旧形状 | 现在的形状 |
| --- | --- | --- |
| `video/episodes/<系列>/<合集>/<文档>/skeleton.yaml` 讲稿骨架 | 不存在（曾规划 `video/plans/<EP>.yaml`） | **文档目录一份，三档共用** |
| `.../<档位>/contract.json` 画面契约 | `video/contracts/<EP>.json` | 一档一份，**档位在目录里** |
| `.../<档位>/narration.mp3` 旁白 | `video/narration_<EP>.mp3` | 一档一份 |
| `.../<档位>/storyboard.json` | `video/storyboard_<EP>.json` | 一档一份 |
| `video/build/<压平期路径>/` 片段目录 | `video/build/<EP>/` | 压平期路径 |
| `video/out/<压平期路径>.mp4` 成片 | `video/out/<EP>.mp4` | 压平期路径 |
| `video/out/<压平期路径>__vertical.mp4` 竖版 | `video/out/<EP>__vertical.mp4` | 压平期路径 + `__vertical` |
| `.../<档位>/publish.json` 平台文案 | `video/publish/<EP>.json` | 拆到 `platforms/<plat>/publish/<压平期路径>.json`（M7，平台侧） |

骨架**不加档位后缀**——它是三档共用的那一份真相；
它现在住在文档目录里，坐标上本来就与档位无关。

### 5.3 YouTube 平台本体

| 步 | 具体 |
| --- | --- |
| 1 建目录 | `platforms/youtube/__init__.py`，目录名即包名 |
| 2 能力声明 | `platforms/youtube/capability.toml`，`id = "youtube"`，`kind = "video"`，`tiers = ["short","mid","full"]` |
| 3 平台规格 | `platforms/youtube/publish-spec.json`——标题/描述/标签的字段形状与限额来源 |
| 4 adapter | `platforms/youtube/cli.py`，`package = "youtube"`，`command = ["python3", "-m", "youtube.cli"]` |
| 5 automation | `manual` |
| 6 review | `platform` |
| 7 目录 | `outbox/` + `publish/` + `docs/` |
| 8 守卫 | `python3 -m pytest publish/tests -q` |

**`automation = "manual"`** 的理由跟 B 站一样：上传要走平台的凭据体系，
我们手上有没有、能不能长期持有，不确定。没确定之前不写 `api_publish`。
出包 + 人工上传这条路是通的。

**`[limits]` 这一节本次先不写。** 仓库的规矩是「每个数字后面都要写清实测到什么、
还没测到什么」，而且 `platforms/blog/capability.toml` 已经立过先例：
**与其编一个没有依据的数字，不如不声明（不声明就不查）**。
YouTube 的标题 / 描述 / 标签限额要对着平台实测之后再写，
写的时候写清实测日期与来源。

**YouTube 有一个正好对上的原生概念：playlist = 系列。**

| 我们的坐标 | YouTube 的东西 |
| --- | --- |
| 系列 `postgresql/logical-replication` | 一个 playlist |
| 期号 `row-lock` | playlist 里的一条 |
| 档位 | 同一条视频的三个版本，各自一条 |
| 方向（合集） | YouTube 没有原生概念 → 用频道分区 / 播放列表的分组表达 |

playlist 的增删改本身要 API，写在 `platforms/youtube/docs/` 里。

### 6.2 Ceph：预置阶段骨架 + 显式标「筹备中」

**已定：Ceph 预置四个阶段骨架**（对齐 dpdk 的四段式），
每个阶段的 `path_prefix` 指向还不存在的目录；
站点在方向页与学习路径页上给 Ceph 打**「筹备中」**标记。

这样 Ceph 的第一篇文章进来时规则已经就位，而且读者能看见**规划中的课程轮廓**
——这正是「持续学习、持续成长」在站上看得见的样子。

**代价：要给一条现存守卫开口子。**
`tests/test_learning_path.py::test_every_stage_has_articles` 断言
**没有任何阶段是空的**，docstring 明写「An empty stage is a hole in the curriculum
-- remove it instead」。预置四个空阶段当场就红。

开口子的方式必须窄：**只豁免 `status: planned` 的赛道**。
其它赛道里出现空阶段照样红——那条守卫守的是「别在课程里留洞」，
`planned` 赛道不是洞，是**公开宣布的课程大纲**。

所以 `data/learning-path.json` 的赛道对象上加一个状态位：

| 值 | 含义 | 空阶段 |
| --- | --- | --- |
| 缺省（`active`） | 正常赛道 | 不允许 |
| `planned` | 筹备中 | 允许 |

**「筹备中」和「规则缺失」在数据上长得一样**（都是 0 篇），
靠这个状态位区分。兜底阶段仍然要吸收 0 篇——Ceph 兜底吸收 0 篇是
「还没有文章」，不是「文章没规则」。

### 6.3 学习路径：按期号折叠档位

学习路径是**教学轴**，一章一节；视频的三档是同一份内容的三个深度，
不该在路径里出现三次。

规则：

- `data/learning-path.json` 里视频条目写 **期号级** id：`path_exact: "video/row-lock"`；
- 分类器遇到 `video/<ep>-<tier>` 时，**先把档位后缀剥掉**再匹配；
- 渲染时，`video/<ep>` 展开成该期**默认档**（short）内容单元的 permalink。

**但归一化必须改两处，不是一处。** `tools/build-learning-path.py` 里有两套语料：

| 语料 | 怎么算 rel |
| --- | --- |
| `read_posts()` | 按**文件名** → 内容单元改名后是 `video/row-lock-short` |
| `video_corpus()` | 从 Makefile 拿期号，rel 写死 `"video/%s" % episode` → 仍是 `video/row-lock` |

`corpus_mismatch()` **双向比对**这两个集合，不一致就非零退出（CI 硬失败）。
所以剥后缀的归一化必须同时作用在**分类侧**和**交叉校验侧**，
否则「剥掉后缀」跟「语料对不上」两条规则互相打架。

守卫：**每期必须有 short 档内容单元**，否则路径里的链接指向一页不存在的页面。

这样学习路径的语料数仍然是「563 篇母稿 + 6 期视频」，
不因为多一档而膨胀。

### M2 新增 URL 级重定向机制

**这是本次最硬的一块地基，必须先做。**

现有 `data/redirects.json` 只能接住 **`docs/` 下的文章路径**——
`_redirect_target_file()` 拼的是 `os.path.join(DOCS, new_path)`。
它接不住两类 URL：

1. **内容单元的 URL**（`/2026/11/12/video/row-lock/`）——M3 会改它；
2. **学习路径页的 URL**（`/learning/db-internals/`）——M1 会改它。

所以要新加一张 **`data/url-redirects.json`**：键是**旧 URL**，值是**新 URL**，
两边都是站点内的完整路径，逐条显式写：

```json
{
  "/learning/db-internals/": "/learning/postgresql/",
  "/2026/11/12/video/row-lock/": "/2026/11/12/video/row-lock-short/"
}
```

由 `tools/sync-hexo.py` 新增的 `write_url_redirects()` 消费，
在旧 URL 处发一个静态 HTML 跳转页（与现有文章重定向页同构）。

**两类目标要分开处理**：

| 旧 URL 形态 | 目标 | 跳转页落在哪 | front matter |
| --- | --- | --- | --- |
| 帖子 URL（带日期段） | 帖子 URL | `source/<日期段>/<旧slug>/index.md` | 日期段跟着目标走 |
| 页面 URL（**不带**日期段） | 页面 URL | `source/<旧路径>/index.md` | **必须带显式 `permalink:`** |

第二行是必须的：`/learning/db-internals/` 是学习路径页，
hexo 的默认 permalink 是 `:year/:month/:day/:title/`，
不给显式 `permalink:` 它会给自己安一个 `2026/01/01/` 的日期段。

还有一条硬约束：`sync-hexo.py` 开头 `shutil.rmtree(SRC)` **把整个 `source/` 删掉**再重建。
所以跳转页必须由 sync-hexo 自己写（跟现有 `write_redirects()` 一样），
不能手工放进 `source/`。

**为什么不复用 `data/redirects.json`**：那张表的键是**文件路径**，值也是**文件路径**，
URL 是从 git 日期 + slug **推导**出来的。而上面这两类 URL 的目标不是
`docs/` 里的文件，推导不出来。强行塞进去会把「文件在哪」和「URL 长什么样」
两件事搅在一起。

## 十、风险与注意

**风险一：六期的 URL 变更。** 视频内容单元加了档位后缀，六个已发布页面的 URL 变了。
M2 的 URL 重定向机制必须**先于** M3 上线，否则中间会有一批 404。
服务器对未知路径返回 HTTP 200 + 首页（2026-11-14 实测过），所以 404 不会很明显——
**必须用 `curl -I` 逐条查**，不能靠肉眼看页面。

> **存量六期的页面已经随视频线清空重来一起删了**，所以「六个已发布页面的 URL 变了」
> 这条现在没有对象。M2 的 URL 重定向机制本身仍要建——它服务的是**将来**的改名
> （赛道改名、方向改名），不是六期这次。

**风险二：「季 / 系列」改名的实际范围比想象中小。**
多数字幕稿里有「第一季 / 第二季」，但 `字幕-并行解码.md`（EP01）里一个「季」字都没有。
**已发布成片的字幕不动**，新写的口播稿用新措辞。
（存量六份字幕稿已随视频线清空重来删除，这一条现在没有对象；
新坐标下口播稿直接落在档位目录里，档位在目录名上，不加 `-short` 后缀。）

**风险三：档位进 content_id 之后 `data/learning-path.json` 的手维护条目会错位。**
现在 `path_exact: "video/row-lock"` 是手工维护的，六条。档位后缀一加，
这六条全部失配，直接落进兜底阶段 → 第 9 条守卫立刻红。
这是好事——它会**逼着**把那六条从手维护改成推导。改法见 §6.3。

**风险四：方向改名波及站点 CSS 类名。**
`.lane-card--db-internals` 是主题里唯一一处按赛道 id 生成的类名。
改名要同时改 CSS 与 EJS，改漏了不报错，只是赛道卡片掉色——
**这类问题守卫查不出来**，只能靠 §九 的第 1、2 条间接兜住（赛道 id 与目录一致）。

**风险五：Ceph 的空阶段触发守卫。** 见 §6.2。
`status: planned` 那个状态位一定要跟「规则缺失」区分开，
否则第 9、15 条守卫会一直红。

**风险六：`[limits]` 空着的 YouTube 声明。**
不声明就不检查，所以第一次投 YouTube 时可能撞上标题超长之类的问题。
处理办法是**人工核对**，并在 `platforms/youtube/docs/` 里记下实测，

`epmeta` 变通用加载器之后，三个既有视频 adapter 取文案的方式都要改。

> 逐字节这条口径本身仍然有效，它约束的是
> 「骨架裁出来的 short 档与手写的 short 档不许有差别」，等真有存量时再启用。

**风险九：M0 搬错了会静默改掉 URL。**
内容单元的相对布局原样保留，站点 URL 才不变。一旦搬运时多套了一层目录
（`source/_posts/video/row-lock-short.md` 变成
`platforms/blog/site/source/_posts/video/row-lock-short.md` 是对的，
变成 `.../_posts/source/video/...` 就错了），hexo 的 `:title` 段会变，
URL 就变，而**服务器对未知路径返回 200 + 首页**，不会报 404。
所以 M0 的验收必须逐个比对 content_id 集合与站点 URL 集合（验收第 18 条），
不能靠肉眼看页面。

**风险十：`sync-hexo.py` 切两半会切错。**
3032 行、两个角色混在一起。切的时候有两个诱惑：
把 `rewrite_links` / `rewrite_images` 挪到站点侧（因为它们产出 hexo 格式），
或者把 `write_redirects` 挪到平台无关侧（因为它读 `docs/`）。
**两个都不行**：前者动发布层的既有产物，后者把站点的 URL 机制放到平台无关侧。
按 §3.2 的表切。切完跑一遍 `git diff` 看函数是不是**平移**过去的——
有一行逻辑变了，就是切错了。

## 附：术语

| 词 | 指什么 |
| --- | --- |
| 母稿 | 内容的唯一真相。文档流在 `docs/`，视频流在期坐标里（`video/episodes/<系列>/<合集>/<文档>/`） |
| 讲稿骨架 | `video/episodes/<系列>/<合集>/<文档>/skeleton.yaml`，一篇文档一份，三档共用，里面带 `role` 标签 |
| 内容单元 | 文档流的编译产物，在 `content/units/`，一个一个 URL |
| 内容仓库 | `content/units/`——平台无关的内容单元的家 |
| 站点工作区 | `platforms/blog/site/source/`——hexo 的渲染输入，站点自己的 |
| 平台产物 | 某个内容单元在某个平台上的落地形态 |
| 方向 | 一个源码研究方向，一个 `docs/source-tracks/` 下的目录 |
| 系列 | 方向下的连续专题，一个目录；等同于学习路径的一个阶段（源码方向） |
| 期号 | 一期视频，全局唯一 slug，母稿与它一对一 |
| 档位 | 时长档位：`short` / `mid` / `full` |
| 版式 | 画布与品牌变体：`horizontal-branded` / `vertical-nobrand` |
| 合集 | 方向的另一个叫法，站点上的 `/videos/<direction>/` |
