# 术语纪律与反造词

> **这是什么**：一条**内容**判据——文章、目录页、阶段名该怎么措辞。
> 它回答一个具体问题：读者遇到一个不认识的词，是**学到了新东西**，还是**在猜作者在说什么**。
>
> **给谁读**：审稿的人、写稿的人（AI 与作者）。
>
> **判据是文档，不是测试**：什么算「公认术语」机器判不了，
> 只有词表和已被否掉的命名能被 `tools/review-check.py` 固定成信号（TERM-01/02/03）。

---

## 一、为什么

面向同行的技术文章，术语密度是专业感的一部分，但**造词是反效果**：

- 「管线」「心智模型」「抓手」这类词**在本领域没有公认定义**。读者只能从上下文反推，
  推不出来就当成营销词跳过——一句话白写。
- 造词常常是**用一个词替代解释**：「本文建立了一条关于 X 的心智模型」听着有分量，
  其实什么也没说；换成「先说清 X 是怎么分层的，再看它怎么落到代码上」才有信息。
- 造词还会**污染仓库自己的坐标**：目录名、阶段名一旦叫「起步与全景」，
  往后每一篇稿子的链接文字都跟着含糊。
- 造词最常见的形状是**拿一个字当分类单位**：「顶层只分三摊」「中间是五站」——
  「摊」「站」都不是现成的量词，读者只能从上下文反推作者想数的是什么。
  现成的单位是类、组、层、段、块、部分、环节、目录；
  要数几样东西，就用这些词，别自己造一个。

所以判据不是「少用术语」——恰恰相反，是**用有定义的术语**。
专业性来自「调用链」「MVCC」「checkpoint」「WAL」这种读者查得到的词，
不来自「范式」「抓手」「心智模型」这种自造的词。

## 二、总则三问

审稿时对着这个词问三句：

1. **这个词有公认定义吗？** 有 → 用它。首次出现给一句话定义或英文原词
   （「行锁（row lock）」），后文直接用。
2. **没有公认定义？** → 换成通用描述：「一条处理流程」「理解这件事的方法」
   「具体做法」「这一层」。把包装拆掉，露出对象、步骤、条件。
3. **拿不准？** → **写具体的做法、对象、步骤**，别用词替代解释。
   读者读到的是事实还是包装，是这一条判据的落点。

## 三、硬禁词（TERM-01）

> 这三张表的**唯一一份**在 [`../../rules/terminology.json`](../../rules/terminology.json)
> （读取器 `tools/terminology_rules.py`）。同一份文件里另有标题用的两张表，
> 见《[标题与章节顺序](2026-11-24-标题与章节顺序.md)》。
> 本文是**人读的那一半**：为什么禁、怎么换、什么算例外。
> 机器读的那一半只管「有没有这个词」。

这些词在本领域**没有公认定义**，一律换：

| 词 | 换成 | 例子 |
| --- | --- | --- |
| 管线 | 流程（说清是什么在流转） | 「发布管线」→「发布流程」；「一条 SQL 的管线」→「一条 SQL 从解析到返回的完整流程」 |
| 心智模型 | 方法论 / 技术原理 / 理解方式 | 「建立一套心智模型」→「先把分层讲清楚，给出一个读源码的固定顺序」 |
| 抓手 | 具体做法 / 关键步骤 / 着力点 | 「找准抓手」→「先量一遍 p99，别先改代码」 |
| 拉齐 | 统一 / 同步（说清谁跟谁） | 「跟上下游拉齐口径」→「跟发布脚本统一字段名」 |
| 三摊 | 三类 / 三块 / 三部分 | 「顶层只分三摊」→「顶层分成三类：内核本体、对外接口、扩展与工具」 |

**表里为什么只有「三摊」这么具体的写法**：检查器是**子串匹配**，
一个单字进来就会误伤（「摊」撞上「摊开」，「站」撞上「第五站」）。
所以词表守得住的只有**已经被否掉的具体写法**；
「拿一个字当分类单位」这个**类别**，靠第一节那条与第三节的总则去人判。

**例外**：引用外部材料时保留原名（论文标题、产品名里的 “mental model”），
第一次出现补一句中文说明它在这儿指什么。

## 四、建议具体化（TERM-02）

不是硬禁，是「换个说法更好」——这两词在中文技术写作里已经常见，
但它们常常代替了本该写出的事实：

| 词 | 换成 |
| --- | --- |
| 沉淀 | 积累 / 整理成 / 总结成（说清留下了什么） |
| 底座 | 基础设施 / 底层能力 / 公共库（说清它是什么） |

## 五、命名（TERM-03 + 人工判断）

目录名、阶段名、标题与正文同一把尺子：**这一段回答什么问题，就叫什么**。

不合格的是**两个抽象名词拼起来的对仗短语**——「起步与全景」「实战与故障现场」。
读的人从名字里看不出里面有什么，导航就失去了导航的作用。

合格的样子：

| 名字 | 为什么合格 |
| --- | --- |
| 架构总览 | 说得出这一段讲什么 |
| 存储引擎：页、文件与内存 | 点得出具体对象 |
| 事务、MVCC 与并发 | 列得出三样东西 |
| 索引与查询执行 | 两个都是公认概念（不是「查询管线」） |

判定法：**把名字里的抽象词换成「这一段实际讲的东西」，还能站住吗？**
站不住 → 名字不合格，改到站得住为止。

已经被否掉的名字进 TERM-03 黑名单（机械可查）；
通用规则靠人判断——机器分不出「存储引擎」和「起步与全景」的差别。

## 六、机械检查

词表是**共享规则文件** [`../../rules/terminology.json`](../../rules/terminology.json)，
读取器 [`../../tools/terminology_rules.py`](../../tools/terminology_rules.py)——
层与层之间共享的是**文件**，不是 import（见 `rules/README.md`）。

`tools/review-check.py` 的三条信号：

| 信号 | 级别 | 内容 |
| --- | --- | --- |
| `TERM-01` | warn | 硬禁词（第三节词表） |
| `TERM-02` | info | 行话建议具体化（第四节词表） |
| `TERM-03` | warn | 已被否掉的命名（第五节黑名单） |

扫描范围是**整篇原文**，含 front matter 与代码块——description 会出现在站点列表页，
mermaid 标签会出现在图上，都是读者看得见的地方。

**适用范围**：对外内容（`docs/`、`drafts/`）。
仓库内部的 specs / plans / 代码注释说的是工程语言——那里的「渲染管线」
是准确的技术描述，不按这条判据改。

学习流的阶段名登记在 `platforms/blog/site/data/learning-path.json`，
那是站点数据（JSON），检查器只读 markdown，所以由人守：
阶段名与 `docs/` 里的目录页标题必须一致。

## 七、与其他判据的关系

- 「让抽象话落地」（审校原则第 3 条）是这条的上位原则：
  造词通常出现在「想说得有力」的地方，而落地要求把话写实。
- 「常见 AI 味信号」里的第 5 条（自造术语与对仗式命名）由本判据展开。
- 判据服从稿件：**先改稿**（把词换成说法、把名字换成内容），不改判据。
