# 顶层设计：主题、草稿箱、两条流水线、六个第三方平台

## 一、意图

### 1.1 核心理念

这一轮的顶层设计，是把**整条内容生产链**重新说一遍清楚。理念是这么一句话：

> **输入一个主题**，手动编写或自动生成内容，**放入草稿箱**
> （写的文章先进入草稿箱），经过 review 后进入第三方平台
> （第三方平台包括博客，即 growdu.cn 也属于第三方平台）、video。
> 这是**文档的顶层流向（文档流）**。
>
> 而**视频流**则是从草稿箱流入 video，根据各平台生成内容，
> 流出经过内部 review 流向各个视频平台。
>
> 按内容划分是**两条流水线**，但是**启动内容都是草稿箱里的文档**。
>
> **加平台影响的是第三方平台适配**（包括内容和视频），
> 第三方平台又有各自的规则。
> 第三方平台的核心流程主要包括：根据草稿箱内容进行**内容适配**、
> **视频生成**，然后 **review**，然后 **output**，最后再自动 **upload**。

### 1.2 确切的逻辑流

**两条流水线，两条线，各自有明确的入口与出口：**

```
① 文档流   draft ──▶ review ──▶ docs  ──▶ 第三方平台（文档类）
② 视频流   draft ──▶ review ──▶ video ──▶ 第三方平台（视频类）
```

要点有三个，一个都不能含糊：

1. **`draft` 的下游才是 `docs`。** `docs/` 是**第二段的产物**，
   不是流水线的起点。母稿在 `docs/`，但它是从草稿箱里**审出来的**。
2. **两条线的入口完全一样**（都是 `drafts/`），出口按内容形态分家：
   文档流喂文档类平台，视频流喂视频类平台。
3. **第三方平台在两条线的下游**，不分家——文档类平台与视频类平台
   接的是同一种接缝（一份能力声明、一份发布清单）。

主题（一段话）是流水线的**输入**，不是一层的目录：

```
主题（一段话）
     │
     ├──▶ 手动编写 ──┐
     │               ├──▶ drafts/ ──▶ review ──▶ docs / video ──▶ 第三方平台
     └──▶ 自动生成 ──┘
```

### 1.3 存量：`docs/` 里已经有的那 560 篇

`docs/` 现在有 **560 篇内容单元**（另有 61 个目录页），
`video/` 现在有 6 期成片。它们是**存量**。

**存量不是「本该从草稿箱出来的东西」。** 它们是在草稿箱这一层存在之前
就写完、审过、发过、验证过的，现在停在流水线的**第 2 段出口**
（`review → docs` / `review → video`）。它们**不倒回去**走 `draft → review`。

草稿箱约束的是**新内容**：从这一轮起新写的稿子，
先落 `drafts/`，过总审核，再进 `docs/` 或 `video/`。

为什么要专门说这一句？因为不这么说，就会问出一个**没有答案**的问题：

> 「那 `docs/` 里这 560 篇的草稿在哪？」

答案是**没有，也不需要有**。把存量当成「本该从草稿箱出来的东西」，
会顺着一个错误的推论走到底——「草稿箱是多余的」——
然后把这一层删掉。那才是真正的事故。

### 1.4 现状跟理念差在哪

理念是清楚的，现状差了**三块**。

| # | 差距 | 现状 | 理念要求 |
| --- | --- | --- | --- |
| **G1** | **主题这一层不存在** | 草稿箱是入口，但**入口之前是空的**——「这一篇为什么写」的落点没有 | 主题是流水线的起点 |
| **G2** | **站点不在平台层** | `platforms/` 下有五个平台；growdu.cn 走 `docs/` → `sync-hexo.py` → `public/` 的**另一条路** | 第三方平台有**六个**，站点是其中之一 |
| **G3** | **平台层的通用流程没有写下来** | 「适配 → 生成 → review → output → upload」这五步散在六个平台的实现里，**没有一处统一表述**，也没有一处统一入口 | 五步是第三方平台的**核心流程**，所有平台同构 |

G2 是最扎眼的：目录里数得出来**五个**平台，设计里说的是**六个**；
「加平台只动 `platforms/`」这句话对站点**不成立**——站点根本不在 `platforms/` 里。

G3 的代价是**每一次加平台都要重新想一遍流程**。
五个平台各自实现了一遍「适配 → 出包 → 发」，顺序大同小异但没人写过对照表，
所以新平台的作者只能去读别人的代码猜流程。

### 1.5 这一轮要做什么

**先加层，先定架构**——把三层补齐、把流程写下来、把目录摆对，
**不做大规模迁移，不追求一次跑通**。

具体三件事：

1. **站点进平台层**：`platforms/blog/`，与另外五个同构（补 G2）；
2. **主题落进草稿箱**：草稿的 front matter 里多一个 `topic:` 字段，
   主题不建目录、不单独成层（补 G1）；
3. **第三方平台层写清楚**：`platforms/README.md` 统一表述五步流程与共同规矩
   （补 G3）。

### 2.2 六个平台

| id | 名字 | 内容形态 | 自动化档位 | 发布前审核 | 实现住在哪 |
| --- | --- | --- | --- | --- | --- |
| `wechat` | 微信公众号 | 文档 | `api_draft` | 平台机审 | `platforms/wechat/` |
| `toutiao` | 头条号 | 文档 | `manual` | 平台机审 | `platforms/toutiao/` |
| `blog` | **个人站点 growdu.cn** | 文档 | **`api_publish`** | **本地预检** | `platforms/blog/`（构建链在 `platforms/blog/site/`） |
| `douyin` | 抖音 | 视频 | `manual` | 平台机审 | `platforms/douyin/` |
| `channels` | 微信视频号 | 视频 | `manual` | 平台机审 | `platforms/channels/` |
| `bilibili` | 哔哩哔哩 | 视频 | `manual` | 平台机审 | `platforms/bilibili/` |

### 2.3 站点构建链为什么住进 `platforms/blog/`

站点的构建链（hexo、主题、`sync-hexo.py`、`public/`）现在挂在**仓库根**，
而站点在**平台层**。同一个东西被拆在了两层：
「站点是平台」这句话只对了 `capability.toml` 那一小块，
构建链还在外面飘着。

三个后果：

1. **「加平台只动 `platforms/`」对站点仍然不成立**——
   改站点主题要动仓库根，改站点构建要动仓库根。
2. **仓库根越来越杂**——`_config.yml`、`themes/`、`scripts/`、`theme-assets/`、
   `package.json` 混在根上，看不出是给谁用的。
3. **接缝被稀释**——站点成了唯一一个「adapter 在别处」的平台，
   而接缝原则（契约层不 import 平台层、平台层不 import 契约层）
   正是靠「每个平台自成一目录」撑住的。

搬进去之后，「六个平台一个规矩」才真的成立：
**目录名 = 平台 id = 包名 = 快照后缀 = 实现的住处**。

### 2.4 流程

**平台层五步（每个平台各来一遍）：**

```
内容单元 ──适配──▶ 平台内容 ──生成──▶ 产物 ──review──▶ ──output──▶ 可发布的东西 ──upload──▶ 平台
```

**六个平台在五步上的具体形态**（详表见 `platforms/README.md` §三）：

| 步 | 别的五个平台 | 站点 |
| --- | --- | --- |
| 适配 | 按限额裁标题、压正文、配图 | `platforms/blog/site/tools/sync-hexo.py` |
| 生成 | 渲染成平台版式 | hexo + `platforms/blog/site/themes/matery/` |
| review | 平台机审 + 人工预览 | `platforms/blog/site/tools/check-*.py` + `site-guard.yml` |
| output | 一篇一个包 | **整个 `public/`**（2400 个页面 / 167 MB） |
| upload | 调平台 API / 浏览器自动化 | CI：rsync + GitHub Pages |

## 三、逐项决策

| # | 决策 | 取舍 |
| --- | --- | --- |
| D1 | **站点住 `platforms/blog/`，与另外五个同构** | 「加平台只动 `platforms/`」对站点才成立。代价：站点从此在平台层里有一份声明，那份声明的**出包方式**跟别人不一样（见 D4） |
| D2 | **主题不建目录，落进草稿的 front matter `topic:`** | 主题是一段话，不是一个分类。给它建目录，就会长出「主题/xxx/」这样的层级，然后有人会想「主题要不要也进站」。**不给它目录，它就只能是输入** |
| D3 | **主题不是流水线的一层** | 它是**输入参数**，不是内容单元，不产生产物，不进站。流水线仍然是**两层**（文档流 / 视频流），入口都是草稿箱 |
| D4 | **站点的 adapter 没有 `publish` 子命令** | 站点是**全量构建**（一次 push 重建 2400 个页面），不是逐篇出包。把逐篇出包重写一遍等于把 `sync-hexo.py` + hexo 再写一遍，**两份必然漂移**。代价：站点与其他五个平台的 CLI 形状**不一样**——这在「同构」这个词下是个例外，明写出来 |
| D5 | **站点的能力声明不声明标题/正文限额** | 声明一个数就是**许诺**一个数：契约层会拿它当闸，超了判违规。站点不吃那套限额。与其编一个没依据的数字，**不如不声明**（不声明就不查）。代价：`[limits]` 里只剩 `image_bytes` 一项，比别的平台单薄——但那是**诚实**的单薄 |
| D6 | **`outbox/` 先空着，不预填快照** | 全仓库快照总数有一条守卫断言**恰好 566**（另外五个平台的账）。预填会红。而且站点没有 `published_at`——只有 git 历史，回填是**另一个动作**，不是一个顺手的事 |
| D7 | **这一轮不写测试、不搬内容** | 用户定的口径：「先加层，先定架构，不着急进行测试验证」。代价：新加的 `platforms/blog/` **暂时没有 `tests/`**，守护靠的是既有的那几条通用守卫（目录名 == id、adapter 存在、模块存在） |
| **D8** | **`docs/` 里现有的 560 篇是存量，不倒回去走草稿箱** | 存量在草稿箱这一层存在之前就已经审过、验证过。**草稿箱约束新内容，不追溯存量**。代价：仓库里同时有两种「进 `docs/` 的方式」——新稿走 `drafts/`，存量是历史事实。**这条要在文档里写明**，否则半年后有人会问「这批文章的草稿在哪」，而那是个没有答案的问题 |
| **D9** | **站点的构建链搬进 `platforms/blog/site/`** | 「加平台只动 `platforms/`」对站点才**完整**成立。代价：仓库根少了一批文件，CI 的工作目录、产物路径、`.gitignore` 规则、`node_modules` 的位置全都要跟着改——**这是一次真搬移，不是登记**（见 §4.2）。**内容单元除外**：它是所有平台共用的，搬进 `platforms/blog/site/` 就成了「共用的契约住在某一个平台里」，所以它去 `content/units/`（见《层间接口与内容坐标系》§3.2） |
| **D10** | **搬移分两批：先搬配置与产物，再搬脚本** | `themes/`、`_config*.yml`、`public/`、`source/` 先搬（影响面小、看得见）；`tools/` 里那二十来个脚本后搬（引用面大：CI 27 处、测试 45 处）。分两批是为了**每批都能独立验一次**，而不是一把搬完再/debug |

### D1 的取舍细节：站点凭什么算「第三方平台」

「第三方」这个词本来指「内容发到别人的地盘上」。
站点是自己的地盘——**但它仍然是第三方**，理由有三条：

1. **它有它自己的规则。** 站点的分类链深度、构建排除目录、图片大小取舍、
   主题的渲染约束——**都不是内容契约定的**，是站点自己定的。
   「内容 → 站点」这一步一样要做**适配**。
2. **它有它自己的发布动作。** rsync + GitHub Pages，与「调平台 API」是同一类事：
   把一个产物送到一个站上去。
3. **它有自己的账号体系与边界。** Gitalk 评论、站点统计、PV——
   跟公众号的 `media_id` 是同一种东西：**平台侧的身份**。

反过来，**契约层不需要为站点写任何代码**——
它按目录扫能力声明就认出了第六个平台。**这才是「加平台只动 `platforms/`」的完整含义**。

### D4 的取舍细节：为什么「同构」在这里要打折

六个平台同构的部分：能力声明格式、outbox 快照格式与文件名约定、
接缝方式（不互相 import）、共同的五步流程。

**不同构的部分只有一处：出包粒度。**

- 那五个是「一篇一个包，发一篇」→ outbox 天然是**幂等键**；
- 站点是「整站一份」→ outbox 记的是**当前在站上是什么状态**（**账**，不是**锁**）。

这一处差别必须写下来，否则下一个人会拿着「幂等键」的心智模型去理解站点的快照，
然后发现「重发一遍」在站点上根本不是错误——**每次 push 都重发全站**。

### D8 的取舍细节：为什么存量要单独点名

流水线的图很容易画成「所有内容都从 `drafts/` 出来」。
但仓库里的事实是：`docs/` 已经满了，**一篇草稿都没有**。

这两种说法同时挂在嘴上，会产生一个**假矛盾**，
然后引出两种都错的修法：

- 修法一：「草稿箱是多余的」——把这一层删掉。**错**：
  新的稿子确实需要一个「审之前先存着」的地方，否则审校记录没有对照物。
- 修法二：「那得给 560 篇补草稿」——倒灌 560 份历史底稿。**也错**：
  草稿箱的价值是**审校痕迹**，给已经审过的存量补一份，只会造出
  560 份「审校前长什么样」的假记录。

正确的说法只有一句：**草稿箱在 `review` 的上游，`docs/` 在 `review` 的下游；
存量停在下游，不回上游。**

### D9 的取舍细节：搬之前先看清什么跟着走

搬 `public/` 与 `themes/` 是**搬目录**；搬 `tools/` 里那二十来个脚本是**改引用**。
后者才是真正的工作量：CI 的 `hexo.yml` 里有 27 处 `tools/...`，
根 `tests/` 里有 45 处，`publish/publishkit/` 的注释里还有若干处。
所以 D10 把它分成两批。

**搬移不改变任何行为**——脚本的代码一行不改，只改「在哪儿」和「怎么被找到」。
这是这次搬移唯一的纪律：**只改路径，不改逻辑**。

## 六、验收

**这一轮是「加层」，验收看的是「层加对了没有」，不是「跑通了没有」。**

1. `platforms/` 下有**六个**平台目录，每个都有 `capability.toml`，
   且 `id` == 目录名；
2. `cd platforms && python3 -m blog.cli status` 能跑通并打印出
   平台信息、限额、560 篇内容单元、0 份快照；
3. `cd platforms && python3 -m blog.cli check <一篇真实文章的路径>` 能跑通，
   打印标题、构建排除判定与分类链；对一个不存在的路径**退出码非 0**；
4. `platforms/blog/outbox/` 里**没有 JSON**；
5. 全仓库 outbox 快照总数**仍是 566**（`publish/tests/test_schedule.py` 的守卫不红）；
6. 既有的通用守卫全绿：
   `python3 -m pytest publish/tests -q`；
7. 根 `README.md` 的架构图与目录速查跟实际目录一致；
8. `drafts/README.md` 写清楚了主题是什么、为什么不建目录；
9. **文档把存量说清楚了**：根 `README.md`、`drafts/README.md` 与本文 §1.3
   都要写明「`docs/` 里现有的 560 篇是存量，不倒回去走草稿箱」。

**明确不在这一轮的验收里**（下一轮再说）：

- `platforms/blog/tests/` 的存在；
- outbox 快照的回填；
- 自动生成器；
- 面向读者的文章（`docs/platform-meta/`）；
- **站点构建链的物理搬移**（§4.2）——搬移自带验收：站点能构建、产物路径对、
  CI 能跑。

## 七、风险与注意

| 风险 | 处理 |
| --- | --- |
| **加了第六个平台，把「同构」说过头了** | 差别只有一处（出包粒度），但这一处**写在三处**：`platforms/README.md` §二、`platforms/blog/docs/01-站点即第三方平台.md` §二、根 `README.md` §2.5。三个地方都明写「唯一差别」 |
| **`outbox/` 被人随手填几份快照试试** | `platforms/blog/outbox/README.md` 里明写了那条 566 的守卫，并说明「回填是成批的、可重放的动作」 |
| **站点能力声明里的数字将来不成立** | `verified = "2026-11-18"` 记着复核日期；`[limits]` 里只有一个数字，且注释写清了它是**我们自己的取舍**、不是站点的限制 |
| **`build/`、`out/`、`tests/` 这类工程目录名进了 `docs/`** | `platforms/blog/__init__.py` 里抄了一份 `EXCLUDED_DIR_NAMES`（与 `sync-hexo.py` 同源），`check` 会判「构建会排除它」。**改那边要改这边**——这是明知的重复，九个名字，两年不会变 |
| **「主题」被当成一层来实现** | `drafts/README.md` 里明写「主题不是一层，也不是一个目录」。D3 也记在本文 §三 |
| **有人把 `topic:` 字段透传进站点 front matter** | `topic` **不在** `publishkit.contract` 的 `PASSTHROUGH_FIELDS` 白名单里——它不会被搬到 `content/units/`，站点上看不到它。要透传得改白名单，那是另一个决定 |
| **把存量当成「该走草稿箱的东西」** | D8 + §1.3 明写：存量停在 `review` 的下游，不回上游。**不给 560 篇补草稿**——补出来的是假记录 |
| **搬移时顺手改了脚本的行为** | D10 的纪律：**只改路径，不改逻辑**。搬完的验收是「站点照样构建出来」，不是「脚本重写了一遍」 |
| **搬移把 CI 弄坏了**（hexo.yml 里 27 处路径） | 分两批搬，每批单独验。CI 的产物路径、`npm install` 的目录、hexo 的工作目录是三个必须同时改的地方，漏一个就发不出站点 |
| **`source/all/`、`source/recommended/` 是 git 跟踪的** | 这两个目录不在 `.gitignore` 的忽略范围里，搬的时候要**跟着 `git mv`**，不能当成产物丢掉 |

## 九、附：术语

| 词 | 意思 | 在哪 |
| --- | --- | --- |
| **主题** | 用户产生 idea 时输入的**一段话**，记着核心思想。**不是一层，不建目录**，落进草稿的 front matter `topic:` 字段 | `drafts/README.md` §一 |
| **草稿箱** | 两条流水线的**共同入口**。稿子先落这里，审完也留着 | `drafts/` |

| **母稿** | 文档流在 `docs/`、视频流在 `video/` 的那一份。**真相只在这里** | 既有说法 |
| **存量** | `docs/` 与 `video/` 里**在草稿箱这一层存在之前**就写完、审过、验证过的内容。停在 `review` 的下游，**不回上游** | 本文 §1.3 |
| **文档流** | `draft` → `review` → `docs` → 第三方平台（文档类） | 本文 §1.2 |
| **视频流** | `draft` → `review` → `video` → 各平台生成内容 → 成片层审核 → 视频类平台 | 本文 §1.2 |

| **能力声明** | `platforms/<plat>/capability.toml`：限额、档位、审核方式。**能力即数据** | 既有说法 |
| **outbox 快照** | 一个内容单元在一个平台上的发布状态。**文件名就是幂等键** | `publish/publishkit/manifest.py` |
| **接缝** | 契约层与平台层之间只有两处接缝：同一份 `capability.toml`、同一份 manifest JSON | `platforms/README.md` §二 |
| **总审核** | 根 `review/`（文章）与 `video/review/`（成片）。管「内容本身对不对」 | 既有说法 |
