## 一、这套架构要解决什么

**一句话：让「内容」与「发布」这两件会一直变的事，各自住在自己的模块里；
模块之间只通过文件上的接口说话。**

要解决的四个问题，都是「会一直变」的：

| 会一直变的 | 所以架构要给它什么 |
| --- | --- |
| 内容（写、审、改、删） | 一个**唯一**的真相与一条单向的路：草稿 → 审 → 母稿 → 内容单元 |
| 平台（加平台、改限额、换发布方式） | 一个**目录即接口**的注册表：加平台只动 `platforms/` |
| 身份（站名、品牌、账号、地址） | 一条**缝**：框架源码里不许出现站名，值全在使用者那一侧 |
| 验收（加模块、改接口） | **各模块各跑各的**：谁改了什么，只有谁的套件会红 |

### 这一版明确不做

- **不做内容。** 仓库里现在一条面向读者的内容都不剩——这是「只做框架，不做内容」的直接结果。
- **不做整站快照验收**（页面清单 / 死链基线放 `/tmp`，会被清）。
- **不做「全套测试合跑一遍」当验收。**
- **不做通用的插件系统。** 六个平台是目录，不是注册表里的条目。
- **不把浏览器自动化做成通用发布框架。** `browser/` 只服务那几个没有公开 API 的平台。

## 二、九个模块

| # | 模块 | 住在哪 | 它拥有（写） | 它不碰（读别人的内容） |
| --- | --- | --- | --- | --- |
| 1 | 草稿层 | `drafts/` | 在改的稿子 | 不发布 |
| 2 | 母稿层 | `docs/` | **唯一的内容真相**：已过审的稿子与分类页 | 不发布 |
| 3 | 审校层 | `review/` | 什么算「已过审」的判据：规则、范围划分、审校记录 | 不碰正文 |
| 4 | 编译器 | `tools/build-content-units.py` → `content/units/` | 内容单元这一层产物 | 只读 `docs/` |
| 5 | 站点 | `platforms/blog/`（含 `site/`） | 六个平台之一的 adapter + Astro 工程 | 只读内容单元与母稿 |
| 6 | 平台适配层 | `platforms/{wechat,toutiao,douyin,bilibili,channels}/` | 每个平台一份能力声明与出包逻辑 | 只读内容单元 |
| 7 | 契约与发布层 | `publish/` | 能力模型、内容契约、发布清单、调度、规格 | 只读能力声明与内容单元 |
| 8 | 视频线 | `video/` | 视频生产：人格 / 形象 / 音色 / 片头片尾 / 流水线 | 不读 `docs/` 的文章 |
| 9 | 发布执行器 | `browser/` | 把「人在平台后台手动做的事」做成命令 | 只读出包目录 |

> **1–3 是内容侧，4 是内容侧的出口，5–7 是发布侧，8–9 是视频与执行侧。**
> 视频线（8）自成一条闭环：它的产物是**内容单元**（`content/units/video/`），
> 于是它跟发布侧的接口跟文档视频走的是同一条，不另开一道门。

## 三、模块之间只通过四处说话

### 缝 1：内容单元（`content/units/`）

编译器写，所有 adapter 读。**它是构建产物，不入库**（`.gitignore`），
CI 里现编。

- 一篇文档 = 一个内容单元 = 一个 markdown + 一份 front matter；
- 正文**一个字都不改**——编译器只推导与拷贝 front matter；
- id = 相对 `content/units/` 的路径（不带 `.md`）；
- 分类页是 `kind: category` 的单元，id 去掉 `_index` 尾巴。

### 缝 2：能力声明（`platforms/*/capability.toml`）

adapter 写，契约层**按目录扫出来**（`platforms/*/capability.toml`，
**目录名就是平台 id**）。契约层因此不需要为任何平台写代码，
也不需要知道有哪些平台。

视频线也读这一份声明的 `[limits]` 段（`video/pipeline/pyv/epmeta.py`
的 `load_limits`）——同样**只读文件，不 import**。

### 缝 3：身份（各模块自己的配置）

框架源码里**不许出现站名**（`platforms/blog/site/tests/test_site_config.py` 守着）。

| 谁的 | 缝在哪 | 环境变量 |
| --- | --- | --- |
| 站点 | `platforms/blog/site/data/site.json` | `SITE_URL`（Astro 构建与 CI 用同一个） |
| 视频线 | `video/config.toml`（`[brand].*` / `[character].*`） | `VIDEO_CONFIG`（指向另一份配置） |
| 发布层 | `publish/deploy/*.template`（`com.example.*`） | —— |

### 缝 4：验收（各模块各跑各的）

每个模块一条命令，跑在自己的目录里。命令清单与实测数字见
[`acceptance/README.md`](../../acceptance/README.md)。

### 还没成缝的一处：**URL 规则**

站点的 URL 规则现在**只在站点的 TypeScript 里**
（`site/src/lib/urls.ts`，注释里明写「站点里只有这一处决定链接长什么样」）。
但根 `tools/` 的视频编译器与 `publish/` 的契约层**都要算同一个地址**，
它们算出来的是 hexo 时代的形状（见 §五 第 10 条）。

于是「一篇文章的地址是什么」现在有**两份答案**，而其中一份是死的。
**要么把 URL 规则提成一处共享的规则（新的缝），要么让站点从那边取
（现有的缝上加一个接口）——这不是「抄一下 `urls.ts`」能了的事，
抄一份就是又造一个漂移源。**

## 四、依赖方向

**现在仓库里两个模块互相 import 的地方是 0 处。** 这不是巧合，是规矩：

- 契约层**不** import 站点层，站点层**不** import 契约层——
  两边唯一的接缝是同一份 `capability.toml`；
- 契约层**不** import 任何 adapter（它按目录扫）；
- adapter 之间**不**互相 import（各发各的平台）；
- 上层要下层的东西，**只准通过文件要，不准通过 import 要**——
  这条让「加一个平台」「换掉一个平台」都只是目录的事。

方向：

```
docs/ ──编译──▶ content/units/ ──▶ 各 adapter（站点 / 微信 / 头条 / 抖音 / B站 / 视频号）
   ▲                  │                        │
   │                  ▼                        ▼
drafts/         platforms/*/capability.toml   publish/（按目录扫，不 import）
                                                  │
review/（判据）                                    ▼
                                             browser/（只服务没有公开 API 的平台）
```

## 五、这轮清库暴露的接口缺口

**写明，不装作没有。** 每一条都要人拍板，不是「顺手就修」的活。

| # | 缺口 | 后果 | 可能的修法 | 归谁 |
| --- | --- | --- | --- | --- |
| 1 | **期号字段在编译时被静默丢掉**。`tools/build-content-units.py` 的 `PASSTHROUGH` 只有 title/date/author/description/tags/top/draft，没有 `episode:*`；而契约层仍按 `episode:*` 校验期号 | 期号区块会是空的，**页面照常渲染**（静默失败） | 编译器透传 `episode:*`，或者契约层不再假设内容单元带期号 | 编译器 + 契约层 |
| 2 | **分类归档页地址在站点上不存在**。微信 adapter 拼 `{站点}/categories/{slug}/`，Astro 站点**没有** `/categories/` 路由（分类页在 `/docs/<id>/`） | 公众号文章里的「阅读原文 → 分类归档」指向不存在的地址；站点是软 404（返回 200 + 首页），探活看不出来 | 分类名 → 分类内容单元 id 的映射，落到 `/docs/<id>/` | 微信 adapter + 站点 |
| 3 | **adapter 读的是站点的副本，不是内容单元仓库**。`I3`（内容单元 → toutiao/wechat）因此只能验「副本与内容单元逐字节相同」 | 图片落点与解析基准还挂在站点那一侧，两个 adapter 各自带着一份假设 | 图片落成 `content/units/images/`，解析基准改成显式的图片根 | 编译器抽取那一轮 |
| 4 | **`tools/site_root.py` 还读着已删的 `_config.yml`**（hexo 时代的挂载点推导） | 它现在只会退化成空串；发布层还有一条测试 import 它 | 删掉它，或者把「部署挂载点」这条缝重新定义（站点现在 `base: '/'`） | 契约层 |
| 5 | **`browser/` 还没进验收矩阵** | 它的 1 条红没人知道是存量红还是新红 | 把 `browser/` 加进 `acceptance/README.md` 的矩阵 | 验收那一层 |
| 6 | **站点套件的「站点重做后基线」是 26 条，实际现在是 51 条** | 验收文档里的数字对不上，读者会以为少了用例 | 数字随实现走，验收文档要定期对账 | 验收那一层 |
| 7 | **两条工作流监听的是 `master`，而仓库的默认分支是 `main`** | `contracts.yml` 与 `site.yml` **从来没跑过**——闸门形同虚设 | 已修（`d1da8f2d`）：两条都改听 `main` | 验收那一层 |
| 8 | **抖音 adapter 有 19 条红，没人跟踪**（它不在 CI 里） | 全是「被测对象没了」：`pyv.epmeta.PUBLISH_DIR` 随视频线清空一起没了，六期具体内容也没了 | 按 publish 那套做法，把用例改成自己在 `tmp_path` 里造期 | 抖音 adapter |
| 9 | **I2（契约层 ↔ 内容单元）现在没有测试钉着** | 原来钉它的是一条真跑 `sync-hexo.py` 的集成用例，那个脚本删了，用例也删了 | 照着现在的编译器写一条新的 | 契约层 |
| 10 | **两处算出来的「一篇文章/一期的地址」还是 hexo 时代的形状**，而站点已经不是那个站了。站点的 URL 规则只有一处：`site/src/lib/urls.ts`（文档 `/docs/<id>/`、视频 `/videos/<slug>/`），**站点没有重定向**。<br>① `publish/publishkit/episode.py` 的 `landing_url` 拼 `/YYYY/MM/DD/<content_id>/`；<br>② `tools/build-video-pages.py` 的 `permalink()` 拼同样的形状，用它改写视频页正文里的兄弟期链接 | ① 下一次发布记进 outbox 的 `published_url` 就是死链（**现在 outbox 全空，还没造成损失**）；② 视频页正文里的互链全是死链（**现在视频内容也没了，暂时看不出来**） | 两处都改成按 `urls.ts` 的规则拼；`tools/site_root.py` 一起退役——它是 hexo 挂载点的遗物，读的 `_config.yml` 已经不存在。**但这两处在根 `tools/` 与 `publish/`，都不该直接抄站点的 TypeScript——要么把 URL 规则提成一处共享的规则，要么让站点从那边取** | 编译器 + 契约层（**要先定口径**） |
| 11 | **视频线跟三个视频平台 adapter 对「一期是什么」没有共同口径**。三处对不上：<br>① **成片的路径**：流水线出的是压平的 `out/系列-合集-文档-档位.mp4`（`episodes.ep_id()` 把斜杠换成连字符），adapter 找的是 `out/系列/合集/文档/档位.mp4`（斜杠原样）——**adapter 永远找不到成片**，除非手工传 `--video`；<br>② **期身份**：`contract.json` 的 `episode` 是**三层文档路径**，adapter 传的是**四层期路径**，`epmeta.check_meta` 因此报「元数据的 episode 与契约里的对不上」；<br>③ **快照文件名**带斜杠，落成 `outbox/系列/合集/文档/档位__douyin.json` 这样的嵌套目录，而 outbox 是要入库的**扁平** JSON 目录 | 抖音 / 视频号 / B站三个 adapter **出包这一步跑不通**（抖音 / 视频号 / B站都受影响） | 定一条「期身份」口径（文档路径还是期路径？成片用压平名还是分目录？），两边都按它来。**这是接口决定，不是某一边改个常量能了的** | 视频线 ↔ 平台适配层（**要人拍板**） |

## 六、这一版之后仍然不做的

- 不回炉存量内容（`docs/` 现在只有规则模板与目录页，这是对的）；
- 不把 `content/units/` 入库（它是产物）；
- 不做整站快照验收；
- 不做平台插件系统；
- 不让发布模块读 `drafts/` 的内容（草稿层只在母稿层与审校层的视野里）。
