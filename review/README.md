新的稿子、还有对旧稿的改动，都先落 `drafts/`，审完复制进 `docs/`（或 `video/`）；本目录存审校记录与复盘。

# 博客内容审校（review）

这里存放对 `docs/` 中博客内容的审校任务、修改建议与复盘记录。

**审的是哪一份**：稿子先落 `drafts/`（新增与改动都在那儿做），审完才进 `docs/`。
所以本文这套规则审的是 **`drafts/` 里那一份**——改动稿在 `drafts/` 期间不覆盖
`docs/` 那一份，`docs/` 里任何时刻都是已过审的版本。
（顶层设计 D11，见 `review/specs/2026-11-18-顶层设计与目录调整.md`。）

## `docs/` 里放什么

`docs/` 是**已过审母稿**的唯一落点：稿子先落 `drafts/`，过完审才复制进来。
所以 `docs/` 里任何时刻都是「已过审的版本」——**没有「未过审」这个状态**。

- 目录即接口：`docs/<分类>/<二级内容>/<篇>.md`，一级目录 = 一个分类，
  二级目录 = 一块二级内容，一篇文档 = 一期。规程见
  [`specs/2026-11-18-目录即接口与分类增设.md`](specs/2026-11-18-目录即接口与分类增设.md)。
- **草稿层与母稿层之间的接口**（什么能过去、带走什么、两边该是什么关系）见
  [`specs/2026-11-18-草稿层与母稿层的接口协议.md`](specs/2026-11-18-草稿层与母稿层的接口协议.md)。
- **分类页也是母稿**：它列的文章必须都已过审，否则站内链接就是死链。
  分类页与它列的文章要**一起过审**。
- 2026-11-18 起 `docs/` 里**只有过审的内容**。此前那 560 篇母稿与 57 个分类页
  没有走过「`drafts/` → `review/` → `docs/`」这条流程，整体撤出；
  原件曾镜像在 `drafts/` 的六条线下（逐字节一致），那批镜像已随内容清空删除，git 历史里也留着。
  往后的每一篇都走同一条路：**在 `drafts/` 里改 → 过 `review/` → 复制进 `docs/`**。

目标不是把文章改得更华丽，而是让它读起来更像一位有经验的工程师在清楚地说明问题：
具体、自然、有判断，也保留原文的技术准确性和个人风格。审校还应当让每篇文章
有足够的技术密度、可验证性与辨识度，逐步形成 growdu 的个人专业品牌。

## 审校原则

1. **先保真，再润色。** 不改变技术结论、数据、引用、命令、链接或作者立场；拿不准的事实标为待核实，不靠改写补全。
2. **按读者的阅读路径组织。** 先说明问题、背景和结论，再展开原理、步骤与边界；删掉读者无需知道的铺垫。
3. **让抽象话落地。** 优先用具体对象、条件、行为和结果，少用空泛评价。
4. **保留人的声音。** 保留有价值的经验、犹豫、取舍和失败案例；不把文章统一改成模板腔。
5. **小步可审。** 每次只处理一篇或一个明确章节，建议应能逐条确认和回滚。
6. **用证据建立技术感。** 技术感来自源码、实验、日志、指标、版本差异和取舍，
   不来自堆术语或把简单问题说复杂。
7. **写出自己的工程判断。** 除了“是什么”，尽量说明“为什么这么做、别的方案为什么
   不选、什么条件下结论会失效”。

## 技术深度检查

一篇技术文章不必面面俱到，但应至少具备下列要素中的两到三项：

- **问题边界**：版本、系统规模、前置条件、本文不讨论什么。
- **机制解释**：从调用链、数据流、状态变化或关键数据结构解释“为什么”。
- **可复现证据**：SQL、命令、最小示例、日志、压测方法或源码定位。
- **工程取舍**：方案的成本、风险、性能影响与适用场景，而不只给唯一“最佳实践”。
- **踩坑与校验**：常见误解、失败路径、如何观察和验证结果。

审校时优先补“读者因此能做什么”，而不是扩写背景。例如，把“需要注意并发问题”
改成并发在哪个临界点发生、怎样复现、观测什么指标、该选什么规避方案。

## growdu 个人 IP 的内容策略

growdu 的差异化不应是泛泛的“技术博主”，而是围绕数据库内核、分布式系统、
高性能网络与长期工程实践，提供能落到机制和现场的中文技术解释。

每篇文章可视情况完成以下四件事：

1. **一句话定位。** 开头讲清楚文章替读者解决什么难题，以及为什么值得现在读。
2. **一个可记住的判断。** 用清晰、可证伪的观点串起全文；避免为了吸引注意而夸大。
3. **一份可带走的产物。** 结尾给出排查清单、决策表、实验命令、源码入口或延伸阅读。
4. **一条自然的内容路径。** 链向上一篇基础文章、相关实战或系列目录，让读者知道下一步看什么。

适合长期沉淀的内容支柱：

| 支柱 | 读者获得 | 推荐表达 |
| --- | --- | --- |
| 数据库内核与 PostgreSQL/openGauss | 从表象走到事务、WAL、执行器与复制机制 | 源码导读、机制图、实验复现 |
| 分布式一致性与存储 | 理解多数派、状态机、故障恢复与工程边界 | 反例、时序、决策取舍 |
| 高性能网络与系统工程 | 把 DPDK/VPP、Linux 和性能调优接到真实工作负载 | 指标、火焰图、排障记录 |
| 工程成长与工具实践 | 将复杂技术转成可执行的学习和交付方法 | 路线图、模板、复盘 |

“营销”在这里指帮助对的人发现、理解并持续信任内容：标题和摘要应准确承诺收获，
开头尽快进入问题，系列文章互相连接，案例与实验支撑可信度。不得使用标题党、
伪造案例、制造焦虑或把尚未验证的观点包装成结论。

## 常见“AI 味”信号

- 用“首先、其次、最后”“值得注意的是”“总而言之”等连接词堆砌结构。
- 反复强调“高效、全面、显著、至关重要”等结论，却没有条件或证据。
- 一段塞进多个结论，没有示例、因果关系或适用边界。
- 为凑完整而重复前文，或用泛泛的总结收尾。
- 把不确定的推断写成确定事实，或把工具、版本和场景抹平。
- **拿自造术语和对仗式命名当行话**（见下一节）。

对应的修改方法通常是：删去重复句；补上“谁、在什么条件下、做了什么、结果如何”；把大段概述拆为短段；用原文已有的代码、日志或案例支撑判断。

## 术语纪律：不造词

> 权威判据：[`specs/2026-11-24-术语纪律与反造词.md`](specs/2026-11-24-术语纪律与反造词.md)。

**一条规则**：要么用本领域**有公认定义**的术语，要么用**通用描述**——不造词。

读者是同行，不是作者肚里的蛔虫。一个没有公认定义的词，读者得先猜「作者说的管线
是什么意思」，再去看内容。“心智模型”“管线”“抓手”这类词就是这种：听起来专业，
实则没有定义，只能靠上下文硬猜。

判据落成三问，审稿时照着问：

1. **这个词有公认定义吗？** 有 → 用它，并在首次出现时给一句话定义（或英文原词）。
2. **没有公认定义？** → 换成通用描述：「一条处理流程」「理解这件事的方法」
   「具体做法」——把作者脑子里的那层包装拆掉。
3. **拿不准？** → 写具体的对象、步骤、条件。别用词替代解释。

### 硬禁词（TERM-01，warn）

> 下面两张表与第三张命名黑名单的**唯一一份**在
> [`rules/terminology.json`](../rules/terminology.json)——
> 读取器是 [`tools/terminology_rules.py`](../tools/terminology_rules.py)。
> 改词表改那份文件，别改代码。

这些词在本领域**没有公认定义**，一律换成右列的说法：

| 词 | 换成 |
| --- | --- |
| 管线 | 流程（说清是什么在流转：「发布流程」「处理流程」） |
| 心智模型 | 方法论 / 技术原理 / 理解这件事的方式 |
| 抓手 | 具体做法 / 关键步骤 / 着力点 |
| 拉齐 | 统一 / 同步（说清谁跟谁） |

### 建议具体化（TERM-02，info）

不是硬禁，但换个说法更好：

| 词 | 换成 |
| --- | --- |
| 沉淀 | 积累 / 整理成 / 总结成（说清留下了什么） |
| 底座 | 基础设施 / 底层能力 / 公共库（说清它是什么） |

### 命名也要说人话（TERM-03，warn + 人工判断）

目录名、阶段名、标题同理：**这一段回答什么问题，就叫什么**。

两个抽象名词拼起来的对仗短语（「起步与全景」「实战与故障现场」）看着像标题，
读完不知道里面有什么——判据是**名字里能不能看出内容**。合格的样子：

- 「架构总览」——说得清这一段讲什么；
- 「存储引擎：页、文件与内存」——点得出具体对象；
- 「事务、MVCC 与并发」——列得出三样东西。

**例外**：引用外部材料时保留原名（论文标题、产品名里的 “mental model”），
但第一次出现要跟一句中文说明它在这儿指什么。

### 机械检查

`tools/review-check.py` 给出三条信号：**TERM-01**（硬禁词，warn）、
**TERM-02**（行话，info）、**TERM-03**（已被否掉的命名，warn）。
词表来自共享规则文件 [`rules/terminology.json`](../rules/terminology.json)。
判据是文档，检查器只是把能算的部分固定下来——「什么算公认术语」仍然是人判断。

适用范围：**对外内容**（`docs/`、`drafts/`）。
仓库内部的 specs / plans / 代码注释说的是工程语言（「渲染管线」在那里是准确的技术描述），
不按这条判据改。

## 标题：层级、顺序与信息量

> 权威判据：[`specs/2026-11-24-标题与章节顺序.md`](specs/2026-11-24-标题与章节顺序.md)。

标题是读者唯一的导航。读者读文章时先扫目录：这一节讲什么、为什么排在这儿、
标题说的那件事正文里有没有。**标题对不上正文，读者只能自己猜。**

四条人工要求：

1. **层级要断得住。** 一篇一个 H1（文章标题）；H2 是并列的大块，
   H3 是 H2 下面的小块。不跳级（H2 直接到 H4）、不多 H1。
2. **顺序跟读者的疑问顺序一致。**
   问题/背景 → 原理/机制 → 实现/实践 → 验证 → 扩展 → 总结与产物。
   收束类标题（「总结」「小结」「结语」）只能出现在最后——
   它后面还有章节，就是顺序乱了。
3. **标题要概括这一节。** 读完一节，标题能不能一句话说出它讲了什么？
   **标题里出现的术语，这一节正文里得出现**——别用 A 的词说 B 的事
   （标题写「宕机」、正文写「服务器挂了」也要统一）。
4. **标题要精简紧凑。** 一个标题不超过 **24 字**；不并列太多样东西；
   不用营销词（干货、揭秘、一文读懂、保姆级……）与懒词（深入、详解、初探……）——
   懒词不算错，但标题得另有「讲什么」的那一半。

> **标题不是标题党。** 标题承诺的东西，正文得兑现；
> 反过来，正文里的关键结论，标题别替它先说破。

### 机械检查

| 信号 | 级别 | 查什么 |
| --- | --- | --- |
| `HEAD-01` | warn | 层级断了：多个 H1、H1 不在最前、H2 跳到 H4 |
| `HEAD-02` | warn | 标题超过 24 字，目录里扫不完 |
| `HEAD-03` | warn / info | 标题带营销词（warn）或懒词（info） |
| `HEAD-04` | warn | 顺序不对：收束标题在中间、阶段词次序颠倒 |
| `HEAD-05` | warn | 空节：标题下面没有内容 |
| `HEAD-06` | info | 标题里的术语，这一节正文里没出现 |

标题里的营销词与懒词在共享规则文件 [`rules/terminology.json`](../rules/terminology.json)
的 `title_words` / `title_words_soft` 两张表里。

**标题能不能概括这一节**，整体上要人判断——机器只能查机械的那几件。
`README.md` 是模块说明不是稿子，标题规则不管它。

## 可读性、布局与图表

前面几节管的是「说得对不对、说得实不实」。这一节管的是「读者读不读得下去」。
它以人读为主——检查器只能标出最机械的几处（图太大、引用离图太远），
其余的靠人判断。

### 四条人工要求

1. **有趣。** 开头给一个具体场景或一个反直觉的结论，让读者有理由往下读；
   中途给一次「原来是这样」的转折；结尾留一个能自己动手验证的入口。
   「有趣」不是加段子、不是用感叹号，而是**读者被承诺的回报被兑现了**。
   从头到尾只有正确结论、没有意外也没有细节的文章，是准确，但不好读。
2. **布局合理。** 信息的顺序要跟读者的疑问顺序一致：先问题，再边界，
   再机制，再证据，最后是取舍与产物。同一层级的内容放在同一层级，
   并列的两件事不要分居两节。目录能看出骨架；读者翻到任何一节都知道自己到了哪一步。
3. **可读。** 句子短，术语先解释后使用，缩写第一次出现给全称，
   一段只讲一件事，关键结论不要埋在长段落中间。
   读者中途不需要回读上一段才能接上下一段。
4. **简洁。** 删掉重复的、删掉正确但无用的常识、删掉「为了显得完整」而写的话。
   简洁不是短，是**没有一句是多余的**。删到删不动为止。

### 图表：太长就该拆

流程图和架构图最容易失控：加一个分支不用改文字，图就多一层；
作者顺着源码想的时候记得住十步，读者看图时记不住。

判据（机械可判，检查器实跑；阈值与 `tools/review-check.py` 的常量一一对应，
改一处必须改另一处）：

| 规则 | 指标 | 阈值 | 为什么是这个数 |
| --- | --- | --- | --- |
| `FIG-01` | 一张图里的框数 | 超过 15 个 | 到这个量级读者已经没法一眼扫到全貌，只能在框里找关系 |
| `FIG-01` | 顺着一路走的步数 | 超过 8 步 | 再长就要往回翻才能接上前后，起点和终点对不上 |
| `FIG-01` | 一个框分出的支线 | 超过 6 条 | 布局已经散了，视线要在同一个点上来回跳 |
| `FIG-01` | mindmap 的内容行数 | 超过 20 行 | 摊开这么长，已经不是导图是目录 |
| `FIG-02` | 「下图 / 上图」离图的距离 | 超过 10 行 | 读者会以为漏看了什么，图要紧跟在引用它的那一段后面 |

超限**不等于画错了**，而是说这张图该拆：按「一段一件事」拆成几张，
每张配一句话说明它在讲什么。拆的时候沿**语义边界**切（哪一步之后状态变了），
不要按框数均分——均分出来的两张图，仍然各自说不清一件事。

位图（PNG/JPEG）暂不做机械判定：图片的尺寸、比例、分辨率要人看。

## 每篇文章的审校流程

1. 确认原文路径、目标读者与本轮范围。
2. 先列出问题：表达不自然、结构跳跃、信息重复、论断缺乏边界、术语不一致，
   以及缺少机制、证据、取舍或可执行产物的位置。
3. 给出可直接采用的逐段建议，必要时提供改写前后对照；技术补充必须注明需要的依据。
4. 检查定位：标题、开头、核心判断、结尾产物和系列链接是否形成一致的读者路径。
5. 检查可读性：布局是否跟读者的疑问顺序一致，图表是不是太长该拆，
   段落是不是各自讲一件事，有没有删得掉的话。
6. 复核：技术事实、命令、链接、标题层级和作者原意均未被误改。
7. 跑一遍机械检查（下面一节），把信号跟人工判断对齐。
8. 在本目录留下简短记录；只有确认后的正文修改才进入 `docs/`。

### 合入那一步的提交标题

**改稿合入 `docs/` 的那一次提交，标题要一字不差地写成
`docs(review): <记录文件名>`**——记录文件名就是那个 `.md` 的名字，
不含后缀。例：记录叫 `postgresql基操.md`，提交标题就是
`docs(review): postgresql基操`。

**为什么这么严**：机器要核对「这条记录说合入了，那次提交是不是真的
改了这篇文章」。它只认这一个标题——认标题比认正文里的某个标记稳，
标记会被人改，标题是提交的一部分。要核对的路径还可能是**中文**，
而 `git show --name-only` 默认把非 ASCII 路径转义成八进制
（`"docs/.../\\350\\276\\205..."`），所以机器那一步必须带 `-z` 取原始字节
（`tests/test_review_records.py` 盯着这条）。

标题写错的后果不是「难看」，是**机器看不到那次提交**：它会以为这条记录
从没合入过，`tests/test_review_records.py` 那边就会报「没有已合入的记录」。

## 机械检查与人工审校的关系

`tools/review-check.py` 把上面这些规则里**可计算**的部分固定下来，输出一组带编号的信号
（STR / DEP / MET / AIF / FIG / TERM）。它**不下结论**，只标出「值得看一眼的地方」。

**过审 = 人工审过 + 机械检查无信号。** 两个都要。

信号不是门禁（脚本总是返回 0）：一篇老文章的历史问题不该永久卡住流水线。
但**新稿要过**——一篇刚过完人工审的稿子还带着信号，说明判据和稿子没对齐，
那就改稿子或改判据，不能就这么进 `docs/`。

判据在规则文件那一层，稿子服从判据。例子：某篇开头写了「这篇解决什么」、
结尾写了「收尾：三件最容易搞错的事」，人工审认为都到位，但检查器只认
`POSITIONING_RE`（`本文…解决`）和 `TAKEAWAY_WORDS`（含「小结」「清单」…），
于是报了 STR-02 与 STR-03。解法是把标题改成判据认的说法，不是去改判据。

### 稿子和索引页适用不同的规则

索引页（`_index.md`）是一张清单。检查器按**文件名**分流：

- 稿子（其余 `.md`）：全套规则。
- 索引页（`_index.md`）：只查链接、拼写、H1、图示；**不查**编写人信息表、
  二级章节数、技术深度五要素、AI 味信号——那些是稿子的判据，套到清单上全是噪声。
- **术语纪律（TERM）两边都查**：阶段名、目录名恰恰落在索引页上。

这个分流同样由**目录层级**承担：层级说了它是什么，检查器照着办。

### 怎么跑

```bash
python3 tools/review-check.py docs/source-tracks/postgresql/getting-started/postgresql基操.md
python3 tools/review-check.py drafts/                             # 草稿箱（目录即接口，按需新建）
python3 tools/review-check.py docs --json --out /tmp/rc.json        # 机器可读
```

只读：不修改被检文件，也不往仓库里写东西。

## 审校记录模板

新建记录时，建议以文章 slug 命名，路径与稿子**镜像**（见《草稿层与母稿层的接口协议》§七）。

记录的 **front matter 是机器可读的那一半**：

```md
---
status: 建议中
src: 相对 drafts/ 的路径
---

# 审校：文章标题

- 原文：drafts/…/文章.md（新增稿或改动稿）
- 范围：全文 / 第 N 节
- 目标读者：
- 一句话定位：
- 核心判断：

## 优先修改

1. 位置：
   - 问题（类别）：
   - 建议：
   - 原因：

## 事实待核

- 

## 可补的技术证据或产物

- 机制 / 源码入口：
- 实验或观测：
- 工程取舍：
- 结尾清单或下一篇链接：

## 已确认的改动

- 
```

## front matter 里那两个字段

| 字段 | 取值 | 谁用 |
| --- | --- | --- |
| `status` | `建议中` / `已确认` / `已合入` | 守卫 G-01：`docs/` 里每一篇都要有一份 `status: 已合入` 的记录 |
| `src` | 相对 `drafts/` 的路径 | 记录自己是从哪一篇来的 |

`src` 之所以要写，是因为**层级表达不了它**：记录的路径是 `review/<镜像路径>`，
而 bundle 形态的稿子（`<名>/index.md`）的记录是 `<名>.md`——少了 `/index.md`，
从记录路径反推不出源路径。扁平稿与索引页能反推，但统一写上省掉分支。

正文里原来那行 `- 审校状态：…` 不再重复写——它在 front matter 里，
两处写会漂。

### 「问题（类别）」怎么写

「优先修改」每条建议的**问题**一行以类别开头，写成 `- 问题（类别）：一句话描述`。
类别固定这五个——写不出来的，多半是问题还没想清楚：

| 类别 | 指的是 |
| --- | --- |
| 结构 | 章节顺序、层级、该拆该合 |
| 表达 | 句子、术语、语气、AI 味 |
| 事实 | 数据、版本、引用、链接 |
| 图表 | 图太长该拆、图与正文对不上、引用离图太远 |
| 可读性 | 趣味性、布局、可读、简洁 |

「可读性」这一类由人判断，检查器帮不上忙：它能标出「这张图有 18 个框」，
但说不出「这篇读起来闷」。

### 「事实待核」怎么写

每条待核事实用三种标记之一，机器从这三行解析：

| 标记 | 含义 | 阻塞「已合入」 |
| --- | --- | --- |
| `- [x] 事实` | 已核实，依据写在条目里 | 否 |
| `- [不适用] 事实` | 该事实涉及的正文本次没改，原文保留 | 否 |
| `- 事实` | 还没销掉 | **是** |

「已合入」的语义是：**与本次改动相关的**待核事实都销掉了，不是全篇事实都核实过。
所以标「不适用」是合法的——核不完、而本次又没碰它，就不该卡住合并。
（进度表里这两类分开记：「待确认」是没销掉的，「不阻塞」是标了「不适用」的。）

## 边界

- `review/` 只记录审校过程和建议，不是对外发布内容。
- 涉及事实、数据、版本、引用或外链的修改，必须可回溯到原始依据。
- 不为“去 AI 味”而删除必要的定义、前提、警告或操作步骤。
