## Task 1: B1 — 站内搜索 100% 失效

**根因**（已在 node 里复现）：MiniSearch 的 `saveStoredFields` 走的也是
`extractField`，所以 `categories` / `tags` 存下来是**字符串**而不是数组；
`search.ejs` 渲染时按数组调 `.join(' · ')` → `TypeError: c.join is not a function`。
`search.ejs:144` 那句 `r.categories && r.categories.length` 守卫挡不住——
字符串也有 length。

**改哪**：`themes/matery/layout/_partial/search.ejs`

**测试**：`tests/test_search_result_fields.py`（新）
用 node 跑一段脚本，脚本做三件事：
1. 加载主题自带的 `minisearch.min.js`，用 `search.ejs` 里那套 `extractField`
   建索引，存一条带 `categories: ['AI']` 的文档；
2. 取出 MiniSearch 存下来的 `categories`（**字符串**）；
3. 把 `search.ejs` 里渲染用的那段表达式抽出来，用这个字符串跑一遍。

断言：不抛异常，且渲染结果是 `'AI'`。
再喂数组、`undefined`、`null` 各一遍，都不许抛。

**实现**：在 `search.ejs` 里加一个归一化函数，渲染前把值统一成数组。

**验证**：
- `python3 -m pytest tests/test_search_result_fields.py -q`
- `python3 -m pytest tests/ -q`

**提交**：`fix(site): 站内搜索崩了——MiniSearch 存下来的字段是字符串，不是数组`

## Task 2: B2 — 57 个空白 `/page/N/`

**根因**：首页是单页设计——`themes/matery/layout/_partial/home-content.ejs`
只在 `page.current === 1` 渲染内容。但 `_config.yml` 的 `index_generator.per_page`
还是 10，hexo-generator-index 照样按 10 篇一页切，于是生成了
`/page/2/` … `/page/57/` 共 57 个零内容页（每个 84219 字节，一模一样）。

**改哪**：`_config.yml` 的 `index_generator.per_page` → `0`。

`hexo-pagination` 在 `perPage` 为 0 时只产出一页（`total = 1`，
`posts` 是全部），首页渲染的是 `site.posts`，所以**首页内容一个字都不变**。

**测试**：`tests/test_home_pagination.py`（新）
1. 断言 `_config.yml` 的 `index_generator.per_page == 0`；
2. 断言 `home-content.ejs` 里的 `page.current === 1` 判断还在
   （单页设计的前提，改分页前必须先确认它没被拆掉）；
3. 断言站点里没有任何地方链到 `/page/`（主题模板 + patch-theme 注入的 CSS/JS）。

**验证**：
- `python3 -m pytest tests/test_home_pagination.py -q`
- `python3 -m pytest tests/ -q`

**提交**：`fix(site): 首页不分页——57 个空白 /page/N/ 是纯粹的零内容页`

## Task 3: B3 — 404 页「最近发布」6 条死链

**根因**：`tools/sync-hexo.py` 生成 `source/recent-posts.json` 时拼的 URL 是
`/{cat}/{slug}/`，而站点真实的 permalink 是 `/:year/:month/:day/:title/`
（`_config.yml` 的 `permalink` + `permalink_defaults`）。
形态不匹配 → 404 页上那 6 条链接**每一条都是死的**。

**改哪**：`tools/sync-hexo.py` 生成 `recent-posts.json` 的那段。
用现成的 `site_root.permalink(date, post_path)`——它已经处理了挂载点前缀
（镜像站挂在 `/blog/` 下）和 URL 编码。

**测试**：`publish/tests/test_sync_recent_posts.py`（新）
1. 用 `test_sync_exclusions.py` 那套「小语料 + 真的跑一遍 sync」的办法，
   造一篇带 `date` 的文章，跑 sync，断言 `source/recent-posts.json` 里
   的 url 形如 `/YYYY/MM/DD/<cat>/<slug>/`；
2. 断言 url 带站点根前缀（`site_root.permalink` 的既有约定）；
3. 断言拼出来的 url 与 sync 生成的**文章 permalink 一致**
   （拿 `source/_posts` 里那篇的目录结构对一遍）。

**验证**：
- `python3 -m pytest publish/tests/test_sync_recent_posts.py -q`
- `python3 -m pytest publish/tests -q`

**提交**：`fix(site): 404 页的「最近发布」链接补上日期段——现在每一条都是死的`

## Task 4: B4 — 404 页的搜索指向不存在的 `/search.xml`

**根因**：404 页的搜索框 `fetch('/search.xml')`，但站点里根本没有 `search.xml`
（hexo-generator-searchdb 出的是 `search.json`）→ 永远走 catch 分支跳
Google site: 搜索，国内不可用。等于 404 页没有搜索。

**改哪**：`tools/sync-hexo.py` 里 404 页那段 HTML。

**决定（与方案原文有出入，记一笔）**：方案写的是「`search.xml` → `search.json`」。
直接换过去的话，404 页要下载 **13.5 MB** 的 `search.json` 才能搜一个词——
把「搜索等于没有」换成「搜索慢到等于没有」。所以另出一个精简索引
`source/search-lite.json`（每篇只有 title / url / cat，约 60 KB），
404 页用它做标题匹配，命中不了再退回 Google。

代价：404 页的搜索只匹配**标题和分类**，不搜正文。站内完整搜索仍在首页。

**测试**：`publish/tests/test_sync_404_search.py`（新）
1. 跑一遍 sync，断言 `source/search-lite.json` 存在，每条记录有
   `title` / `url` / `cat` 三个字段；
2. 断言 404 页 HTML 里 fetch 的是 `/search-lite.json`，**不再**出现
   `search.xml`；
3. 断言 404 页 HTML 里没有任何 `/page/N/` 形态的死链。

**验证**：
- `python3 -m pytest publish/tests/test_sync_404_search.py -q`
- `python3 -m pytest publish/tests -q`

**提交**：`fix(site): 404 页的搜索改用精简索引——原来指向一个不存在的 /search.xml`

## Task 5: B5 — 元数据表污染摘要

**根因**：85 篇文章正文顶上有一张编辑履历表：

```
| 编写人 | 编写内容 | 编写时间 |
| --- | --- | --- |
| growdu | 修订：理顺结构与定位，…… | 2026-11-14 |
```

这张表被当成正文抓走，污染了三处：`<meta name="description">`、
首页卡片摘要、RSS 的 `<summary>`。实测 98 个页面的 meta description
是表格残骸。

**改哪**：`tools/sync-hexo.py` 的 `process()`。
1. 认出这张表（表头含 `编写人` + `编写内容`），把「编写内容」列取出来
   （去掉 `初稿，` / `修订：` 这种履历前缀），截到 150 字
   （契约上限），写进生成文章的 front matter `description`；
2. 把这张表从正文里剥掉——它不进正文，摘要自然干净；
3. 源 front matter 里已经有 `description` 的，以源为准，不覆盖。

**测试**：`publish/tests/test_sync_description.py`（新）
1. 单元：对**真实的** `docs/` 树里每一张履历表，跑一遍新的提取函数，
   断言都拿到一段非空 description，且没有一张表残留在正文里；
2. 集成：跑一遍 sync，断言生成的文章 front matter 里有 `description`，
   正文里没有 `| 编写人 |`；
3. 断言 `description` 不超过 150 字（契约上限）。

**验证**：
- `python3 -m pytest publish/tests/test_sync_description.py -q`
- `python3 -m pytest publish/tests -q`
- `python3 -m pytest tests/ -q`

**提交**：`fix(site): 85 篇文章的编辑履历表不再污染摘要——拆成 description，剥出正文`

**留给阶段 1 的三件事**（评审里的 Minor，刻意没在阶段 0 做）：

1. **URL 编码两套写法**：`tools/site_root.py` 的 `permalink()` 用 Python 的
   `quote()`，hexo 用 `encodeURI`——527 条里有 3 条的 URL 与站点自己的
   canonical 写法不一致（都能打开）。统一 URL 生成时一并处理。
2. **SEO 描述与卡片摘要还没用上高质量 description**：
   `themes/matery/layout/_partial/head.ejs` 与 `post-card.ejs` 读的是
   `page.summary || strip_html(page.content)`，不读 `page.description`。
   阶段 0 写下的 83 条摘要目前只进了 og / twitter / RSS。
3. **履历表不认围栏代码块**：`extract_edit_history` 会把代码块里当样例展示的
   履历表也剥掉。当前语料 0 例，等语料里出现再修。
4. **`<meta name="description">` 会把 HTML 实体转义两次**（阶段 0 之后的构建里
   发现，7 个页面）：hexo 的 `strip_html()` 只去标签、不还原实体，于是正文里的
   `&quot;` 进了 description，`<%= %>` 又把 `&` 转义一次 → 页面里是
   `&amp;quot;`，爬虫读到的是 `&quot;`。受影响的是正文以代码块开头的文章
   （`shell脚本进阶` 等）。og / twitter 那两行已经在阶段 0 修掉了，
   `<meta name="description">` 这行还没有。
