## Task 2: 首屏搜索框用 78KB 的精简索引，不拖全文索引

### 现状

- 导航栏的搜索弹窗（`_partial/search.ejs`）在首次输入时 fetch `search.json`，
  实测 **13,490,267 字节**，线上 gzip 后 **4,202,343 字节 / 0.45s**。
- 首屏搜索框如果复用它，**第一次击键**就要下 4.2MB。
- 阶段 0 已经造好 `source/search-lite.json`（约 78KB，字段 title / url / cat），
  404 页正在用它做标题级匹配。

### 改哪

`home-hero.ejs` 里加一个独立的搜索框：

- 数据源：`/search-lite.json`（**零新增字节依赖**，阶段 0 已生成）；
- 匹配：标题子串 + 分类名，**大小写不敏感**；输入防抖 200ms；
- 渲染：最多 8 条（标题 + 分类），回车跳第一条；
- 一行提示：「按标题搜索 · 全文搜索用顶部导航」。

**不做**的事：不把全文搜索搬进首屏（4.2MB 首次击键的代价不值得），
也不改 `search.json` 的内容（瘦身留到阶段 5 的性能项）。

### 测试（新）

`tests/test_home_search_box.py`

1. `test_the_hero_search_box_has_a_stable_id` —— `id="homeSearch"`。
2. `test_the_hero_search_uses_the_lite_index` —— 抓的是 `/search-lite.json`，
   **不是** `/search.json`（这条是防回归的关键：改回全文索引会直接让测试红）。
3. `test_the_hero_search_renders_title_and_category` —— 渲染函数里有 title 与 cat。
4. `test_the_lite_index_has_the_fields_the_search_needs`
   —— `search-lite.json` 每条有 title / url / cat。

### 验证

## Task 4: 卡片摘要与 TL;DR 框改读 description

### 现状（线上实测）

- `post-card.ejs`：`post.summary || strip_html(post.content).substring(0,80)`。
- **568 篇里只有 1 篇有 `<!-- more -->`** → `post.summary` 基本是空 →
  摘要 = 正文前 80 字。线上 18 张卡片里 3 张以「TL;DR」开头，
  另有几张是表格残骸、「[TOC]」、视频口播稿抬头。
- `post-tldr.ejs`：`page.tldr || page.summary` → 同样基本为空 → TL;DR 框基本不出现。
- **阶段 0 已经把 85 条 description 写进了 front matter**，但
  `post.summary` 不会读 front matter 的 `description` → **那 85 条至今没在卡片上露过面**。

### 改哪

- `post-card.ejs`：`post.summary || post.description || strip_html(...)`
- `post-tldr.ejs`：`page.tldr || page.description || page.summary`

**这里要反转阶段 0 的一个决定。** 阶段 0 明确写了「description 只喂 og / twitter，
不喂 TL;DR 框，不喂卡片摘要」——**理由是那时候 description 是履历句**

## Task 5: 85 条履历句换成真摘要（顺带补齐没有摘要的 483 篇）

## Task 6: 把真实阅读统计用起来，并删掉假的「🔥」

### 现状（实测）

**三套东西，其中两套是真的，一套是假的。**

| 来源 | 状态 | 实测 |
| --- | --- | --- |
| **GoatCounter** | ✅ 真实、在收 | `_config.matery.yml` 里 `goatcounter.code: 'growdu'`；线上每页都加载 `//gc.zgo.at/count.js`。`growdu.goatcounter.com/count` 返回 200 + GIF，而一个不存在的 code 返回 400 → **站点确实存在、确实在采集**。但是 private（首页跳 `/user/new`） |
| **不蒜子** | ✅ 真实、能显示 | 脚本每页加载；文章页有 `busuanzi_value_page_pv`（per-page PV）；`site_pv ≈ 3744` / `site_uv ≈ 1670`。**只有一个按 Referer 判路径的端点** `/busuanzi`，**每次请求会给该路径 +1**（返回值含自己那一次），实测约 30–50% 的请求返回 502 |
| **侧栏「最热文章」的 🔥 数字** | ❌ **假的** | `patch-theme.py`：`Math.max(5, Math.floor(字数 / 50))`。线上那篇 PG 逻辑复制显示「🔥 **2152**」——**它是字数除以 50** |

另外：「近期热门」tab 用的是手写的 `top` 分数（568 篇里只有 19 篇有 `top`），
与真实热度无关。

### 改哪

1. **删掉假数字**（先做，这个最要命）：
   `patch-theme.py` 里 hot-views 的计算改成**真实 PV**；拿不到真实值时，
   **宁可这一格不显示**，也不显示一个假的🔥。
2. **真的热门**：新建 `tools/fetch-view-counts.py`，
   用 **GoatCounter 的 API** 读每页 PV → 写快照 `data/view-counts.json`（进 git）。
   - **为什么是 GoatCounter 而不是不蒜子**：GoatCounter 的 API 是**只读**的，

   - 需要作者提供 GoatCounter 的 API key → 放 CI secret `GOATCOUNTER_API_KEY`。
