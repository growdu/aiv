# 展示审计与优化方向

**范围**：站点「长什么样」这一层 —— 有哪些页面、每页承担什么、页面之间怎么接、
读者从哪进来、往哪去。**不含**内容质量（文章写得好不好）、SEO 细节、
评论系统。基准是 `docs/blog/重构方案.md`（下称 spec）。

**方法**：不是读模板猜，是量产物。`public/` 里 801 个 HTML 全部量过一遍，
关键页面用 headless Chrome（CDP）量了真实几何与计算样式，
死链扫了全站外链。**本文里带数字的判断都是量出来的**，不是印象。

---

## 一句话结论

**内容够了，展示没跟上。** 577 篇文章、44 个分类条目、6 期视频，存货很足；
问题全在展示层：

1. **同一批信息在一页里说了 3～4 遍**（首页最明显）；
2. **页面之间没有「下一站」**——读完一篇，没有任何机制把读者送到
   「同主题的另外几篇」或「这一系列的下一步」；
3. **每页都要背 2.1 MB 的公共家具**（其中 770 KB 只为了评论区）；
4. **六个平级入口并列**（项目/分类/数据库/播客/标签/关于），
   读者没有判断依据，spec §6.1 设计的 6 项信息架构一次也没落地；
5. **109 张 mermaid 图（8.4%）渲染不出来**，页面上只留一行
   「⚠ 此图语法错误，未能渲染」——因为长这样，它们一直是隐形的（见第七节）。

## 一、站点是怎么搭起来的（展示逻辑）

### 1.1 流水线

```
docs/blog/**.md
   │  tools/sync-hexo.py            （front matter 不覆盖，只同步正文与元数据）
   ▼
source/_posts/**
   │  npx hexo generate              （Hexo 7.3.0 + matery 主题）
   ▼
public/**                            → GitHub Pages
```

CI（`.github/workflows/hexo.yml`，两个 job）比本地多跑 5 个生成器
（`build-video-pages` / `build-publish-index` / `build-podcast-index` /
`build-series-page` / `build-podcast-feed`）和 2 个产物检查
（`check-episode-block` / `check-home-tabs`）。
**本地漏跑其中任何一个，产物就跟线上不一致** —— 本次审计第一版就踩了这个坑
（漏 `build-podcast-index.py` → 首页少了「最新一期」区块、`/videos/` 变死链）。

主题配置有**两层**，容易搞错：

| 文件 | 是什么 |
| --- | --- |
| `themes/matery/_config.yml` | 主题**默认值**，被 `tools/patch-theme.py` 打补丁 |
| `_config.matery.yml` | 站点**真配置**，hexo 自动合并进 `ctx.config.theme_config` |

站点真实配置在后者。**别把前者拷成后者**（会把 `libs.css.*` 一起丢）。

### 1.2 骨架：只有一个 `layout.ejs`

每个页面 = `layout.ejs`（497 行）+ 一个 `layout/*.ejs`。
`layout.ejs` 无条件注入这些东西，**一页都不例外**：

| 注入物 | 量级 |
| --- | --- |
| 左侧「分类导航」固定侧栏 | 44 条分类链接 |
| 右侧「最多阅读」固定侧栏 | 20 篇文章 |
| 本地 JS + CSS | **≈ 2.19 MB**（文章页实测，含图片） |
| service worker 注册 | **两次**（layout.ejs:165 与 layout.ejs:318） |

也就是说：**每页的固定成本是 2.1 MB 资源 + 64 个链接**，
不管这一页是 8 KB 的 404 还是 394 KB 的分类页。

固定资源里最重的几项（文章页实测）：

| 资源 | 大小 | 备注 |
| --- | --- | --- |
| `gitalk.min.js` | **769.8 KB** | 评论区，每篇文章都加载 |
| `materialize.min.js` + `.css` | 327.7 KB | 框架 |
| `awesome/all.min.css` | 99.3 KB | 图标字体 |
| `jquery-3.6.0.min.js` | 87.4 KB | |
| `lightgallery-all.min.js` | 55.4 KB | |
| `aos.js` + `.css` | 37.5 KB | 滚动动画 |
| `instantpage.js` | 4.5 KB | |

### 1.3 导航（8 项）

```
首页  归档  项目  分类  数据库  播客  标签  关于
```

问题不是数量，是**层级**：8 项里只有「首页」「归档」是站点级入口，
剩下 6 项是 6 个平级的子目录，彼此没有上下级关系。读者面对的是
「六个并列的口子」，而不是「一条从大到小的路径」。

spec §6.1 要的是：

```
首页 / 知识地图 / 专题与系列 / 探索 / 实验室 / 关于
```

**一次都没落地。** 现在的 8 项是主题自带的默认导航，
加上后期补的「项目」「数据库」「播客」三个链接。

### 1.4 页面清单（801 个 HTML）

| 类型 | 数量 | 说明 |
| --- | --- | --- |
| 文章页 | 594 | |
| 归档页 | 93 | 年 8 个 + 月 85 个 |
| 标签页 | 57 | |
| 分类页 | 48 | 侧栏只列 44 条；多出的 4 个是空页；另有级联重复页 |
| 其他（首页/静态/404） | 7 | |

分类层的实测口径（`public/categories/`）：

- **48 个分类页**（不含 `/categories/` 索引页）；
- 侧栏只列 **44 条**，多出的 4 个（`hometown` / `stock` / `成长之路` / `随笔`）
  **既没内容、也不在侧栏** —— 是没人能发现的空页；
- 44 条里 **`数据库` 出现两次**（60 篇 / 96 篇），所以只有 **43 个不同的名字**；
- 标签层 **57 个**（不含索引），其中 **42 个分类名同时也是标签名**，
  纯技术词只有 8 个 —— 标签层几乎没提供分类之外的新信息。

### 2.1 首页 —— 同一件事说了四遍

当前结构：

```
首屏   定位句 → 站内搜索 → 9 个分类徽章 → 打字机 → 3 篇代表作
       ↓
统计条 4 张卡：577 篇 / 173w 字 / 2699 天 / 44 个分类
       ↓
最新一期（EP06）
       ↓
学习路径 6 条线：数据库内核 / 高性能网络 / 分布式系统 / AI / 操作系统 / 思维
       ↓
3 个 tab × 6 张卡：最新发布 / 编辑推荐 / 最多阅读
```

**四遍说的是同一批方向**：

| 出现位置 | 内容 |
| --- | --- |
| 9 个徽章 | PostgreSQL / openGauss / 分布式系统 / DPDK / VPP / 股票·金融 / 工具·视频·培训 / 哲学·人生 / 社会观察 |
| 打字机 9 句 | PostgreSQL·openGauss 内核 / Raft·DCF / 逻辑解码与 DDL / 性能调优 / eBPF·DPDK / 工具·视频·培训 / 股票与金融 / 哲学思辨·人生感悟 / 社会观察·城市记录 |
| 学习路径 6 条线 | 数据库内核 / 高性能网络 / 分布式系统 / … |
| tab 卡片分类标签 | 数据库深入 / 数据库 / … |

一页之内「PostgreSQL」出现 **80 次**。

而且 **9 个徽章是硬编码在模板里的**（`home-hero.ejs` 的 `heroBadges` 数组），
只有它们的**链接**是从 `site.categories` 反查的 —— 也就是说：
分类改个名，徽章的文字不会跟着变；分类删了，徽章会被 `console.warn` 跳过，
首屏就少一个格子。**徽章文案和分类体系是两套要手工同步的东西。**

统计条里两个数字也不可靠：

- 「总字数 173w」：手工累加 `wordcount()` 再解析 `Xk` 后缀
  （曾经出过一次 `NaNw`，代码里留了注释）；
- 「天持续更新 2699 天」：从 `theme.time` 起算到**构建当天** —— 每次构建都变，
  缓存命中与否数字不同。

tab「最多阅读」用 GoatCounter 的真实阅读量快照；快照缺失时降级成
「编辑精选」，但排序还是 `top`。现有代码有 guard
（`pv[0].pv > pv[1].pv` 才敢叫「最多阅读」），这一点是对的。

**「查看全部 577 篇」指向 `/archives/`** —— 一个 93 页的时间序页面。
想「看全部」的人点进去看到的是编年的目录，不是内容的目录。

### 2.2 归档页

- 168.9 KB HTML + **1.9 MB 资源**，其中 `echarts.min.js` **1 MB**，
  只为了在侧栏画一个「文章发布日历」热力图 —— 而且每个归档页（93 个）都带。
- 归档页是**时间序**。它承担了「查看全部 577 篇」的职责，
  但按主题找东西的人在这里找不到东西。

### 2.3 分类

- **3D 轮播**：分类页用 `.carousel-3d-container` 把全部文章做成轮播，
  `/categories/数据库深入/` 因此有 96 张卡、393.6 KB HTML。
  **同样的模式在 `/all/` 已经因为「577 张卡进不去」被删过一次**
  （commit `c347da1b`：「『查看全部 577 篇』不再把人丢进一个 1/577 的轮播」），
  分类页又用回来了 —— 只是卡片少一点。
- **级联重复**：Hexo 把 front matter 的分类列表当成层级链，
  于是 `/categories/数据库深入/` 和 `/categories/数据库深入/数据库/`
  列出**同一批 96 篇文章**。
- **4 个分类页是空的**：`成长之路` / `随笔` / `hometown` / `stock`（0 篇），
  而且它们**不在侧栏** —— 没人能点到的空页。
- **侧栏里「数据库」出现两次**（60 篇 / 96 篇），紧挨着「数据库深入」（96 篇）——
  三个框并排摆在一起，看到的人只会觉得站点自己也不知道内容怎么分。

### 2.4 标签

- 57 个标签页；**42 个分类名同时也是标签名**，纯技术词只有 8 个。
  也就是说**标签这一层几乎没有提供分类之外的新信息**，只是把分类复制了一遍。
- 标签页用的是普通列表（`.tag-post-list`），**比分类页的轮播好** ——
  同一个站点里两种并列视图用了两种完全不同的呈现方式。

### 2.5 文章页

- 每篇 **2.19 MB** 本地资源，其中 `gitalk.min.js` **769.8 KB** 为了评论区。
- **mermaid 是按需加载的**（页面里没有 `.mermaid` 元素就不加载）——
  这块做对了，是全站资源加载做得最好的一处。
- **「相关文章」= 同分类里最新的 6 篇**（`related-posts.ejs`）：
  取的是「共享任一分类」的全部文章，按日期倒序取前 6。
  对一个 96 篇的分类来说，这等于「同分类最新 6 篇」——
  标题写着「相关文章」，内容是「同分类最新」。**名不副实。**
- 难度星：`page.difficulty || 3` —— 没填的一律 3 颗。

### 2.6 搜索

**两套**：

| | 入口 | 索引 | 匹配 | 代价 |
| --- | --- | --- | --- | --- |
| 首屏搜索 | 首页 | `search-lite.json` **0.1 MB** | 只匹配标题 + 分类 | 一次 100 KB |
| 全文搜索 | 顶部导航 🔍 → modal | `search.json` **12.9 MB** | 全文（MiniSearch） | **第一次击键 gzip 后 4.2 MB** |

全文搜索在 **modal** 里：没有 URL，搜出来的结果**不能分享、不能后退**。

### 2.7 404

8 KB 的独立单页，自带深色模式，有搜索引导和热门文章链接。
**这是全站做得最好的一个页面** —— 其他页面都该向它学。

### 2.8 静态落地页（项目 / 数据库 / 关于）

三个都是 `post.ejs` 的全套家具：评论区（gitalk 770 KB）、相关文章、
分享按钮、上下篇导航。但它们是**落地页**，不是文章 ——
「关于」页面底下挂着「上一篇/下一篇」，没有意义。

### 2.9 视频系列页 `/videos/`

6 期，每期给出：**一句话 / 时长 / 完整版长文 / 口播稿 / 各平台链接**。

```markdown
## EP01 · PostgreSQL 18 并行逻辑解码
- 一句话：openGauss 把发布端拆成三层线程：reader 读 WAL，worker 池并行解码，walsender 收口输出
- 时长：32 秒
- 完整版（长文）：[PostgreSQL 逻辑复制全链路…](/2026/10/10/database/postgresql-logical-replication-end-to-end-flow/)
- [口播稿与字幕](/2026/11/09/video/pg-parallel-decode/)
- 平台：B站（未发布） · 视频号（未发布） · [抖音](…)
```

**这是全站信息结构做得最好的一个页面** —— 每个条目都回答了
「这是什么 / 要花多久 / 完整内容在哪 / 有没有字幕 / 在哪能看」。
而且它证明了一件事：**这个站完全有能力把一篇文章包装成一个「入口」**，
只是这个能力目前只用在了视频上。

### 2.10 移动端

- 移动导航在 logo 下面印的是 `config.description` ——
  **93 个字的 SEO 长句**，手机上占 3 行。
  这跟首屏那个 eyebrow 是同一个毛病（eyebrow 已经去掉，这一处还在）。
- 首页首屏搜索在移动端没有替代品（顶部导航的搜索图标在移动端折叠）。

## 三、整体衔接：读者动线在哪断了

现在的动线：

```
外部搜索 / 分享链接
        ↓
   落地页（某一篇文章）
        ↓
   顶部导航（8 个并列入口）
        ↓
   首页（同一批方向说了 4 遍）
        ↓
  「查看全部 577 篇」→ /archives/（时间序的 93 页）
```

**三处断点**：

### 断点 1：落地页 → 下一站，没有

文章页底部唯一的内部链接是「相关文章」，
而它其实是「同分类最新 6 篇」—— 对一个大分类来说信息量约等于零。
读完一篇，读者手上**没有任何一条通向「相关内容」的可靠路径**。

### 断点 2：首页 → 发现，是四选一而不是一选一

徽章、打字机、学习路径、tab 卡片，讲的是同一批方向。
读者不需要做任何判断，只要挑一个看着顺眼的点下去 ——
**而判断本身正是内容站该替读者做的事**。

### 断点 3：阅读 → 再发现，是单向的

读完 → 没有「同主题的另外 5 篇」，没有「这一系列的下一步」，
没有「这一期视频的下一期」。读和读之间是断开的。

### 另外三个「存在但没人用」的东西

| 页面 | 状态 |
| --- | --- |
| `/recommended/` | 145.7 KB，**全站 0 个入口**；两个 3D 轮播；「阅读全部」→ `/all/` → 302 → `/archives/` |
| `/all/` | 只为了重定向而存在的 73 行页面 |
| `/videos/` | 6 期，结构做得最好，但只有首页一小块导流；导航里叫「播客」，页面上叫「数据库内核机制」 |

## 四、优化方向

### P0 —— 这一轮就该做

**P0-1　首页的主题清单从 4 遍压到 1 遍。**
保留：9 个徽章（唯一带链接的）、学习路径（唯一讲「怎么学」的）、
卡片上的分类标签（元信息）。
删掉或改造：**打字机**（9 句硬编码文案，与徽章重复）。
顺带把**徽章的文案**改成从 `site.categories` 取（分类改个名，
首屏的字跟着变）；「挑哪 9 个」仍然是策展，保持手写清单。
首页从 4 段重复降到 3 段。

**P0-2　给文章页一个真正的「下一站」。**
把「相关文章 = 同分类最新 6 篇」换成两样东西：

- **同主题的另外 3 篇**（按关键词/标签重合度排，不是按日期）；
- **这一系列的上一篇 / 下一篇** —— `/videos/` 那套
  「一句话 + 完整版长文 + 口播稿」的结构就是现成的模板，
  文章系列完全可以照抄。

**P0-3　推荐页要么接进首页/导航，要么删。**
0 入口的 145.7 KB 页面是纯粹的体积。

**P0-4　清掉分类层的重复与空页。**
`/categories/数据库深入/数据库/`（与父页同 96 篇）、
`成长之路` / `随笔` / `hometown` / `stock` 四个 0 篇空页。

**P0-5　把 109 张坏图修掉（先让它们可见）。**
`tools/check-mermaid.py` 已经能一次量出全站所有渲不出来的图。
顺序：先接进 CI 当「报告」，再逐张修到 0，最后把 CI 改成「失败」。
（详见第七节。）

### P1 —— 下一轮

**P1-1　分类页别再用 3D 轮播。**
96 张卡的轮播 = 393.6 KB HTML，而且用户找不到东西。
`/all/` 已经因为同样的原因改掉了，分类页应该跟上：
普通网格 + 排序（时间 / 阅读量）。

**P1-2　归档页与分类页的职责分开。**
`/archives/` 只做时间轴：把 echarts 日历挪走或改成按需加载
（1 MB 换一张热力图不值），把「按主题找东西」交给 spec §6.5 的 `/explore/`。

**P1-3　gitalk 769.8 KB 按需加载。**
评论区折叠后再加载 —— 没人看评论的读者不该先付 770 KB。

**P1-4　两套搜索合并。**
首屏 lite 搜索 + 导航全文搜索可以共存，但全文搜索要有 URL
（`/search/?q=…`），能分享、能后退。

## 六、本轮顺手修掉的一个渲染 bug

审计首页几何时用 headless Chrome（CDP）量到了重叠，
根因不在布局，在**框架的一条全局规则**：

```css
/* materialize.min.css —— 按元素名选，不是按类 */
nav{color:#fff;background-color:#ee6e73;width:100%;height:56px;line-height:56px}
@media (min-width:601px){nav{height:64px;line-height:64px}}
```

**页面上任何一个 `<nav>` 都会被当成顶部那条 64px 的红导航条。**
而内容里有两个 `<nav>`：

| 位置 | 后果（实测） |
| --- | --- |
| `home-hero.ejs` 的「三篇代表作」 | 网格被压成 64px 高、行高 64px → 卡片涨到 261px → 溢出首屏盒子 84px → **统计条（文章数/总字数/天数/分类数）直接盖在代表作卡片上**，被盖住的正是分类为「数据库深入 / 数据库」的那几张 |
| `episode-block.ejs` 的「上一期/下一期/全部期号」 | 渲染成**一条红色横条、白字**，在文章正中间 |

修复：内容模板里不再用 `<nav>`（改成 `<section>` / `<div>`），
并加了一条契约测试 `tests/test_content_nav_not_materialize_navbar.py`
——以后谁在内容模板里写 `<nav>`，CI 会拦下来。

修复前后实测（首页，1400px 宽）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| `.home-hero__featured` 标签 | `<nav>` | `<section>` |
| 高度 | 64px（Materialize 写死的） | 168px（内容真实高度） |
| 背景色 | `rgb(238,110,115)`（红） | `rgba(0,0,0,0)`（透明） |
| 行高 | 64px | 22.5px |
| 首屏盒子 `scrollHeight` vs `clientHeight` | 695 vs 547（溢出 84px） | 651 vs 651（不溢出） |
| 代表作卡片底 vs 统计条顶 | 817 > 693 → **重叠** | 725 < 898 → 不重叠 |

文章页同一处也量了：`.episode-nav` 从「红色横条、64px 高」变成
「透明背景、33px 高的一行 flex 链接」（`my.css` 里本来就有这个样式，
一直是被 Materialize 抢了才没生效）。

## 七、顺带量到的第二个问题：110 张图渲染不出来（本轮修掉 1 张）

### 7.1 为什么一直没被发现

mermaid 解析失败时，`layout.ejs` 把它换成一行
**「⚠ 此图语法错误，未能渲染」**——从页面上看就是一块空提示框，
不点开源码根本不知道原来画的是什么。
于是「图坏了」这件事在站点上一直是隐形的。

### 7.2 量法与结果

把产物 `public/**/*.html` 里所有 `<div class="mermaid">` 的源码收集起来
（去重后 **1304 张**），在一个 headless Chrome 里逐张调用
**站点自己用的那个** `mermaid.render()`（不是 `parse`——`render`
才是真正画出 SVG 的那条路径）：

| | 数量 |
| --- | --- |
| 唯一 mermaid 图 | 1304 |
| 渲染成功 | 1194 |
| **渲染失败（读者看到的是提示框）** | **110（8.4%）** |

本轮修掉了其中 1 张（EP01 的首图，见 7.4），**还剩 109 张**。

抽样核对过：这些图在真实页面里确实是坏的
（例如 `08-locks-and-concurrency` 页 7 张图坏 1 张、
`12-physical-replication` 页 5 张图坏 1 张，
页面上 `.mermaid-broken` 计数与之一致）。

工具留在 `tools/check-mermaid.py`（本地跑，需要 Chrome）：

```
npx hexo generate
python3 tools/check-mermaid.py --list
```

### 7.3 坏因分两类

**一、机械类（规则能查，18 张）**

| 坏因 | 张数 | 例子 |
| --- | --- | --- |
| `gantt` 用 `dateFormat mm:ss` | 8 | `Invalid date:65:00`（mermaid 的 gantt 不认 `mm:ss`） |
| 虚线箭头带 `\|标签\|` | 6 | `A -.->|BEFORE| C` 不是合法写法（带文字的虚线要写 `-. 文字 .->`） |
| 全角竖线 `｜` | 2 | `XLogSendLogical-->｜非级联｜GetFlushRecPtr` |
| `grpah` 拼写 | 1 | |
| `...` 紧跟 `"]` | 1 | 见 7.4 |

**二、逐条不同的语法错（92 张）** —— 每张一个自己的问题，
没有共同规律，只能逐张看。

### 7.4 本轮修掉的那张：EP01 的首图

`postgresql-logical-replication-end-to-end-flow` 的第一张图
（也就是 EP01 的「本期机制图」）渲染不出来。错在这行：

```
A -->|"落盘到 subscriber 的 pg_wal/0000..."]
```

**根因不是少了个节点，是 mermaid 词法的一个坑**：
引号里的标签以 `...` 结尾、紧接着一个 `]` 时，mermaid 会把它拆错
（报错 `Expecting 'PIPE', 'TAGEND', ... got 'SQE'`）。
实测：

| 写法 | 结果 |
| --- | --- |
| `A -->\|"a..."\| B["x"]` | ✅ |
| `A -->\|"a..."]\| B["x"]` | ❌ |
| `A -->\|"a..."] B["x"]` | ❌ |

改成（补上缺的 `|`，并把落点这个节点补出来）：

```
A -->|"落盘到 subscriber 的 pg_wal/0000..."| SUBWAL["subscriber 的 pg_wal"]
```

现在这张图能正常渲染了——它是 6 期播客里 EP01 的门面图。
修完实测该页 **21 张图全部渲染成功**（原来 20 成功 1 失败）。

顺带把这件事变成可查的：`tools/check-mermaid.py` 能一次量出全站
所有渲不出来的图，`tests/test_mermaid_diagrams.py` 守住
`-->|"..."]` 这种写法不再进 `docs/`。

### 7.5 剩下的 109 张怎么办

不是这一轮该做的事（那要逐张改内容、逐张判断语义），但它应该是
P0/P1 里的一个明确条目：

1. **先让它们可见**：把 `tools/check-mermaid.py` 接进 CI
   （GitHub runner 自带 Chrome），哪怕只是「报告」也行——
   坏图从此不再隐形。
2. **再逐张修**：剩下的 109 张里有 91 张是各自的语法错，
   但错误信息很具体（mermaid 会指出行号和期望的 token），
   机械改一遍不难。
3. **修完把 109 降到 0 之后**，再把 CI 从「报告」改成「失败」——
   顺序反了会把部署卡住。
