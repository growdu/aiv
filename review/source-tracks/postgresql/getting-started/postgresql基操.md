# 审校：PostgreSQL 基本操作与基本对象

- 原文：drafts/source-tracks/postgresql/getting-started/postgresql基操.md（改动稿）
- 范围：全文
- 目标读者：刚接触 PostgreSQL、想弄清「库 → 表 → 文件」这条链到底怎么串起来，
  以及想在 psql 里自己查证的开发者
- 一句话定位：把「客户端要凑齐哪几样才能取到一条数据」与「服务端把库、表、oid、
  文件这四层怎么串起来」讲清楚，并给出每层都能自己跑的查询
- 核心判断：PostgreSQL 里最容易错的不是命令，是**概念的身份**——
  视图不是缓存（没有存储）、oid 不是文件号（`TRUNCATE` 会换）、
  表和索引不是一份文件

> **核实依据**：源码树 `/work/cwork/postgresql`，`REL_17_4-106-ga5b535fe0ad`
> （本文所有源码结论都逐条对过这一版）。原判断稿里有一条把「视图是内存里的缓存」
> 当成事实，本轮**推翻**并改正。

## 优先修改

1. 位置：L19「视图」条
   - 问题（类别）：事实
   - 建议（已采用）：改为「视图存的是一条查询定义，不是数据；视图**没有物理存储**」，
     并补源码依据：PG 17 的 `RELKIND_HAS_STORAGE`（`src/include/catalog/pg_class.h:197-202`）
     只含表、索引、序列、TOAST、物化视图，**不含视图**；连带的后果是
     `pg_relation_filepath('视图')` 返回 **NULL**（`src/backend/utils/adt/dbsize.c`
     的 `pg_relation_filepath()` 里 `"no storage, return NULL"`）。
     另补一句「要落地结果集的是物化视图（`relkind='m'`）」
   - 原因：这是全文唯一的**硬错误**。原稿说「视图是表的一部分在内存中的缓存」——
     视图不是缓存，它是一条存下来的查询；读者按缓存去理解性能与一致性，
     结论会整个反过来

2. 位置：L25-29「oid」与「文件」两条
   - 问题（类别）：事实
   - 建议（已采用）：补一条**号与号的区分**——`oid` 是对象身份，
     `relfilenumber`（PG 16 及以前叫 `relfilenode`）是物理文件号；
     `TRUNCATE` 之后 oid 不变、relfilenumber 换新的
     （源码：`src/backend/commands/tablecmds.c:2158` `ExecuteTruncate()`
     → `RelationSetNewRelfilenumber()`）
   - 原因：原文把 oid 一律说成「文件的编号」，读者会以为 `TRUNCATE` 之后
     表的「身份」也换了——这在扩展、监控、脚本里都会踩

3. 位置：L23「每个数据库都有自己的 oid」
   - 问题（类别）：事实
   - 建议（已采用）：明确写成「**oid 是实例级唯一的**」，
     依据 `src/backend/access/transam/varsup.c:545-556` 的 `GetNewObjectId()`：
     *"OIDs are generated by a cluster-wide counter."*
   - 原因：原文只说「不同数据库的 oid 不同」，读者容易反向理解成
     「每个库各有一套 oid 编号空间」——不是的

4. 位置：L17「表的数据最终以表的形式写入到文件里……小于 1gb 时是一个文件」
   - 问题（类别）：事实
   - 建议（已采用）：改成「**单个文件的上限是 1GB**（`RELSEG_SIZE * BLCKSZ`，
     默认 1GB），超了**拆成多个段文件**」
     （依据 `src/include/pg_config.h.in:647-658`：*"the maximum size of a single
     file is RELSEG_SIZE * BLCKSZ; relations bigger than that are divided into
     multiple files … By default, we make the limit 1 GB"*）
   - 原因：原文把「1GB」写成了表的属性，其实它是**文件系统的切分粒度**，
     跟表多大无关；而且方向说反了（不是小于 1GB 才是一个文件）

5. 位置：L14「结构相同的数据放在一起就是一张表……表的数据最终会写入到文件里」
   - 问题（类别）：事实
   - 建议（已采用）：补两条容易漏的——**索引不在表的文件里**（索引是独立的关系，
     自己的 oid、自己的文件），**大字段另存**（TOAST 表也是独立的关系）；
     并点明 `pg_relation_size()` 只算堆、`pg_total_relation_size()` 才含索引与 TOAST
   - 原因：原文讲完「表 → 文件」就停了，读者照着 `pg_relation_size` 看磁盘占用
     会发现和 `du` 对不上

6. 位置：L44-51「如何查找数据库有多少张表」
   - 问题（类别）：事实
   - 建议（已采用）：**这条命令给不出答案**——`\d` 只列**当前 `search_path` 下**

     `pg_class` 按 `relkind` + `pg_namespace` 过滤，并说明 `relkind` 的取值
     （`r` 表、`m` 物化视图、`v` 视图、`i` 索引、`S` 序列、`t` TOAST、`p` 分区表，
     依据 `src/include/catalog/pg_class.h:164-175`）
   - 原因：题目问「有多少张表」，给的却是「列出眼前可见的关系」——
     这是**命令与问题不匹配**，读者照做会以为答案是对的

## 事实待核

- [x] 视图没有物理存储 —— **初稿判断相反，本轮推翻**。PG 17
  `src/include/catalog/pg_class.h:197-202` 的 `RELKIND_HAS_STORAGE` 只含
  `RELKIND_RELATION` / `INDEX` / `SEQUENCE` / `TOASTVALUE` / `MATVIEW`，
  **不含 `RELKIND_VIEW`**
- [x] 无存储的关系，`pg_relation_filepath()` / `pg_relation_filenode()` 返回 NULL
  —— `src/backend/utils/adt/dbsize.c`，两处都是 `"no storage, return NULL"`
- [x] oid 由集群级计数器分配 —— `src/backend/access/transam/varsup.c:545-556`
  `GetNewObjectId()` 的注释 *"OIDs are generated by a cluster-wide counter."*
- [x] `TRUNCATE` 会换 relfilenumber —— `src/backend/commands/tablecmds.c:2158`
  `ExecuteTruncate()` → `RelationSetNewRelfilenumber()`
- [x] 单个关系文件上限 1GB，超出拆段 —— `src/include/pg_config.h.in:647-658`
  的 `RELSEG_SIZE` 说明（默认 1GB，`RELSEG_SIZE * BLCKSZ`）
- [x] `relkind` 的取值 —— `src/include/catalog/pg_class.h:164-175`：
  `r` 普通表、`i` 索引、`S` 序列、`t` TOAST、`v` 视图、`m` 物化视图、
  `c` 复合类型、`f` 外部表、`p` 分区表、`I` 分区索引
- [x] 认证方式的名字 —— 密码类：`password` / `md5` / `scram-sha-256`
  （`src/backend/libpq/auth.c:52`）；本地类：`trust` / `ident` / `peer` / `gss`
  （`src/backend/libpq/hba.c:105-117`）
- [不适用] `relfilenumber` 这个名字是 PG 17 才有的，PG 16 及以前叫 `relfilenode`
  —— 本次改动只在版本声明里标了这一条，正文里的行为描述在两版都成立，
  不阻塞
- [不适用] `pg_relation_filepath()` 在更早的版本对无存储关系返回 0 而不是 NULL
  —— 本次只对 PG 17 下断言，版本声明已写明；未核，不阻塞

## 可补的技术证据或产物

- 机制 / 源码入口：本文给了 `RELKIND_HAS_STORAGE`、`GetNewObjectId()`、
  `ExecuteTruncate()`、`RELSEG_SIZE` 四处。**还缺两处最关键的**——
  `src/backend/catalog/storage.c` 的 `RelationSetNewRelfilenumber()`（换文件号的
  实际动作）与 `src/backend/catalog/objectaddress.c` 的对象创建路径
  （`oid` 与 `relfilenumber` 各自从哪来）
- 实验或观测：原文只有两条查询，没有一条「我怎么看见它」。可补：
  建一张表再 `TRUNCATE` 一次，前后各跑一次 `pg_relation_filepath()`，
  看它怎么变；再 `SELECT relname, oid, relfilenumber FROM pg_class WHERE relname='student';`
  看 oid 没变而 relfilenumber 变了
- 工程取舍：原文只说「表是一个文件或多个文件」，没说**代价落在哪**——
  段文件多了，relcache 与检查点要管的段就多；`TRUNCATE` 换文件号意味着
  监控里的「文件路径」不能当稳定标识用
- 结尾清单或下一篇链接：结尾补了「三件最容易搞错的事」，但仍缺一篇
  「下一步」——同系列的《PostgreSQL 启动流程》讲的是后端起来之后怎么分工，
  正好接在本文的「客户端 ↔ 服务端」之后
