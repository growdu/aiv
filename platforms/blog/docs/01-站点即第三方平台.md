# 站点即第三方平台

**2026-11-18 顶层设计的一号改动**：把 growdu.cn 登记成 `platforms/` 下的
**第六个第三方平台**，跟公众号、头条号、抖音、视频号、B 站平级。

这一篇讲清楚三件事：

1. 站点**为什么**现在才算平台（它一直都在发内容，只是没登记）；
2. 站点跟另外五个平台**哪里同构、哪里不同构**；
3. 第三方平台那套通用流程（适配 → 生成 → review → output → upload）
   在站点上**分别是什么**。

顶层设计的全文在
[`review/specs/2026-11-18-顶层设计与目录调整.md`](../../../review/specs/2026-11-18-顶层设计与目录调整.md)，
站点重做的全文在
[`review/specs/2026-11-18-站点重做-学习流门面.md`](../../../review/specs/2026-11-18-站点重做-学习流门面.md)。

## 一、站点为什么现在才算平台

在这之前，站点走的是**另一条路**：

```
docs/  ──tools/build-content-units.py──▶  content/units/  ──site/tools/build-posts.py──▶  site/source/_posts/
                                                                                            site/source/docs/
                                                                                            site/source/images/
                                       └──site/tools/build-learning-path.py──▶  site/data/learning-path.compiled.json
                     Hexo（site/）──npm run build──▶  site/dist/
```

（`content/units/` 是**所有平台共用的那一半**——它由根 `tools/` 里那个
平台无关的编译器编出来，站点只是它的一个消费者。
见 §六之二与顶层设计 §4.2。）

而另外五个平台走的是：

```
docs/  ──适配──▶  清单 manifest  ──出包/接口──▶  平台草稿箱  ──▶  已发链接
       读 platforms/<plat>/capability.toml
       写 platforms/<plat>/outbox/*.json
```

两套东西，于是顶层的心智模型**缺了一块**：

- 目录里数得出来**五个**平台，设计里说的是**六个**；
- 「加平台只动 `platforms/`」这句话对站点**不成立**——
  站点根本不在 `platforms/` 里；
- 「第三方平台的核心流程是 适配 → 生成 → review → output → upload」
  这句话套不上站点——站点没有「output 一个包再 upload」这一步。

现在的形状是**同构**的：

```
platforms/blog/
├── capability.toml      能力声明（限额、档位、审核方式）
├── __init__.py cli.py   adapter
├── outbox/              发布账本
├── docs/                这一篇
└── site/                站点构建链（Hexo + matery）
```

**目录名 = 平台 id = Python 包名 = 快照后缀**，六个平台一个规矩。

> 上游的 `docs/` 是**已过审的母稿**（工作区在 `drafts/`，见
> `review/specs/2026-11-18-草稿层与母稿层的接口协议.md`）。
> 平台层只管「从母稿到站点」这一段，**不回头**管「稿子是怎么审出来的」。

## 二、同构在哪，不同在哪

| | 公众号 / 头条 / 抖音 / 视频号 / B 站 | 站点 |
| --- | --- | --- |
| 能力声明 | `capability.toml` | **同一份格式**（`capability.toml`） |
| 限额从哪来 | 平台实测值 | **我们自己的取舍**（见 §4） |
| 自动化档位 | `manual` / `api_draft` | **`api_publish`**——六个里只有站点是这个档 |
| 发布前审核 | 平台机审 / 后台预览 | **本地闸门**（`site/tools/` + `site/tests/` + `site.yml`） |
| 出包 | 逐篇出一个包，发一篇 | **全量构建**：一次 push 重建全站 |
| 发布账本 | `outbox/*.json`（幂等键：发过就不重发） | `outbox/*.json`（**账**：当前在站上是什么状态） |
| 凭据 | 账号 / token | **没有**——推上去就重建 |

### 唯一的实质差别：出包方式

那五个平台是「**逐篇出包、发一篇文章**」。
站点不是——站点没有「一篇一篇发」这回事，只有「**整站重建一次**」。

所以 `platforms/blog/` **没有 `publish` 子命令**。
这不是漏做，是刻意的：把逐篇出包在这里重写一遍，
等于把 `site/tools/` + Hexo 再写一遍，**两份必然漂移**。

站点 adapter 只回答三个问题：

```bash
cd platforms
python3 -m blog.cli status                          # 这个平台是什么、站上现在是什么样子
python3 -m blog.cli check <content_id>              # 这一篇能不能进站
```

`check` 问的四件事，每一件都问权威，不自己复刻规则：

| 问什么 | 问谁 |
| --- | --- |
| 母稿过审了没有 | `docs/`（母稿层）还是 `drafts/`（草稿层） |
| 编译器收不收 | `tools/build-content-units.py --only <id>` |
| 地址是什么 | `site/tools/urls.py`（站点里唯一决定链接形状的地方） |
| 归到学习流哪一格 | `site/data/learning-path.compiled.json` |

## 三、五步流程在站点上各是什么

第三方平台的通用流程是
**适配 → 生成 → review → output → upload**（详见
`review/specs/platform/multiplatform/` 与 `publish/spec/00-架构设计.md`）。
站点在这五步上各有对应物：

| 步 | 别的平台 | 站点（目标位置 `platforms/blog/site/`） |
| --- | --- | --- |
| **适配** | 按 `capability.toml` 的限额裁标题、压正文、配图 | **根 `tools/build-content-units.py`**：推导 front matter（标题、描述、日期、分类链、标签链），**正文一个字都不改**；`docs/` 下的图片也按 docs 相对路径拷进 `content/units/images/`。站点侧再由 `site/tools/build-posts.py` 把内容单元接进 Hexo 工程（文章写进 `source/_posts/`，分类页写进 `source/docs/`）、把图片拷进 `source/images/` |
| **生成** | 渲染成平台版式（HTML / 竖版切片 / 投稿包） | **Hexo**（`site/`，matery 主题）：markdown → 静态站。链接重写走 **AST**（`site/tools/rewrite-links.mjs`，remark），mermaid 转换走 hexo 过滤器（`site/scripts/mermaid.js`），两者都不扫文本 |
| **review** | 平台机审 + 人工预览 | **本地闸门**：`site/tools/check-markdown.py docs/`（围栏体检；CI 只扫 `docs/`，草稿箱归母稿层）、`site/tests/`（身份通用性、学习流归属、死链、页面齐全、首页一屏）、`tools/build-content-units.py --check`（编译器幂等、无残留）、`site/tools/build-learning-path.py`（**漏归类即失败**；编译结果是产物不入库，所以 CI 跑的是编译而不是 `--check`），加上 `.github/workflows/site.yml` 把它们串起来 |
| **output** | 出一个包（`out/<content_id>/`）或一份 manifest | **整个 `site/dist/`**——一次构建一份（页数随内容走） |
| **upload** | 调平台 API（`draft/add`）或浏览器自动化 | **还没做**——上线那一轮才接。现在 CI 只构建与校验，产物作为 artifact 挂在 run 上 |

两处**结构性**的差异，值得单独记住：

1. **output 的粒度不同。** 别的平台 output 是一篇一个包，
   所以 outbox 能当幂等键用。站点 output 是全站一份，
   所以「重发一遍」不是错误，而是**常态**（每次 push 都重建全站）。
2. **upload 没有凭据。** 站点是自己的站，推上去就重建。
   别的平台停在 `manual` 档，是因为**平台那边**的权限或审核拦着，
   不是我们偷懒——这是六个平台里唯一一个 `api_publish`。

## 四、能力声明里那几个值是怎么来的

`platforms/blog/capability.toml` 里只有两个真数字：

```toml
[limits]
image_bytes = 2097152     # 2 MB
```

**标题与正文的限额故意不声明。**
声明一个数就是许诺一个数——契约层会拿它当闸，超了判违规。
站点不吃平台那套限额（标题和正文都不设上限），
与其编一个「站点标题上限 200 字」这种没依据的数字，**不如不声明**
（不声明就不查）。

`image_bytes = 2 MB` 是**我们自己的取舍**，不是站点的限制：

- 站点的图片随母稿进 git（`docs/` 下），构建时**按原文件名拷进 `source/images/`，不转码**——
  所以这个数字约束的是「**进 git 之前**」，不是「上传到站点时」；
- 单张图超过 2 MB，仓库与 CI 传输都会明显变重；
- 这个数来自旧站点的实测（那时产物有 167 MB / 2400 个文件）。
  现在站点是 Hexo + matery，产物体积早已不是大头，
  但「图片进 git」这一点没变，所以这条约束照旧成立。

其余几个字段：

| 字段 | 值 | 为什么 |
| --- | --- | --- |
| `id` | `blog` | 目录名即 id（六个平台同一规矩） |
| `kind` | `document` | 站点上的一切都是 markdown 页面。视频内容单元（口播稿）也是**文章**，不是成片 |
| `auth` | `none` | 推上去就重建，没有账号、没有 token |
| `automation` | `api_publish` | 六个里唯一。声明的是这个平台的**档位**；部署那一步还没做（§3 的 upload） |
| `review` | `precheck` | 站点没有「平台机审」，但有一整套本地闸门——那套闸门就是站点的「平台审核」 |
| `verified` | `2026-11-18` | 上面这些值最后对着实测复核过的日期 |

## 五、账本（`outbox/`）现在为什么是空的

**空的，而且是刻意的。**

要回填账本，先得回答一个问题：**站点的「已发布」是什么时候？**
站点没有 `published_at`——它只有 **git 历史**（哪一次 push 把它带上站的）。
所以快照里的 `status` 该写 `published`？`updated_at` 该写哪个时间？
这不是随手能填的字段，要单独做一次。

在那之前，站点「在不在站上」的真相在两个地方：
**git 历史** 与 **构建产物**（`site/dist/`）。
快照补上之后，这两个是**补充**，不是唯一。

> ⚠️ **不要先放几份快照试试。**
> 快照落盘就是「这篇已经发过了」的断言——调度器读到它会跳过这一篇
> （`status = failed` 除外）。放一份假的进去，等于替某个内容单元说了「发过了」。
> 回填是一次**成批的、可重放的**动作。
> 账本的字段与文件名约定写在 [`outbox/README.md`](../outbox/README.md)。

## 六、这个包里有什么、没有什么

有：

| 文件 | 干什么 |
| --- | --- |
| `capability.toml` | 能力声明：限额、档位、审核方式、adapter 入口 |
| `__init__.py` | 包常量：仓库根、母稿层 `docs/`、草稿层 `drafts/`、内容单元仓库 `content/units/`、outbox 目录、地址深度上限 |
| `cli.py` | `status` / `check` 两个子命令 |
| `outbox/` | 发布账本（现在空着） |
| `docs/01-站点即第三方平台.md` | 这一篇 |
| `site/` | 站点构建链（见 §六之二） |

**没有**：

- **没有 `publish` 子命令**——站点是全量构建，没有「逐篇出包」这回事（§2）；
- **没有 `render.py` / `package.py` 之类**——
  站点适配的实体是**编译链**（根 `tools/build-content-units.py`）
  加**渲染层**（`site/`，Hexo + matery 主题），
  它们**不是**另写一套 adapter，而是站点这一平台**自己的构建链**；
- **没有 outbox 快照**——理由见 §五。

### §六之二、站点构建链住进 `platforms/blog/site/`

站点的构建链原本散在仓库根（`_config*.yml`、`themes/matery/`、
`scripts/`、`source/`、`public/`，以及 `tools/` 里那一批 hexo 时代的脚本）。
**它们是站点这一个平台自己的实现**，所以搬到了 `platforms/blog/site/`
（2026-11-18 落地）——「**加平台只动 `platforms/`**」对站点**也成立**。

站点重做（2026-11-18 晚些时候）把 hexo 换成了 **Astro**；
2026-11-20 又换回 **Hexo + matery**（作者要的是 blog-bak 那套的效果，
规格见 `review/specs/2026-11-20-站点框架换成hexo.md`）。
于是 `site/` 里的私产换了一遍：

| 目录 | 装什么 |
| --- | --- |
| `site/themes/matery/` | 主题树：页面模板、样式、静态资源。**框架层，不含身份** |
| `site/scripts/` | Hexo 过滤器：mermaid 转换、归档页兜底 |
| `site/source/` | Hexo 源（**构建时生成**，不入库）：`_posts/`（文章）、`docs/`（分类页）、`learning/`、`_data/`（身份投影与学习流数据）、`images/`、`lib/`、`about/`、`all/`、`404.md`、`robots.txt` |
| `site/data/` | 站点私产的数据：**站点身份与结构**（`site.json`）、学习流规则表（人工策展）、编译结果、代码块语言别名表 |
| `site/content/` | 站点自己的页面正文（现在只有「关于」页）——使用者写的，不是内容单元 |
| `site/tools/` | 站点这一平台自己的工具：文章编译、学习流编译、身份注入、第三方库本地化、**AST 级链接重写**、围栏体检 |
| `site/tests/` | 站点自己的守卫：身份通用性、学习流归属、地址形状、死链、页面齐全、首页一屏、mermaid（79 个用例） |
| `site/dist/` | 构建产物（不入库） |

> **站点只读 `content/units/`**（上游编译器编出来的产物）。
> 内容是它的来源与接口；`drafts/`、`video/`、仓库的旧历史都不在它的视野里。
> 它**不留副本**——副本是字节级重复，仓库早就把它记成欠账。

> **站点是个通用框架，规则在框架里，身份在使用者手里。**
> 名字、简介、首页首屏、导航、页脚全在 `site/data/site.json`；
> 框架源码里**不许出现站名**（`site/tests/test_site_config.py` 守着这条）。
> 学习流是**可选模块**：`site/data/learning-path.json` 里 `enabled: false`，
> 就一个学习流页面都不生成，导航项自动消失。
> 怎么把它变成自己的站，见 `site/README.md`。

> 留在根 `tools/` 的是**平台无关**的那批（`build-content-units.py`、
> `check-content-contract.py`、`review-check.py`、`paths.py` 等）——
> 它们不属于任何一个平台。
>
> 另有一处**内容单元仓库** `content/units/`：它是**所有平台共用的那一半**，
> 由根编译器编出来。站点**直接读它**，不留副本。

## 七、这一轮之后仍然不做的

- **不部署**——`upload` 那一步留给上线那一轮。CI 现在只构建与校验；
- **不写 `publishkit` 的站点支持**——**契约层不认识任何平台**，
  站点的能力声明由契约层**按目录扫出来**即可，它不需要额外代码；
- **不回填 `outbox/` 快照**（§五）；
- **不新增面向读者的文章**（`docs/platform-meta/`）——
  那是内容层的事，见顶层设计 §8。
