# 站点即第三方平台

**2026-11-18 顶层设计的一号改动**：把 growdu.cn 登记成 `platforms/` 下的
**第六个第三方平台**，跟公众号、头条号、抖音、视频号、B 站平级。

这一篇讲清楚三件事：

1. 站点**为什么**现在才算平台（它一直都在发内容，只是没登记）；
2. 站点跟另外五个平台**哪里同构、哪里不同构**；
3. 第三方平台那套通用流程（适配 → 生成 → review → output → upload）
   在站点上**分别是什么**。

顶层设计的全文在
[`review/specs/2026-11-18-顶层设计与目录调整.md`](../../../review/specs/2026-11-18-顶层设计与目录调整.md)。

---

## 一、站点为什么现在才算平台

在这之前，站点走的是**另一条路**：

```
docs/  ──tools/sync-hexo.py──▶  source/_posts/  ──hexo──▶  public/  ──CI──▶  站点
```

而另外五个平台走的是：

```
docs/  ──适配──▶  清单 manifest  ──出包/接口──▶  平台草稿箱  ──▶  已发链接
       读 platforms/<plat>/capability.toml
       写 platforms/<plat>/outbox/*.json
```

两套东西，于是顶层的心智模型**缺了一块**：

- 目录里数得出来**五个**平台，设计里说的是**六个**；
- 「加平台只动 `platforms/`」这句话对站点**不成立**——
  站点根本不在 `platforms/` 里；
- 「第三方平台的核心流程是 适配 → 生成 → review → output → upload」
  这句话套不上站点——站点没有「output 一个包再 upload」这一步。

现在的形状是**同构**的：

```
platforms/blog/
├── capability.toml      能力声明（限额、档位、审核方式）
├── __init__.py cli.py   adapter
├── outbox/              发布账本
├── docs/                这一篇
└── README.md
```

**目录名 = 平台 id = Python 包名 = 快照后缀**，六个平台一个规矩。

---

## 二、同构在哪，不同在哪

| | 公众号 / 头条 / 抖音 / 视频号 / B 站 | 站点 |
| --- | --- | --- |
| 能力声明 | `capability.toml` | **同一份格式**（`capability.toml`） |
| 限额从哪来 | 平台实测值 | **我们自己的取舍**（见 §4） |
| 自动化档位 | `manual` / `api_draft` | **`api_publish`**——六个里只有站点是这个档 |
| 发布前审核 | 平台机审 / 后台预览 | **本地闸门**（`tools/check-*.py` + `site-guard.yml`） |
| 出包 | 逐篇出一个包，发一篇 | **全量构建**：一次 push 重建 2400 个页面 |
| 发布账本 | `outbox/*.json`（幂等键：发过就不重发） | `outbox/*.json`（**账**：当前在站上是什么状态） |
| 凭据 | 账号 / token | **没有**——推上去就部署 |

### 唯一的实质差别：出包方式

那五个平台是「**逐篇出包、发一篇文章**」。
站点不是——站点没有「一篇一篇发」这回事，只有「**整站重建一次**」。

所以 `platforms/blog/` **没有 `publish` 子命令**。
这不是漏做，是刻意的：把逐篇出包在这里重写一遍，
等于把 `tools/sync-hexo.py` + hexo 再写一遍，**两份必然漂移**。

站点 adapter 只回答两个问题：

```bash
cd platforms
python3 -m blog.cli status                          # 这个平台是什么、有什么限额、账本上多少条
python3 -m blog.cli check <content_id>              # 这一篇能不能进站
```

## 三、五步流程在站点上各是什么

第三方平台的通用流程是
**适配 → 生成 → review → output → upload**（详见
`docs/platform-meta/multiplatform/` 与 `publish/spec/00-架构设计.md`）。
站点在这五步上各有对应物：

| 步 | 别的平台 | 站点 |
| --- | --- | --- |
| **适配** | 按 `capability.toml` 的限额裁标题、压正文、配图 | **`tools/sync-hexo.py`**：剥首个 H1、重写图片与相对链接、重建 front matter（推导字段 + 透传白名单）、排除工程目录 |
| **生成** | 渲染成平台版式（HTML / 竖版切片 / 投稿包） | **hexo + `themes/matery/`**：markdown → 静态站 |
| **review** | 平台机审 + 人工预览 | **本地闸门**：`tools/check-content-contract.py`、`tools/check-markdown.py`、`tools/check-internal-links.py`，加上 `.github/workflows/site-guard.yml` 的契约测试 |
| **output** | 出一个包（`out/<content_id>/`）或一份 manifest | **整个 `public/`**——一次构建 2400 个页面、167 MB |
| **upload** | 调平台 API（`draft/add`）或浏览器自动化 | **CI 部署**：rsync 到自建服务器 + 推 GitHub Pages |

两处**结构性**的差异，值得单独记住：

1. **output 的粒度不同。** 别的平台 output 是一篇一个包，
   所以 outbox 能当幂等键用。站点 output 是全站一份，
   所以「重发一遍」不是错误，而是**常态**（每次 push 都重发全站）。
2. **upload 没有凭据。** 站点是自己的站，推上去就部署。
   别的平台停在 `manual` 档，是因为**平台那边**的权限或审核拦着，
   不是我们偷懒——这是六个平台里唯一一个 `api_publish`。

## 四、能力声明里那几个值是怎么来的

`platforms/blog/capability.toml` 里只有两个真数字：

```toml
[limits]
image_bytes = 2097152     # 2 MB
```

**标题与正文的限额故意不声明。**
声明一个数就是许诺一个数——契约层会拿它当闸，超了判违规。
站点不吃平台那套限额（标题和正文都不设上限），
与其编一个「站点标题上限 200 字」这种没依据的数字，**不如不声明**
（不声明就不查）。

`image_bytes = 2 MB` 是**我们自己的取舍**，不是站点的限制：

- 站点产物一共 **167 MB / 2400 个文件**（2026-11-18 实测）；
- CI 部署那一步要搬三遍（构建产物 → artifact → 服务器 / Pages）；
- 单张图超过 2 MB，git 仓库与 CI 传输都会明显变重；
- 站点的图片走 `source/images/`，**按原文件名落盘，不转码**——
  所以这个数字约束的是「**进 git 之前**」，不是「上传到站点时」。

其余几个字段：

| 字段 | 值 | 为什么 |
| --- | --- | --- |
| `id` | `blog` | 目录名即 id（六个平台同一规矩） |
| `kind` | `document` | 站点上的一切都是 markdown 页面。视频规范页面（`docs/life/aiv/`）也是**文章**，不是成片 |
| `auth` | `none` | 推上去就部署，没有账号、没有 token |
| `automation` | `api_publish` | 六个里唯一 |
| `review` | `precheck` | 站点没有「平台机审」，但有一整套本地闸门——那套闸门就是站点的「平台审核」 |
| `verified` | `2026-11-18` | 上面这些值最后对着实测复核过的日期 |

## 五、账本（`outbox/`）现在为什么是空的

**空的，而且是刻意的。**

要回填账本，先得回答一个问题：**站点的「已发布」是什么时候？**
站点没有 `published_at`——它只有 **git 历史**（哪一次 push 把它带上站的）。
所以快照里的 `status` 该写 `published`？`updated_at` 该写哪个时间？
这不是随手能填的字段，要单独做一次。

在那之前，站点「在不在站上」的真相在两个地方：
**git 历史** 与 **CI 构建产物**（`public/`）。
快照补上之后，这两个是**补充**，不是唯一。

> ⚠️ **不要先放几份快照试试。**
> `publish/tests/test_schedule.py` 里有一条守卫断言全仓库快照总数**恰好 566**
> （另外五个平台的账）。多一份少一份，那条守卫就红。
> 回填是一次**成批的、可重放的**动作。

## 六、这个包里有什么、没有什么

有：

| 文件 | 干什么 |
| --- | --- |
| `capability.toml` | 能力声明：限额、档位、审核方式、adapter 入口 |
| `__init__.py` | 包常量：仓库根、`docs/` 目录、outbox 目录、分类链深度、构建排除名单 |
| `cli.py` | `status` / `check` 两个子命令 |
| `outbox/` | 发布账本（现在空着） |
| `docs/01-站点即第三方平台.md` | 这一篇 |

**没有**：

- **没有 `publish` 子命令**——站点是全量构建，没有「逐篇出包」这回事（§2）；
- **没有 `tests/`**——这一轮不写测试（顶层设计阶段，先定架构）；
- **没有 adapter 代码**（`render.py` / `package.py` 之类）——
  站点适配的实体是 `tools/sync-hexo.py` + `themes/matery/`，
  它们在**内容编译层**与**展示层**，不在平台层里。
  把它们搬进 `platforms/blog/` 只会让站点变成唯一特例。

---

## 七、这一轮不做什么

- 不改站点的构建链路（`sync-hexo.py`、主题、CI 一个字不改）；
- 不动 `docs/` 下任何一篇母稿；
- 不回填 `outbox/` 快照（§5）；
- 不写 `publishkit` 的站点支持——**契约层不认识任何平台**，
  站点的能力声明由契约层**按目录扫出来**即可，它不需要额外代码；
- 不新增面向读者的文章（`docs/platform-meta/`）——
  那是下一轮的事，见顶层设计 §8。
