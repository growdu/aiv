# 站点架构（2026-11-18 起：Astro）

加新文章、换样式、修构建，先看这份再下手。

> **这份文档被站点重做整个换掉了。** 旧版讲的是 hexo + matery 主题
> （`themes/matery/`、`_config.matery.yml`、`tools/sync-hexo.py`……），
> 那些**全都不存在了**。旧版留在 git 历史里（`git log -- internal/blog/架构.md`）。
> 新站的完整设计见
> [`review/specs/2026-11-18-站点重做-学习流门面.md`](../../review/specs/2026-11-18-站点重做-学习流门面.md)。

## 三个边界

- `docs/` —— **母稿**。内容的唯一真相。加文章、改文章都从这里开始
  （但要先在 `drafts/` 里写，过审才覆盖 `docs/`）。
- `content/units/` —— **内容单元**。`docs/` 编译出来的中间形态，所有平台共用。
  **不入库**，每次现编。
- `platforms/blog/site/` —— **站点这一个平台的实现**。Astro 工程、数据表、
  站点自己的工具与守卫测试。

链路只有一条：

```
docs/  ──tools/build-content-units.py──▶  content/units/  ──site/tools/sync-content.py──▶  src/content/units/
                                                                                          │
                        site/data/learning-path.json ──site/tools/build-learning-path.py──▶ learning-path.compiled.json
                                                                                          │
                                                                                    npx astro build
                                                                                          ▼
                                                                                       dist/  （61 页）
```

## 一次 push 之后发生了什么

按 `.github/workflows/site.yml` 的执行顺序（两个 job，各管一半）：

**verify job（纯 Python，几秒钟）**

1. `python3 tools/build-content-units.py` —— 读 `docs/` 下所有母稿，编出内容单元。
2. `python3 tools/build-video-pages.py` —— 视频线的口播稿（`video/字幕-<主题>.md`）
   编成 `content/units/video/`。母稿在视频线，**不在 `docs/` 里**，所以这是两件事。
3. `python3 tools/build-content-units.py --check` —— 再编一遍，与上一步写进磁盘的
   逐字节比对：编译器必须每次编出一样的东西；磁盘上也不能有 `docs/` 里已撤掉的残留。
4. `python3 platforms/blog/site/tools/check-markdown.py docs/` —— 围栏畸形、表格列数不齐、
   mermaid 块不对……这些是**母稿层**的毛病，在这里报出来。
   （CI 只扫 `docs/`；本地跑不带参数的版本会连 `drafts/` 一起扫，那是自查草稿用的。）
5. `python3 platforms/blog/site/tools/build-learning-path.py` —— 学习流编译。
   **漏归类是构建失败**，不许静默。
   （CI 跑的是**编译**不是 `--check`：编译结果是产物、不入库，CI 的全新 checkout
   里它不存在，`--check` 在那儿必然报「学习流数据不存在」。真正的闸门是编译本身。）

**build job（要装 Node）**

6. `npm ci` —— 站点依赖（`platforms/blog/site/`）。
7. `npm run build` —— 三步：`compile`（学习流）→ `sync`（内容单元与静态资源进站点）
   → `astro build`（产物在 `platforms/blog/site/dist/`）。
8. `python3 -m pytest tests/ -q` —— 站点守卫测试（26 条）：每个内容单元都有页面、
   站内没有死链。**这一步必须在 build job 里**，因为它要的是刚构建出来的 `dist/`。
9. 产物作为 artifact 挂上（`site-dist`）。

> **不部署。** 线上 growdu.cn 还是旧版，部署链归上线那一轮。

## 怎么改东西

**加一篇文章。**流程跟别的平台一样：**先在 `drafts/` 里写**，过审才覆盖 `docs/`。
`docs/` 下的目录结构**就是**站点上的分类结构——一级目录 = 分类，二级目录 = 二级内容，
一篇文档 = 一期。在 `docs/` 里建新目录 = 在站上新增一个公开分类，慎重。

母稿 front matter 的硬要求（编译器会直接失败）：**标题、描述、日期、目录链**四项齐全。
少任何一项，`build-content-units.py` 就断。

**改学习流。** `platforms/blog/site/data/learning-path.json` —— 人工策展的规则表
（赛道 × 阶段 × 匹配规则）。规则从上往下第一条命中即生效。
加一篇内容进去，**必须**给它写一条规则：漏归类 = 构建失败，不是「先放兜底里」。
分类页（`kind: category`）是目录导航，**不进**学习流。

**改样式、加组件。** `platforms/blog/site/src/`：

| 位置 | 放什么 |
| --- | --- |
| `src/pages/` | 路由页（`index.astro`、`docs/`、`videos/`、`learning/`、`all/`、`about/`、`404.astro`） |
| `src/components/` | 组件（`TrackCard`、`StageLadder`、`UnitRow`、`DocTree`、`TreeItem`、`Outline`） |
| `src/layouts/` | 布局（`Base.astro`） |
| `src/styles/` | 样式 |
| `src/lib/` | 链接规则与渲染插件（见下） |

**文章页的两栏。** 左栏是**目录树**，右栏是**文章大纲**（+ 元信息）：

- 目录树在 `src/lib/tree.ts` 里生成——**树就是 docs/ 的真实结构**：
  内容单元的 id 就是它相对 docs/ 的路径，把 id 切开就是树
  （`_index.md` = 目录的落地页，其余 `.md` = 文章）。站点不另造分类。
- 学习流折在树上：阶段本来就是目录（`…/getting-started/` 就是 L1），
  节点上挂 L1 / L2 标记；目录只有在直接装着同一个阶段的文章时才标。
- 大纲来自 Astro 渲染时给的 `headings`（slug 与正文锚点一致）。
- 树与大纲由 `site/tests/test_sidebars.py` 守着：两栏成对、树里不缺任何一篇。

**改 Markdown 渲染。** `platforms/blog/site/src/lib/` 下三个 remark/rehype 插件：
`remark-drop-first-h1.mjs`（去掉正文第一个 H1，标题由页面模板给）、
`remark-site-links.mjs`（站内链接改写）、`rehype-mermaid.mjs`（mermaid 块转容器）。
Astro 7 默认的处理器不支持 JS 插件，所以走 `@astrojs/markdown-remark` 的 unified()。

**改静态资源。** `platforms/blog/site/public/` 是静态资源的**源码**目录，
**不是产物**（产物是 `dist/`）。`favicon` 入库；`images/`、`js/` 是构建时
从 `docs/` 与 `node_modules/` 同步进来的，不入库。

## URL 规则（只有一处）

`platforms/blog/site/src/lib/urls.ts` —— 站点里**只有这一处**决定链接长什么样。

| 单元 id | URL |
| --- | --- |
| `source-tracks/postgresql/getting-started/postgresql基操` | `/docs/source-tracks/postgresql/getting-started/postgresql基操/` |
| `source-tracks/postgresql/_index`（分类页） | `/docs/source-tracks/postgresql/` |
| `video/row-lock`（视频） | `/videos/row-lock/` |

单元 id 是内容单元相对 `content/units/` 的路径（不带 `.md`）。
分类页的 id 尾巴带 `_index`、视频的 id 开头带 `video/`——那是**内容单元里的形状**，
不是 URL 里的形状。`urls.ts` 负责把这两处抹掉；漏抹一次就是一批死链。

## 站内链接怎么写

- 跨文章：相对路径 `./postgresql基操.md`（文件名跟 `docs/` 里一致）。
  `remark-site-links.mjs` 负责把它改写成站点里的真地址。
- 分类页：相对路径指向目录里的 `_index.md`，**不要**手写 `/docs/...` 绝对地址——
  绝对地址一改目录结构就全成死链。
- 外部站：普通 `https://` 链接。

不要写日期段的绝对地址。日期由编译器从 git log 取，重算之后 URL 会变。

## 同样要避开的

- `content/units/` 与 `platforms/blog/site/src/content/units/`：**构建产物，不入库**。
  改了 `docs/` 要重新编译，不要手改副本。
- `platforms/blog/site/dist/`：构建产物，不入库。
- 在 `docs/` 里写模板语法或站点专有的东西：`docs/` 是母稿，只该有裸内容。
- 在 `platforms/blog/site/tools/` 里写「顺便也改改别的模块」的逻辑：
  站点工具只管站点，跨平台的规则归根 `tools/`。

**本地命令**（在 `platforms/blog/site/` 里跑）：

```bash
npm run compile     # 学习流编译
npm run sync        # 内容单元 → 站点副本
npm run build       # compile + sync + astro build
npm run preview     # 本地预览
npm test            # 站点守卫测试
```

**验收在站点自己的目录里跑**（一条模块一条命令，跨模块只验接口）：

```bash
cd platforms/blog/site && python3 -m pytest tests/ -q
```
