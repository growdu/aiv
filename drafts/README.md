# 草稿箱

新写的稿子先落这里，审完也留着。它是**两条流水线的共同入口**。

**它在 `docs/` / `video/` 的上游**——确切的两条流是：

```
① 文档流   draft ──▶ review ──▶ docs  ──▶ 第三方平台（文档类）
② 视频流   draft ──▶ review ──▶ video ──▶ 第三方平台（视频类）
```

草稿箱管的是**新内容和改动**。仓库里现存的 560 篇母稿与 6 期成片是**存量**，
它们停在第 2 段出口（`review → docs` / `review → video`），
**不回炉**再走一遍 `draft → review`（见
`review/specs/2026-11-18-顶层设计与目录调整.md` §1.3）。

> **一条总规则**：往后的**新增**和**修改**都在 `drafts/` 里做，
> 过完 `review/` 才进 `docs/` 和 `video/`。
> `docs/` 里那一份始终是**已过审的版本**——
> 改动稿在 `drafts/` 期间不覆盖它。

**目录即接口**：这个目录里的**目录结构就是接口**。

```
drafts/<分类>/<二级内容>/<期号>.md
  ↑ 一级目录 = 一个分类      一篇文档 = 一期
    二级目录 = 一块二级内容
```

`docs/` 与 `video/` 是**同形**的两棵树。分类不声明三遍——
它**只存在于目录里**（详见
`review/specs/2026-11-18-目录即接口与分类增设.md`）。

## 一、⚠️ 在这里建目录之前，先读这一段

> **在 `drafts/` 下建目录，是一个策展动作，不是一个文件操作。**

建一级目录 = **新增一个对外可见的分类**；
建二级目录 = **新增一块二级内容**。
它带来三件不会自动消失的事：

1. **URL 命名空间是永久的。** 分类页一旦生成，地址就是它的身份；
   改名等于让所有指向它的链接失效（站外也失效）。
2. **三边要同形。** `docs/` 与 `video/` 要跟着长出同形的一层；
   只长一边，这棵树就不同形，坐标就对不上。
3. **要登记映射。** `platforms/blog/site/data/learning-path.json`
   得给这个目录一条规则。
   **空分类不被任何守卫管**——它没有文章，也就没有「文章必须归到某条赛道」
   这条断言兜着。

所以规矩是：

- **先把稿子放在既有分类里**，确认它确实撑得起一个分类了，再开目录；
- **开目录要过审**——分类审校六问见
  [`review/specs/2026-11-18-目录即接口与分类增设.md`](../review/specs/2026-11-18-目录即接口与分类增设.md) §四；
- **一次只开一层**，别顺手开三级；
- **开完记得在 `learning-path.json` 登记**（全流程唯一的跨层手写处）。

> **反例留档**：`docs/base/` 这类混主题目录，曾经把好几条主线的文章混在一个
> 目录下，拆的时候「该拆该合」只能靠人判断。现在所有目录都挂在一条明确的
> 线下，一条线一个话题。

## 二、起点：主题

流水线的起点不是文件，是**一段话**——**主题**：

> 用户产生 idea 的时候，输入的那段话。

比如「Hexo 的站点构建里，链接重写为什么老出错」——
这一段话就是主题。它记着**核心思想**：想讲什么、给谁看、想解决什么问题。

**主题不是一层，也不是一个目录。**

它不建自己的目录、不产出自己的内容单元、不进站。
它是流水线的**一个输入参数**，最终落进那份稿子的 front matter：

```yaml
---
topic: "Hexo 的站点构建里，链接重写为什么老出错"
---
```

自动生成工具读的就是这个字段；手动写的时候，它是这一份稿子的起点说明。

## 三、主题 → 草稿：两条走法

```
                     主题（一段话）
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
         手动编写                  自动生成
     （人坐下来写）           （工具读 topic 起草）
              └───────────┬───────────┘
                          ▼
              drafts/<日期>-<主题>.md      ← 草稿箱
                          │
                     总审核 review/
                          │
        ┌─────────────────┴─────────────────┐
        ▼                                   ▼
      docs/                               video/
   （文档流母稿）                      （视频流母稿）
```

两条走法产出的是**同一种东西**：一份带 front matter 的 markdown 底稿。
写完都进草稿箱，都过同一道总审核。

> **主题不决定它进哪条线。** 一段主题可能同时是「一篇站点文章」和
> 「一期视频」的起点——那是**两份底稿**（母稿唯一：文档流与视频流各有一份，
> 互不派生）。这一点跟平台层无关：平台是下游的事，
> 主题只管「想讲什么」。

## 四、草稿箱的流程

**新增和修改走同一套。**

1. 要写的稿子、或要改的稿子，都先放进 `drafts/`（文件名带日期与主题）。
2. 过总审核：文章看 `review/`，视频稿看 `video/review/` 的口径要求。
3. 通过后**复制**一份进 `docs/`（站点文章）或 `video/`（视频母稿）。
4. 底稿留在 `drafts/`，**不再参与任何派生**。
5. 平台版由 `platforms/<plat>/` 各自出包，落在 `platforms/<plat>/outbox/`。

**修改已有内容时**多一条：改动稿留在 `drafts/`，**不直接改 `docs/`**。
`docs/` 里那一份要等 review 通过才被覆盖——
所以任何时刻 `docs/` 都是「已过审的版本」，`drafts/` 是「在改的版本」。

> **第 3 步是「复制这一个文件」，不是「整棵树同步」。**
> 整树同步会把还没过审的稿子一起带进 `docs/`。

## 五、底稿不进派生

真相只在文档流：文章线的母稿在 `docs/`，视频线的母稿在 `video/`。
草稿箱留的是同一份内容的历史副本，不是第二个产地——
文章线的下游一切从 `docs/` 的母稿重建，视频线的下游一切从 `video/` 的母稿重建。
留底稿是为了看出「当初交上去的是什么、审校改了什么」，不是为了让稿子有两个地方可以改。

**主题也一样。** 主题留在底稿的 `topic:` 字段里，供复盘时看「当初为什么想写这个」。
它不参与派生——下游重建的是母稿，不是主题。

## 六、这个目录里现在有七样东西

六条线各有一份**镜像**，加这份说明。

### 6.1 稿子：还只有这份说明

**因为现存的那些已经是「存量」。**

现存的 560 篇内容单元**没有「未审」标记**——它们是审完之后的样子，
判定不出「哪一篇还需要审」。它们停在 `review → docs` 这道出口上，
**不需要再回到草稿箱走一遍**。

所以这一轮只建目录与约定，**不搬现有文件**
（这条与 `review/specs/2026-11-17-directory-architecture-design.md` 的 D6 一致）。

> 两个常见的错修法：**把草稿箱删掉**（以为它没用）、
> **给 560 篇补 560 份草稿**（以为流程要求有草稿）。
> 两种都是把「存量」误当成「在途」。

真正的稿子会从两处进来：

- **新写的**——按上面「主题 → 草稿」；
- **改了要重发的**——把 `docs/` 里的那一篇拿过来放进 `drafts/` 改，
  改完的稿子留在 `drafts/` 过 review，通过后才覆盖 `docs/` 里那一份
  （`docs/` 那份在 review 通过前仍是上一版的已过审内容）。

两条来路走的是**同一段流程**：`drafts/ → review → docs/`（或 `video/`）。

### 6.2 六条线的镜像

`drafts/` 下现在有六个一级目录，**每一个都是 `docs/` 下同名目录的一份副本**：

| 镜像 | 对应真身 | 是什么 |
| --- | --- | --- |
| `drafts/distributed/` | `docs/distributed/` | 稿子 |
| `drafts/engineering/` | `docs/engineering/` | 稿子 |
| `drafts/life/` | `docs/life/` | 稿子 |
| `drafts/notes/` | `docs/notes/` | 稿子 |
| `drafts/platform-meta/` | `docs/platform-meta/` | 稿子 |
| `drafts/source-tracks/` | `docs/source-tracks/` | **素材** |

**两类东西的同步方式不一样：**

| | 稿子（5 条线） | 素材（`source-tracks/`） |
| --- | --- | --- |
| 是什么 | 待审 / 在改的文章 | 视频生成要读的素材 |
| 谁写 | 文档流 | 文档流 |
| 谁读 | 审校的人 | 视频线 |
| 过不过审 | **过** | **不过**（不是审校对象） |
| 怎么同步 | **逐个文件**复制：review 通过哪一篇就复制哪一篇 | **整树 `rsync`**（素材没有「未审」状态） |

**稿子不能整树同步**——那会把还没过审的稿子一起带进 `docs/`。

素材那一侧的两条 `rsync`（两个方向，除外项相同）见
[`source-tracks/README.md`](source-tracks/README.md)。

**为什么要有副本**：视频线是**另一个模块**，它不认 `docs/`。
让两个模块读同一个目录，就是让它们能同时写同一个文件——
那正是顶层设计要拆掉的耦合。所以**读**的部分复制一份，**写**的部分各写各的。
