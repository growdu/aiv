## 这篇解决什么

三个问题：

1. 客户端要连上 PostgreSQL、并取到一条数据，**需要哪几样东西**；
2. 服务端把「库 → 表 → oid → 文件」这四层怎么串起来；
3. 每一层**怎么自己查出来**——给的都是能复制粘贴跑的命令，不是「你可以在 psql 里看看」。

## 客户端：连上它需要什么

PostgreSQL 是 **C/S 架构**：客户端与服务端分开跑，靠网络通信。

- **客户端**：命令行工具 `psql`，或者别的语言基于 `libpq`、`JDBC`、`ODBC`
  之类驱动写的程序。它们都连到同一个服务端协议上。
- **服务端**：`postmaster` 负责监听 IP 与端口，真正的查询由**后端进程**
  （一个连接一个）执行。

连接建立在 TCP 之上，**SQL 是通信的语言**。SQL 面向结构化数据，所以先得有
数据结构——这就是**表**；为了把表彼此隔开，才有了**数据库**（同一实例里的不同库）。

服务端不会无条件放行：连接要**认证**，最常见的是用户名 + 密码
（`scram-sha-256`、`md5`，也可以用证书或 `peer`）。

所以客户端要取到一条数据，需要凑齐这些：

| 要什么 | 说明 |
| --- | --- |
| 主机、端口 | 服务端在哪 |
| 用户名、密码 | 认证用 |
| 数据库名 | 连到哪个库 |
| 表名、SQL 语句 | 取哪张表的什么 |

## 服务端：库、表、oid 与文件

### 数据库

一个 PostgreSQL 实例里有多个**数据库**，库是表的集合，库名是客户端访问时的标识之一。

每个数据库有自己的 **oid**，实例内不重复。

### 表

结构相同的数据放在一起就是一张表：多行多列。列在建表时定下来，行数随增删改变化。

表最终落在**文件**里。

### 视图：没有存储的那一层

> **这一节是纠错。** 原稿写「视图是表的一部分在内存中的缓存，并不会写入文件」——
> **前半句是错的**：视图不是缓存。

视图存的是**一条查询定义**（`CREATE VIEW` 里那条 `SELECT` 加上规则），
不是数据。每次查视图，PostgreSQL 都按这个定义去查底表。

**视图没有物理存储**——PostgreSQL 17 的源码里，
有存储的关系类型是「表、索引、序列、TOAST、物化视图」，**视图不在其中**
（`pg_class.h` 的 `RELKIND_HAS_STORAGE`）。直接的后果：

```sql
SELECT pg_relation_filepath('student');   -- 表：base/16384/16387
SELECT pg_relation_filepath('v_student');  -- 视图：NULL
```

**要「把结果集存下来」的是物化视图**（`pg_class.relkind = 'm'`）——
那才有自己的文件、自己的 oid。

### oid：对象的身份

- 每个数据库有自己的 oid；
- 每张表（以及索引、序列、物化视图）都有自己的 oid。

**oid 是实例级唯一的**，不是「每个库各有一套」：PostgreSQL 17 的
`GetNewObjectId()` 注释写得很直白——*"OIDs are generated by a cluster-wide counter"*。

还有一个容易混的号：**relfilenumber**（PG 16 及以前叫 `relfilenode`）。
它是**物理文件号**，跟 oid 不是一回事：

| | 是什么 | 会变吗 |
| --- | --- | --- |
| **oid** | 这个对象**是谁**（catalog 里的一行） | 不变 |
| **relfilenumber** | 数据**落在哪个文件** | `TRUNCATE` 会换新的 |

`TRUNCATE` 之后 oid 照旧，`relfilenumber` 换人——
所以 `pg_relation_filepath()` 的结果会变，而 `pg_class.oid` 不会。
（PostgreSQL 17 源码：`ExecuteTruncate()` → `RelationSetNewRelfilenumber()`。）

### 文件

- 每个数据库在 `base/` 下**以自己的 oid 命名一个目录**；
- 每张表在该目录下**以自己的 relfilenumber 命名文件**；
- **单个文件的上限是 1GB**（`RELSEG_SIZE * BLCKSZ`，默认 1GB），
  超了**拆成多个段文件**（`.1`、`.2`……）。

两个容易忽略的：

- **索引不在表的文件里**——索引是独立的关系，有自己的 oid 和文件；
  `pg_relation_size('student')` 只算堆，`pg_total_relation_size('student')`
  才把索引（和 TOAST）算进去。
- **大字段另存**——超长的行会进 TOAST 表，也是独立的关系。

## 三条可复现的命令

### 一张表在磁盘的哪个文件

```console
$ psql -d test
test=# SELECT pg_relation_filepath('student');
 pg_relation_filepath
----------------------
 base/16384/16387
(1 row)
```

返回的是**相对 `$PGDATA` 的路径**（`base/<库 oid>/<relfilenumber>`）。
要在系统上找它，自己拼上 `$PGDATA` 就行。

### 一个数据库的 oid

```console
test=# SELECT oid, datname FROM pg_database WHERE datname = 'test';
  oid  | datname
-------+---------
 16384 | test
(1 row)
```

注意 `datname` 是**大小写敏感**的，库里叫 `Test` 就得写 `'Test'`。

### 一个库里有多少张表

**`\d` 不给这个答案**——它只列**当前 `search_path` 下**能看见的关系，
不是全库的关系（`\d+` 只是把每一项的描述打得更细，`\dt` 才把关系类型限制成表）。

数全库要问 catalog：

```sql
SELECT n.nspname AS schema, c.relname AS table, c.relkind
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm')
  AND n.nspname = 'public'
ORDER BY 1, 2;
```

`relkind` 的取值：`r` 普通表、`m` 物化视图、`v` 视图、`i` 索引、
`S` 序列、`t` TOAST、`p` 分区表。**分区表本身不存数据**——
数据在它的分区里，所以 `relkind = 'p'` 的那些还得往下数一层。

## 收尾：三件最容易搞错的事

1. **视图不是缓存**，是存下来的查询；它没有文件（物化视图才有）。
2. **oid 是实例级唯一的**，而 `relfilenumber` 只是「数据现在在哪个文件」——
   `TRUNCATE` 会换它。
3. **表、索引、TOAST 是三个关系**，三个文件；`pg_relation_size` 只算其中一个。
