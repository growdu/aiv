### 抽帧这件事本身的两条结论

1. **数字对得上。** 画面上 4 张卡 = 口播「它有 4 条做不到的事」= 字幕「这四条短板」；
   5 张卡 = 标题「分五步走」= 口播「分五步走」。数字口径这一关本期通过。
2. **关键帧不能单独用来判断「有没有漏字」。** 段首的关键帧画面本来就是空的
   （19_key_33.750 只有烧录字幕）。关键帧查的是**段边界有没有接错**——
   本期六段的边界都对得上。

## 优先修改

1. 位置：全篇
   - 问题（类别）：表达
   - 建议：补一句**方法论**——这一期的结论是「别发 SQL 文本，发结构化
     对象」。可以落在一句话上：这个结论是从社区讨论里归纳出来的，
     还是从一次失败里逼出来的；换掉哪个假设之后结论变了。
   - 原因：人格规范要求「持续总结方法」的人格透出来（`persona.method`）。
   - 备注：具体改哪一句、改成什么，**待确认**；改的是口播稿，
     要重跑 `align` 与渲染，**改完必须复审成片层**。

2. 位置：s02（`pyv/scenes/s02_raw_sql.py:54-55`）两端芯片里的那段 SQL
   - 问题（类别）：画面
   - 现象：`ALTER TABLE t ADD COLUMN c int;` 的文字宽度与芯片等宽
     （芯片 499 px，文字实测也是 499 px），左右一点留白都没有：文首的「A」
     压住芯片左边框，文末的「;」被右边框切成一半——超出边框的那半画在深蓝底上，
     等于看不见。放大后实际观感接近 `ALTER TABLE t ADD COLUMN c int`，句号丢了。
   - 建议：字号 28 降到 24，或把芯片宽度从 `box_w - w * 0.05`（= 499 px）
     加宽到 560 px 以上，让文本两侧各留 20~30 px。
   - 原因：文字与芯片都是按 `box_w` 居中排的，但芯片宽度扣掉了边距、
     文字宽度没扣，两边撞在一起。
   - 备注：改的是渲染代码，改完要重渲并复审成片层。

3. 位置：s03 / s04 的底部结论句（`pyv/scenes/s03_shortfalls.py:69`、
   `pyv/scenes/s04_ddl_pipeline.py:83`）
   - 问题（类别）：画面
   - 现象：结论句从 t=0 就是满不透明地写着，而它指认的四张卡／五步要陆续
     淡入近 2~3.5 s。s03 有约 3.4 s 画面上写着「这四条短板」却只摆着 1~3 张卡；
     s04 同样。观众先读到结论、再等证据。
   - 建议：给 caption 也加一段淡入（元素全部出现之后 0.2 s 再浮出），
     或把数量类结论句放到最后一句字幕的时段再出。
   - 原因：`text(ctx, p["caption"], …)` 没传 `alpha`，而卡片的 `appear`
     用 `(t - 0.22 - index * 0.11) * 3.0` 逐个淡入。

4. 位置：s03 / s04 卡片里的说明小字
   - 问题（类别）：画面（可读性）
   - 现象：说明小字（「难只复制一部分对象」「schema 改名难对应」「跨版本更难」
     「像远端执行任意命令」「写进日志」「命令 + 对象」「补全 过滤」「写逻辑日志」
     「重建并执行」）用浅青 `#4FD1C5` 压在浅灰 `#F2F5F9` 卡底上，对比度约 1.5:1，
     在 900 宽缩图上已经偏淡。
   - 建议：说明文字改成 `COLORS["primary"]`（深蓝）或一个中灰（如 `#5A6B85`），
     保证对比度 ≥ 4.5:1。
   - 原因：`pyv/palette.py` 里 `secondary = "#4FD1C5"`，s03/s04 都用它画说明行。

5. 位置：s04 的五步卡片
   - 问题（类别）：画面
   - 现象：底部结论句写「中间那一步 deparse，做的事最多」，但画面上五张卡片
     版式完全相同——deparse 没有更深的底色、更粗的边框、更大的字号或额外高亮，
     观众无从判断「哪一步最多」。同时第 3 步的说明只有「补全 过滤」两个词，
     看不出补全的是什么、过滤的是什么（这两项只出现在同时刻的烧录字幕
     「补全名字 过滤未发布表」里）。
   - 建议：给第 3 步卡片加深底色／加粗边框或加一个「最多」标记；
     说明改成能独立成立的一句话（例如「补全名字 · 过滤未发布表」）。
   - 原因：模块 docstring 里说的「中间那一步画得最深」在代码里没有对应实现；
     说明文案取自契约 `["deparse", "补全 过滤"]`。

6. 位置：s02 的中间箭头、s04 的步骤间箭头
   - 问题（类别）：画面（视觉过渡）
   - 现象：s02 段第一帧就画出中间那条带文案的橙色箭头，而两端盒子要
     0.08/0.26 之后才淡入，出现约半秒「箭头悬空、指向不存在的两端」；
     s04 第 4 步淡入时，它右侧的箭头已经画出来，指向还没出现的第 5 步。
   - 建议：s02 的箭头与其文字一起用两端盒子的 `appear` 做淡入；
     s04 的箭头改用「下一步」的 `appear`（而不是上一步的）来控制显隐。
   - 原因：`s02_raw_sql.py` 的 `arrow()`/`text()` 没传 `alpha`；
     `s04_ddl_pipeline.py` 用当前步的 `appear` 画了通往下一步的箭头。

7. 位置：s05 的例图与收益卡措辞
   - 问题（类别）：画面（可读性）
   - 现象：画面举的例子是「表名 users → app_users」，而收益卡里写的是
     「schema 改名能对应」——举的是表名，说的却是 schema 改名，两者层级不同，
     观众可能误以为「schema 改名」=「改表名」。
   - 建议：要么把例子改成 schema 级的框（如 `public` → `app`），
     要么把卡片措辞改成与例图一致的「对象改名能对应」。
   - 原因：契约 `s05` 的 `source_value/target_value` 是 `users`/`app_users`，
     而 `benefits[1]` 是「schema 改名能对应」。

8. 位置：`aiv/字幕-结构化DDL.md` 第三节「分段时间轴」表格
   - 问题（类别）：文档
   - 现象：表格里 s03 的 renderer 写的是 `s03_structured`，而契约与故事板
     实际用的是 `s03_shortfalls`。
   - 建议：把文档里的 renderer 名改成 `s03_shortfalls`。
   - 原因：文档与 `contracts/structured-ddl.json` 不一致。

## 已确认的改动

- 审核机制：`pyv/review.py` 每个视觉段抽 2 帧（段中点 + 段尾 85%），
  段尾帧是「结论淡入完之后」的样子；清单的「应有文案」改成递归摊平
  契约 `params`（含嵌套列表）。理由与证据见「抽帧判断」的两条结论。
- 审核机制：VV-01、VV-02 不再判品牌片头/片尾的帧（共享素材，
  片头黑场是淡入，不是漏画），报告里留 note 说明跳过了几帧。
- 审核机制：抽帧的**段归属按成片的帧网格算**，不按时间轴上的名义秒。
  新增 `_scene_spans()`（按帧算每段在成片里的真实区间）、`_snap_to_frame()`
  （把时间码吸附到帧网格，ffprobe 的关键帧时间只到 6 位小数，差最后一位就判错段）。
  两条新测试钉住它，其中两条是注入缺陷验证：改回名义秒，两条就红。
