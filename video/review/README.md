# 视频审核（review）

这里存放对 `video/` 视频生产线的审校任务、修改建议与复盘记录。

目标不是把片子做得更华丽，而是让它**像一位有经验的工程师在清楚地讲一件事**：
具体、自然、有判断，同时保住技术准确性与作者自己的口径。

文档侧有一套同构的审校机制（仓库根的 `review/`）。本文是它在视频侧的对应物，
**不是它的复制**：视频的「AI 味」来源与文档不同（见 §2）。

**审的是哪一份**：口播稿与母稿先落 `drafts/`（新增与改动都在那儿做），
文本层审的就是 `drafts/` 里那一份，审过才进 `video/`；
成片层审的是成片本身（`video/out/<slug>.mp4`），那一步在改稿、重出片之后。
（顶层设计 D11，见 `review/specs/2026-11-18-顶层设计与目录调整.md`。）

---

## 1. 审校原则

1. **先保真，再润色。** 不改技术结论、数据、引用、机制描述与作者立场；
   拿不准的事实标为待核实，不靠改写补全。
2. **按观众的接收路径组织。** 观众先听结论，再听机制，再听证据——
   口播稿的句子顺序就是成片的段落顺序，顺序错了片子就散了。
3. **让抽象话落地。** 优先用具体对象、条件、行为和结果，少用空泛评价。
4. **保留人的声音。** 保留有价值的经验、犹豫、取舍与失败案例；
   不把每期口播统一改成模板腔。
5. **小步可审。** 一期一条记录，建议逐条确认、可回滚。
6. **用证据建立技术感。** 技术感来自源码、实验、日志、指标、版本差异与取舍，
   不来自堆术语和把简单问题说复杂。
7. **画面必须配得上口播。** 观众看的和听到的必须是同一件事；
   画面上的数字与口播里的数字对不上，比写错一个数字更糟。

## 2. 视频的「AI 味」从哪来

文档的 AI 味主要在**文字腔调**上。视频不一样：

| 来源 | 能不能改 | 怎么审 |
| --- | --- | --- |
| **旁白的声音** | 改不了 | 旁白本来就是 TTS 合成的，合成音的「机器感」是既定事实，不是缺陷。**不审声音的质感** |
| **口播的腔调** | 能改 | 连接词堆砌、空泛评价、模板化的收尾 → 文本层 |
| **画面的腔调** | 能改 | 十段长得一样、字都是同一套排版、每段都是「标题 + 框」 → 成片层（看帧） |
| **讲稿的骨架** | 能改 | 「首先讲原理，然后讲配置，最后讲案例」——三段话讲一个观点 → 文本层 |

**所以视频审核的重点不在声音，在文案与画面的关系。**

## 3. 两层审核

### 3.1 文本层（`VT-*`）

审**成片背后的文本**：口播稿（`video/episodes/<slug>/口播稿.md` 的「口播稿」节）、
字幕表（同文件「字幕文本」节）、画面契约（`video/episodes/<slug>/contract.json` 的 `params`）、
母稿与数字出处（`video/选题库.md` 的「关联文档」与「数字与出处」）。

| 编号 | 判据 | 严重级 |
| --- | --- | --- |
| `VT-01` | 句首以连接词开头的句占比 > 15% | warn |
| `VT-02` | 空泛评价出现在句中，且该句无数字 | warn |
| `VT-03` | 结尾三句出现泛化收尾语 | warn |
| `VT-04` | 近似重复句（difflib ≥ 0.85） | warn |
| `VT-05` | 口播里的数字在母稿与出处表里找不到 | warn |
| `VT-06` | 口播句里的数字在对应字幕里丢了 | warn |
| `VT-07` | 源字幕表里有禁止词，或单行视觉宽度超限 | error |

`VT-01`~`VT-04` 与文档侧的 `AIF-01`/`AIF-02`/`AIF-04`/`AIF-05` **一一对应、口径相同**，
词表与阈值是同一份字面量，一致性由 `video/pipeline/tests/test_review.py` 钉住。

`VT-05` 与 `VT-06` 是视频独有的两条：

- `VT-05` 管的是**数字的出处**。短片里一个错数字，35 秒就过去了；
  长版 18 分钟里混进一个假数字，没人会发现。
- `VT-06` 管的是**口播与字幕的一致**。口播说了「提升 2 到 5 倍」，
  字幕写成「性能提升明显」——数字在字幕这一层丢了，观众看到的就是一句空话。

`VT-07` 查的是**源字幕表**（`video/episodes/<slug>/口播稿.md` 的「字幕文本」节），
不是 storyboard：`make validate` 查的是上一次 `align` 出来的 storyboard，
源文件改了但还没重跑 `align` 时，那个门禁看到的还是旧字幕。
阈值与禁止词来自 `pyv/timeline.py`（唯一一份），审核层不另抄。

### 3.1.1 为什么只搬了文档侧的四条

文档侧检查器还有 `STR-*`（结构）、`MET-*`（元信息）、`DEP-*`（深度）三组，
**都不搬**。它们判的是文章形态：开头 5 段有没有说明问题、结尾有没有可带走的
产物、有没有「编写人 / 编写内容 / 编写时间」信息表——短视频里没有这些形态。

在口播稿上试过（`python tools/review-check.py video/episodes/<slug>/口播稿.md`）：
搬过来的四条确实一条都不用报；而 `STR-02`「开头 5 段没有说明文章解决什么问题」、
`STR-03`「结尾没有可带走的产物」、`MET-01`「缺少编写人信息表」**条条都报**——全是误报。

**能搬的是「话怎么说的」，不能搬的是「文怎么组织的」。**

### 3.2 成片层（`VV-*`）

审**成片本身**（`video/out/<slug>.mp4`）：抽帧看画面，查音轨，查技术参数。

| 编号 | 判据 | 严重级 |
| --- | --- | --- |
| `VV-01` | 抽到的帧近乎纯色 → 画面漏画或黑场 | warn |
| `VV-02` | 帧的底部字幕带里没有暗色像素 → 字幕没烧上 | warn |
| `VV-03` | 正文区间里旁白中间静音 > 1.0 s | warn |
| `VV-04` | 成片时长与时间轴对不上（差 > 0.15 s） | error |
| `VV-05` | 关键帧最大间隔超限 | warn |
| `VV-06` | 混音电平不合格 | warn |
| `VV-07` | 平台技术门槛不合格 | error |

`VV-05`~`VV-07` **不重写**，直接调 `preflight.py` 与 `bgm.py` 里已有的判定。

两条成片层的口径，说清楚为什么：

- **`VV-01`/`VV-02` 不判品牌片头/片尾的帧**。品牌片是共享素材（`video/brand/clips/`
  下的固定片子），片头第一帧的黑场是淡入，不是漏画——每期都报一条假警，
  等于把规则变成噪声。跳过了几帧，报告里写明。
- **`VV-03` 的阈值是量出来的**。语料里的句间间隙落在自然分布的一段区间里，
  0.6 s 卡在尾巴上，会把约两成的正常换气报成「静音」；1.0 s 远小于一句口播的
  中位时长，只会在「少了一句」的时候响。阈值不许再往下压；
  `tests/test_review.py` 里有一条测试会重新量一遍语料，阈值漂了就红。
  （语料清空之后阈值要**重新量一遍**：以新语料量出来的分布为准，
  别拿旧分布当依据。）

### 3.3 抽帧看画面

机械信号查不出「这张图讲清楚了没有」。所以每个视觉段抽 **2 帧**
（段中点 + 段尾 85%）加**每个关键帧**，生成一份清单：时间码、视觉段、
**这段应该出现什么**（从契约 `params` 递归摊平出来的文案）、对应口播、帧文件。

**为什么抽两帧**：各场景的结论都在段内 48%~84% 之间淡入，段中点正好卡在
动画中间——只抽中点，审核会把「动画中间态」当成「漏字」。实测 `s02`：
段中点上结论框已经画出来了，框里的字还没显影；到段尾才完整。
段尾帧是「结论淡完之后」的样子。

**「应有文案」要递归摊平**：`s03.modes` 是 `[["KEY SHARE", "FOR KEY SHARE"], …]`，
`s05.bit_labels` 同理。只取顶层字符串，清单会漏掉一半以上该有的字——
而那正是画面上最多、最该逐字核对的一批。

**段的归属按成片的帧网格算，不按时间轴上的名义秒**：时间轴上的段边界是
浮点秒，成片却是按帧拼起来的（每段 `round(duration * fps)` 帧），
真实切点比名义值早最多一帧（24fps 下 42 ms）且逐段累积；而编码器切出来的
关键帧**常常正好落在真实切点上**。按名义秒归属，画面上已经是下一段、
归属却记成上一段，抽帧清单就会拿「下一段的画面」去核对「上一段的文案」——
一整片假漏字。实测这样错判的关键帧不止一处。实现见 `pyv/review.py` 的
`_scene_spans()`（按帧算真实区间）与 `_snap_to_frame()`（把时间码吸附到帧网格：
ffprobe 的关键帧时间只到 6 位小数，差最后一位就判错段）。

人（或 Agent）对着清单逐帧看，回答三个问题：

1. 画面上**有没有**该有的字；
2. 字**对不对**；
3. 这一帧**讲不讲得清**。

抽帧的已知局限（写在规范里，别把它当成「成片没问题」的证明）：

- 抽帧看不全动效中间态（段首的关键帧往往只有标题，甚至全空）；
- `VV-02` 在画面底部本来就有深色内容时会漏报；
- 抽帧不看音画对位（谁的声音配哪张图）。

## 4. 每期的审核流程

1. 确认 slug 与期号、口播稿、契约与成片是同一期的（slug 对不上当场报错，不猜）。
2. 跑文本层：机器出信号，信号进记录。
3. 跑成片层：机器出信号，信号进记录；**产物缺失时写明跳过什么**，不假装绿。
4. 抽帧，逐帧看，把判断写进记录（画面对不对、讲不讲得清）。
5. 复核：技术事实、机制描述、数字、作者口径均未被误改。
6. 列改稿 / 改代码的建议，逐条可确认。
7. 确认后才改；改完**重出片并复审成片层**——改稿会改到画面。

**改稿会改到画面**：口播稿改了，契约的句子覆盖关系可能变，`align` 要重算时间轴，
片段要重渲。只审文本不审成片，等于审了一份没出片的稿子。

## 5. 审核记录模板

`video/episodes/<slug>/review.md`，一期一条：

```md
# 审核：<期号> <标题>

- slug：
- 期号：
- 口播稿：
- 契约：
- 成片：
- 状态：待审 / 已出信号 / 已看帧 / 建议中 / 已确认 / 已合入

## 机器信号

| 层 | 编号 | 严重级 | 位置 | 摘录 | 说明 |
| --- | --- | --- | --- | --- | --- |

## 抽帧判断

| 帧 | 时间码 | 视觉段 | 应有文案 | 画面有没有 | 对不对 | 讲不讲得清 |
| --- | --- | --- | --- | --- | --- | --- |

## 优先修改

1. 位置：
   - 状态：
   - 问题（类别）：
   - 建议：
   - 原因：

## 事实待核

- 

## 已确认的改动

- 
```

### 「状态」怎么写

「优先修改」每一条带一个状态，机器从这一行解析：

| 标记 | 含义 |
| --- | --- |
| `- 状态：待改` | 还没动手 |
| `- 状态：已改` | 改完了，**成片还没重出、还没复审** |
| `- 状态：已合入` | 改完、重出片、复审通过 |

**「已改」不等于「已合入」。** 画面改了要重渲成片、重新抽帧、重新看一遍；
没走过这一轮的，状态就停在「已改」。

### 「问题（类别）」怎么写

每条建议的**问题**一行以类别开头。类别固定这五个：

| 类别 | 指的是 |
| --- | --- |
| 结构 | 口播顺序、段落划分，该拆该合 |
| 表达 | 句子、术语、语气、AI 味 |
| 事实 | 数据、版本、机制、引用 |
| 画面 | 漏字、文案不符、版式重复、讲不清 |
| 可读性 | 有没有意思、观众能不能跟上 |

### 「事实待核」怎么写

三种标记之一，机器从这三行解析：

| 标记 | 含义 | 阻塞「已合入」 |
| --- | --- | --- |
| `- [x] 事实` | 已核实，依据写在条目里 | 否 |
| `- [不适用] 事实` | 本次没改到，原文保留 | 否 |
| `- 事实` | 还没销掉 | **是** |

## 6. 进度表

`video/review/INDEX.md`，一行一期：期号、标题、状态、文本层信号数、成片层信号数、
待确认项、批次。**只维护一份**，不另设队列文件。

**信号为 0 不等于这期没问题**——机械信号干净的一期照样可能需要改。
信号是「值得看一眼的地方」，不是「问题清单」。

## 7. 边界

- `video/review/` 只记录审核过程与结论，**不是对外发布内容**，不进 `docs/`，
  也不进发布白名单（与文档侧 `review/` 同一条纪律）。
- 抽帧（PNG）是产物，不入库（`video/.gitignore` 已拦 `frames/`）；入库的是清单与结论。
- 机器信号只出位置与判据，**不下结论**；「是不是空泛」「讲不讲得清」由人和 Agent 判断。
- 涉及数字、版本、机制的修改必须可回溯到母稿或公开出处。
- 不为「去 AI 味」而删除必要的定义、前提、警告或机制细节。
