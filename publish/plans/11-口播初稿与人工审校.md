# 口播初稿生成器实施计划（计划三）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **状态（2026-11-23 开题）**：本计划 32 个步骤 —— 完成 **0** · 作废 **0** · 待做 **32**。
> `- [x]` = 落地了且能验证（行尾注明怎么验的）；`- [-]` = 没落地但已被后来的决定作废（行尾给原因）；
> `- [ ]` = 没落地且现在还该做。

**Goal:** 让「口播稿从哪来」这件事有个机器可跑的答案——母稿 + role 骨架进，
LLM 出一版**初稿**，机器兜底四条全绿，人审校之后才进期目录。

**Architecture:** 在 `pyv/` 下面加两层——一层是 LLM 调用的一层薄封装
（`pyv/llm.py`，走仓库里已经在用的 `mcode-tools` CLI），一层是生成器
（`pyv/narration.py`：读骨架 + 母稿 → 逐段组装 prompt → 调 LLM → 解析 →
过机器兜底 → 落 `drafts/`）。骨架的**形状一个字都不改**：`narration[]` 与
`subtitles[]` 填进去之后，`pyv/derive.py` 就能照旧裁出三档。

**Tech Stack:** Python 3.11、PyYAML（已在用）、`mcode-tools` CLI（仓库里
voice 合成与形象生成都在用）、pytest。**不引入新的第三方依赖**。

**上游规格：** [../spec/09-长视频三档.md](../spec/09-长视频三档.md) §七
（口播生成器）与 §十（实施顺序，批次 4）。

## 本计划的范围

| 做 | 不做 | 为什么 |
| --- | --- | --- |
| LLM 出**初稿** + 机器兜底四条 | 自动写进期目录 | 初稿要人审校（规格 §7.2）；机器绿 ≠ 可发布 |
| 数字出处的**逐句**核对 | 抽样核对 | 规格 §7.3：52 分钟的片子混进一个假数字，没人看得出来 |
| prompt 组装，参数逐字节可复现 | 让模型自己找母稿 | 模型会编事实；喂进去的母稿片段必须来自原文 |
| 一段一次调用 | 整篇一次调用 | 完整版 600 段；一次调用分不清哪句是谁写的 |
| 坏输出当场报错，**原始输出留档** | 重试到合格为止 | 重试会把「模型写不出来」掩盖成「跑得挺顺」 |

## Global Constraints

- **每个 commit 完成立即提交**；每个 commit 必须配套**单元测试 + 集成测试**，
  且在**只含该 commit 内容的干净检出**上独立跑通全部测试。
- **入库的是事实，不入库的是产物。** LLM 的原始输出、草稿骨架、检查报告：
  草稿与报告入库（草稿层就是放这个的），原始响应只进报告。
- **不静默成功、不静默截断。** LLM 返回坏形状 → 当场报错并把原始输出留档；
  句子少了不许拿剩下的凑；重试有上限，超了就报错。
- **阈值独立取值。** 守卫里的阈值写成**字面量**，不许 `from pyv.xxx import CONSTANT`；
  一致性由另一条测试单独钉住。
- **改完守卫要注入缺陷验它会红。**
- **层间零 import。** 视频线不许 import 平台层（`platforms/*`）的代码。
- **测试不依赖网络。** LLM 一律用假 runner 顶替。
- **改动稿先落 `drafts/`。** LLM 的产出是改动稿——先落草稿箱，人审校之后
  才允许写进期目录里的骨架。
- **中文 commit message 不用 bash heredoc。** 写 `/tmp/msg*.txt`，再 `git commit -F`；
  提交后按码位查 `U+FFFD`。

## 关键口径（先定，再写代码）

### D1：LLM 走 `mcode-tools` CLI，不引第三方依赖

规格 §1.2 写死「LLM 走仓库里已经在用的 `mcode-tools` CLI」。
`video/voice/scripts/synthesize_narration.py` 与 `video/character/scripts/_mcode.py`
都走这条路——本计划复用同一套调用形状（`connector call <tool> --args-file`），
**不引入 SDK、不引入 HTTP 客户端**。

**测试不许联网**：LLM 调用的一层必须能注入假 runner。

### D2：初稿落 `drafts/`，过审才进期目录

仓库总规矩：改动稿先落草稿箱。LLM 出的口播稿是**改动稿**——
它要改的是期目录里那份骨架。所以：

- 生成器写 `drafts/video/<文档路径>/<档位>-口播初稿.yaml`；
- 机器兜底报告写 `drafts/video/<文档路径>/<档位>-口播初稿.check.md`；
- **生成器不许直接改期目录里的骨架**——人审校之后由人（或另一条命令）覆盖。

### D3：机器兜底四条必须全绿

规格 §7.1 的兜底清单，落到本计划是四条检查：

1. **人格 9 条**（`pyv/persona.py` 的 `check_sentences`）；
2. **字幕视觉宽度 ≤ 14**（`pyv/timeline.py` 的 `display_width`）；
3. **句数与骨架一致**（口播句数 = 字幕行数，且不为空）；
4. **数字出处**（本计划新增，见 D4）。

**机器全绿不等于可以发布**——人审校在流程外（规格 §十 批次 4 写明）。
机器兜底的作用是：**别让人审校去当打字机**。

### D4：数字出处逐句核对，不抽样

规格 §7.3：口播里的每个数字都要能在母稿里找到出处。
母稿里的数字串（含小数、千分位、百分比）逐句比对；对不上的**报出是哪一句、哪个数**。
抽样等于没查——一条假数字落在没抽到的那句里，就直接进片子了。

### D5：一段一次调用，参数逐字节可复现

长版 600 段 → 600 次调用。合并成一次的话，出问题时分不清是哪句的锅，
而且一次输出几百句，模型自己也会漏。

**同一份骨架跑两次，喂给 LLM 的参数必须逐字节一致**——否则没法复现，
也没法审。

### D6：不静默

LLM 返回不是 JSON / 句数对不上 / 字段多了少了 → **当场报错**，
并把**原始输出原样留档**在报告里（人要看的就是原文）。
不写坏骨架：不校验通过就不落盘。

### D7：喂进去的母稿片段必须来自原文

prompt 里的母稿内容是**从母稿里摘出来的原文**，不是模型「回忆」出来的。
数字出处检查（D4）是这条的兜底：模型编的数字，母稿里找不到。

## 完成标准

1. `python3 -m pyv.cli narration draft --skeleton <骨架> --out <drafts 路径>` 能出一版初稿；
2. `python3 -m pyv.cli narration check --draft <初稿>` 四条兜底全绿时退出码 0，有问题时非 0 并说清是哪一条；
3. 数字出处是**逐句**核对的，且验过「LLM 编数字」会红；
4. 初稿落在 `drafts/`，期目录里的骨架**一个字都没被改**；
5. 全程不联网也能跑完测试（假 runner）。

## 遗留（本计划不做）

- **提示词调优**：讲得像不像人，要人试；本计划只保证「形状对、兜底全绿」。
- **长版的调用耗时与限流**：完整版 600 段就是 600 次调用，量一下要多久、
  会不会撞限流（P0 阶段的实测项）。
- **TTS 合成时间**：最长 22,403 字的完整版，合成要多久、要不要分块
  （规格 §九 的风险表里列着）。
- **选题库与长版的衔接**：《选题库》那套检查是按 10 句短稿写的，
  长版的口播骨架要不要也进库，是另一个决定。
