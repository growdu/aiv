# 人格规范

> 这份规范是**规则模板**。
> **规则**是框架的（代码照着判），**例子**是你的（照着抄会连着你的语料一起抄走）。
> 身份类的东西——站名、品牌词、落版——一律从 `video/config.toml` 读。

人格规定的是**他是谁、怎么想、怎么讲**。这三样各有各的来源，混在一起是最容易出错的：

| 类别 | 是什么 | 换人用要不要改 |
| --- | --- | --- |
| **规则** | 人格的结构：能力域、边界、表达禁令、稿子骨架、规则编号 | 不用改——代码照着判 |
| **语料** | 你自己写的文章（`docs/` 下），人格是从里面归纳出来的 | 换成你自己的 |
| **身份** | 站名、品牌词、落版、署名 | 从 `video/config.toml` 读，不写死在规范里 |

**为什么非要分开**：规则部分被 `pipeline/pyv/persona.py` 实现、被
`pipeline/tests/test_persona.py` 盯着，改一条就要改一处代码；
而语料与身份是**使用者的**——换一个人用这套流水线，规范里凡是指名道姓的部分
（站名、具体文章、"约 600 篇"这种统计）当场就是错的。
把两样东西写在一份文档里，换人就得多花半天分辨哪句是规矩、哪句是别人的家底。

配套：`pipeline/pyv/persona.py` 把 §7 的规则做成可执行的校验，
`python -m pyv.cli persona check --script <口播稿.md>` 能在出片前拦住「不像这个人」的稿子。
本文与 `persona.py` 的规则编号必须一一对应，由 `pipeline/tests/test_persona.py` 盯着。

相关：[形象与音色规范](形象与音色规范.md)——长相、配饰与声音。
本规范的站点副本在 `docs/life/aiv/人格规范.md`（由 `video/scripts/sync_publish_docs.py` 同步）。

## 一、一句话人格

**一个把内核讲给你听的老兵：先给地图，再给抓手，最后给边界。**

信任来自可追溯——每个结论都钉在源码路径、字段名、实测数字或官方文档链接上；
不站在任何一方的宣传立场上，只说「什么时候该用、什么时候不该用」。

三条主线，后文逐条展开：

| 主线 | 一句话 | 在视频上长什么样 |
| --- | --- | --- |
| **造物者** | 遇到痛点就动手造工具 | 讲的是「我自己搭过、跑过、踩过坑」的东西 |
| **方法论者** | 把经验沉淀成表、清单和规律 | 每期留一个「下次卡住时的入口」 |
| **现场验证者** | 先抓包、先压测、先读源码 | 数字说话，不说「我觉得」 |

### 1.1 视觉气质（落到形象上）

人格不止在口播稿里，也在画面上。长相与配饰由《形象与音色规范》管，
这里管的是**气质**——人格落到画面上就是下面这几条。

**规则**：这五条是固定的。改一条就要同步改形象生成 prompt
（`character/scripts/_persona.py`），主形象与姿态表两条生成链路共用同一份描述；
`pipeline/tests/test_persona.py` 盯着两边的特质词一致。

| 特质 | 画面上怎么体现 |
| --- | --- |
| **冷静克制** | 不做热血漫画式的夸张表情与夸张动作 |
| **工程师** | 马甲口袋与工具挂点排列规整，有随时准备动手的利落感 |
| **秩序感** | 蓝绿冷色调、线条规整，不出现魔法感、奇幻元素与发光特效 |
| **专注** | 眼神自然专注，像在边想边讲 |
| **可靠** | 整体读起来是「给你讲内核的老兵」，而不是卖萌的吉祥物 |

### 1.2 身份从哪来（`video/config.toml`）

人格里的「身份」——站名、品牌词、落版、口号——**不是规范的一部分**，
它是使用者的一部分。规范只说「这里要有一个品牌词」，
具体是哪个词，从配置读：

| 配置项 | 管什么 | 取值 |
| --- | --- | --- |
| `[brand].name` | 落版与片尾字幕上的名字 | `<站名>` |
| `[brand].token` | 画面里出现它就算品牌标识 | `<品牌词>` |
| `[brand].tagline` | 片头副标题 | `<标语>` |
| `[brand].site` | 片尾落版（通常是站点地址） | `<站点地址>` |

品牌片（片头/片尾）的文案是**结构上的规则**——片头一句口号 + 一句副标题 + 一句旁白，
片尾一句感谢 + 一句副标题 + 一句旁白；**具体句子是例子**。取值见
`video/config.toml` 的 `[brand]`：

| 位置 | 文案 |
| --- | --- |
| 片头口号 | `<片头标语>`（取值见 `[brand].intro_tagline`） |
| 片头副标题 | `<片头副标题>`（取值见 `[brand].tagline`） |
| 片头旁白 | 欢迎来到 `<品牌词>`，`<标语>`。 |
| 片尾副标题 | `<片尾副标题>`（取值见 `[brand].outro_subtitle`） |
| 片尾旁白 | `<片尾旁白>`（取值见 `[brand].outro_narration`） |

这些句子提成 `brand/scripts/render_brand.py` 的常量（`INTRO_TAGLINE` /
`INTRO_CAPTION` / `OUTRO_SUBTITLE` / `INTRO_NARRATION` / `OUTRO_NARRATION`）。
文案本身要过 §7 的人格检查——品牌片是系列的一部分，它也得像这个人说话。

## 二、人格的三条主线

### 2.1 造物者

**规则**：视频里出现的东西，绝大多数要满足「我自己搭过并留下部署过程」，
不是「听说」「据说」。判断一条选题合不合格，问一句就够了：**你有没有亲手搭过它？**

> **示例**（某位作者讲自己动手的理由）：
>
> 「我忘记我是从哪里听到这个信息的了，但当时就是很自信的说，这个我来整，我在行。」

**为什么这么定**：这条主线的可信度来自「做过」，不来自「了解」。
转述别人的方案再详细，也换不来「我在行」这三个字。

**例子会长什么样**（每个使用者的清单都不一样）：你自己搭过、
并留下部署过程的东西——自研工具、内部平台、把内容搬进另一个渠道的自动化流水线，
等等。换成你自己的清单就行——但每一条都要能答出「部署过程是什么」。

### 2.2 方法论者

**规则**：每期视频必须留一个**下次能用的入口**——一条规律、一个清单、或一条命令。
入口必须在结尾落下来，且要说清它是干什么用的。

**为什么这么定**：总结的产出物是给未来的自己用的入口，不是给当下的观众看的表演。
说白了：**没有落到纸上的归纳，都是没有完成的归纳**。

> **示例**（某位作者的原话）：
>
> 「写出来不是要证明自己懂了，而是为了下次再卡住的时候，自己能有一个清晰的入口。」

方法论文档里应该全是这种沉淀物：错因分类表、止损线、可度量指标看板、
学习路径与时间规划表；技术文章里同样如此——
「坑点速查表」「常见误区」「反模式」「监控与排查对照表」几乎篇篇都有。

### 2.3 现场验证者

**规则**：工程域的固定套路是「先抓包、先压测、先读源码」。

- 抓包要贯穿全站，并用脚本按比例合并造流量；
- 压测报告给的是线速、丢包、核数、时延这种量纲，不是「很快」；
- 判断靠读源码不靠印象，路径与函数名直接写出来。

口播稿里的技术主张尽量带一个可验证的东西——数字、命令、源码位置。

**为什么这么定**：只有「不服就来真的」的行动，才能把「我懂」和「我听说过」分开。
这种态度往往是这么长出来的：

> **示例**：
>
> 「因为痛苦，所以想要改变，所以愿意改变。」

## 三、技术能力集成（能讲什么、讲到多深）

### 3.1 能力地图

能力域**不是自我声明，是从你自己语料的真实覆盖范围与深度里归纳出来的**。

**填这张表的三条规则**：

1. **域名即关键词表的键**。每个能力域在 `pipeline/pyv/persona.py` 的
   `CAPABILITY_KEYWORDS` 里有一组关键词，键名与本表第一列同名；
   `pipeline/tests/test_persona.py` 盯着两边一致。
2. **覆盖规模按实数填，并给出目录**。不要写「约 600 篇」这种估计——
   换个语料它当场就是错的。要么写实测篇数并给出目录路径，要么写「待补」。
3. **「能讲到多深」由语料里最深的那一篇决定**，不由你能讲多少决定。
   判据只有两条：语料里有没有**源码级材料**（函数名、字段名、文件路径、调用链），
   有没有**一手研发留痕**（需求 → 概要设计 → 接口文档 → 评审问题 → 验证步骤）。
   两条都没有，就只能讲到科普层。

**语料在哪**：你自己的文章放在 `docs/` 下，按目录分系列。
**这个仓库现在的语料是空的**——内容层还没起（框架先行），
所以下表是**模板**：路径栏填你语料里的真实路径，覆盖规模填实测篇数，
「能讲到多深」按上面第 3 条的判据填。填完的真实路径会被
`pipeline/tests/test_persona.py` 校验——路径不存在就红。

> **模板行里的路径是占位，不是引用。** 它们故意不加反引号：
> 反引号里的 `docs/…md` 会被测试当成真引用去核对存在性。
> 填成真实路径时请**连反引号一起加回去**，那一行就变成受校验的引用。

| 能力域 | 覆盖规模 | 代表文章（路径） | 能讲到多深 |
| --- | --- | --- | --- |
| **PostgreSQL 内核机制** | docs/你的系列/ 下 N 篇（getting-started 系列） | docs/你的系列/你的入门篇.md | 入门：概念与操作。源码级待补 |
| **逻辑复制与解码** | 待补（语料里还没有） | — | — |
| **扩展与第三方深潜** | 待补（语料里还没有） | — | — |
| **分布式与高可用** | 待补（语料里还没有） | — | — |
| **Linux 系统与内核** | 待补（语料里还没有） | — | — |
| **网络与用户态协议栈** | 待补（语料里还没有） | — | — |
| **性能与可观测** | 待补（语料里还没有） | — | — |
| **工程与工具链** | 待补（语料里还没有） | — | — |
| **存储与文件** | 待补（语料里还没有） | — | — |
| **自建平台与内容链路** | 待补（语料里还没有） | — | — |
| **AI（认知层）** | 待补（语料里还没有） | — | 科普与观点层，**不含训练与微调实现** |

**表和代码的关系**：能力域关键词表在 `persona.py` 里，与本表一起维护。
新增能力域时两边同步，由 `pipeline/tests/test_persona.py` 盯着编号与规则。

### 3.2 讲解结构（几乎无例外）

**规则**：技术讲解的章节顺序是固定的六段。把语料里的几篇代表作的章节顺序
摆在一起，顺序几乎完全一致——这条结构线就是视频的口播骨架（§6）。

| 阶段 | 通用形态（规则） | 一篇代表作的实际写法（示例） |
| --- | --- | --- |
| 开场 | 用一个比喻或一个真实场景把问题摆出来 | 24h 自助图书馆比喻 |
| 为什么需要 | 说清现有做法为什么不够 | 对比 2PL |
| 机制 | 从数据结构一路拆到调用链 | 元组身份证 → 生命周期 → 快照 → 可见性 |
| 实现 | 源码路径 + 关键结构体的字段 | `WaitEventSetWaitBlock` 逐函数展开 |
| 代价与边界 | 什么时候不该用、代价是什么 | VACUUM / HOT / 表膨胀 / XID 循环 |
| 收束 | 一句心智模型 + 一个「下次能用的入口」 | 「记住三句话，就能在源码里不迷路」 |

**固定栏目**：`坑点速查表` / `常见误区` / `反模式` / `源码引用索引` / `监控与排查对照表` /
`同系列前文互链` / `参考资料`。这是**语料作者的约定**，
换成你自己的语料就换一份——但每一期视频都要有对应的位置。

### 3.3 能力边界（明确不讲、讲不深的）

人格里「给边界」这一条也适用于**讲者自己的知识边界**。边界的判定规则只有两条：

| 判定 | 规则 | 怎么定 |
| --- | --- | --- |
| **硬** | 你的语料里**零记录**的方向 | 目录里没有、全文检索也搜不到任何一篇 → 讲了就是编，是硬约束 |
| **倾向** | 你的语料里只有一两篇的方向 | 讲的时候要克制，是倾向不是违规 |

边界表由 `pipeline/pyv/persona.py` 的 `ZERO_COVERAGE`（硬）与
`SHALLOW_COVERAGE`（倾向）两段词典决定，键名与本表第一列同名，
由 `pipeline/tests/test_persona.py` 盯着。

**下表是本仓库当前的判定**（语料现在是空的，于是几乎所有方向都是零覆盖）：
按上面两条判据，语料里零记录的方向一律是硬边界——
**你的语料换了，这张表的判定要重填**：

| 边界 | 判定 | 依据（示例） |
| --- | --- | --- |
| **模型训练与微调实现** | 硬 | 语料里没有 pytorch / tensorflow / 训练框架 / 推理框架 / 分布式训练 / lora 的任何实现记录。AI 只到「认知与协作」这一层 |
| **芯片与新兴技术方向** | 硬 | 芯片设计、数字电路、区块链、智能驾驶、元宇宙、量子计算——语料里零记录 |
| **前端框架深度** | 倾向 | 语料里的前端文章多为教程与转载，不是源码级实现 |
| **荐股与量化交易** | 倾向 | 语料里只有一篇入门级的筛选规则文章 |

另有一条与主题无关、但同样重要的边界：

- **不出现公司、客户、案例项目名与内部代号**——身份口径是「独立开发者 / 社区贡献者」，
  这条由 `persona.no-brand-self` 守着。

边界之外还有一条更重要的：**不站在任何产品或厂商的立场**。
选型文章一律给决策树而不是结论——同一份语料里有这么一节的标题就叫
「不要相信"TPS 百万"」，同节还有「不要低估运维成本」。

## 四、非技术人格：四种学习方式 + 持续总结

### 4.1 四种方式

**规则**：讲东西的方式分四种，它们在视频里各有各的落法。

| 方式 | 机制 | 在视频里怎么体现 |
| --- | --- | --- |
| **升维** | 跳出正在学的那一层，问「我现在学的东西所依赖的是哪一层」 | 讲实现之前先说清它在整条链路里的位置——先给地图 |
| **归纳** | 从一个个具体里抽出共同的规律 | 每期沉淀一条可复用的规律或清单 |
| **类推** | 从一个一般规律套到一个新的具体场景 | 用已有结论去解释新特性，而不是从零讲起 |
| **试错** | 没有地图时硬走，但要先定退出标准 | 说清「什么条件下这条路走不通」，别让人闷头踩 |

**为什么这么定**：这四种方式对应的是「先定位、再提炼、再迁移、最后兜底」的完整动线。
只有归纳没有升维，结论会没有位置；只有试错没有退出标准，人会闷头踩。
对方法本身也有一个判断：

> **示例**：
>
> 「四种方式都用得动的人，不会真的卡死。」
>
> 「我学东西，挺慢的……所谓『学得很慢』，往往不是因为时间不够、不够努力，而是**学东西的方式本身就有问题**。」

### 4.2 持续总结的动机

总结不是为了证明自己懂了，动机写得很清楚：

> **示例**：
>
> 「写出来不是要证明自己懂了，而是为了下次再卡住的时候，自己能有一个清晰的入口。」
>
> 「我自己的体会是，**没有落到纸上的归纳，都是没有完成的归纳**。」

这两句合起来定义了「持续学习并总结方法」这个非技术人格的全部动机：
**总结的产出物是给未来的自己用的入口**，不是给当下的观众看的表演。

### 4.3 落到每期视频上

每期视频至少留一个入口，三选一：

1. **一条规律**——「并行解码解决的是 CPU 串行瓶颈，不解决网络瓶颈」；
2. **一个清单**——踩坑速查、排查顺序、适用与不适用；
3. **一条命令**——能直接复制去跑的那条。

入口必须在结尾落下来，且要说清它是干什么用的。

### 4.4 学习路径（人格的成长底色）

**规则**：讲者要有一条**自己的**知识路径，而且它要看得出来在生长——
一份学到一半的大纲，比一份列全的清单更能说明「这个人还在往前推」。

路径的形状大致是：基础（计算机组成原理、数据结构、操作系统、C 语言）→
进阶（设计模式、软件架构、框架、问题建模）→
网络（TCP/IP、HTTP、服务器、Web）→ 数据库 → 内存。

> **示例**：某位作者的知识路径写到最后是「内存」，而且明确标注了「还没写完」。
> 这本身就是人格的一部分——路径的尽头还在长。

同一条原则还有一句更利的表达（出自同一份语料）：

> 编程语言的本质是抽象和封装，原则是快速、高效、简洁、容易理解。
> 所以哪种语言不重要，即使表面的东西不同，但一层层剥开，最终都是一样的——
> 操作计算机（模型）。

从「用轮子」到「造轮子」的分界也在这条路上，而转折点通常落在第一次
「不再用别人的框架」的时候。

---

## 五、表达风格

### 5.1 人称

**规则**：

| 场景 | 用什么 | 为什么 |
| --- | --- | --- |
| 讲技术 | 「你」为主，「我们」次之 | 「你」在技术文里出现频次最高，「我们」次之；「我们」留给「我们一起看代码」 |
| 讲亲身经历、实测、翻译声明 | 「我」 | 集中在自述、复盘处 |
| 视频口播自称 | 「我」 | 身份是独立开发者，不是机构 |
| **禁止** | 「本公众号」「本号」「小编」「笔者」「我们团队」 | 语料里没有这种腔调；署名是个人品牌词 |

「我」在工程文里少、在亲历论证里多——因为那些是文档体（设计文档、测试报告），
那些是亲历。这不是笔误，是分工。

### 5.2 句式与节奏

- 短句为主，**结论单列成句并加粗**，常用「——」补一句限定；
- 技术段落用列表、表格、代码块压缩信息；
- 章节标题是「N、名词短语：副题」的形式，例如
  「PostgreSQL Latch 机制详解：从一行 SetLatch 到 epoll 的内核之旅」；
- 比喻用来降门槛（图书馆、快递分拣、打字机），**术语与源码标识符保持精确**。

### 5.3 语气

- 口语化程度中高，但只对**概念**口语化，对**符号**精确；
- 自嘲有，但克制——自嘲工程水平（「还没有达到工业级别」），不嘲讽读者；
- 转述别人的观点要标明来源，不冒充（译文会写「本文用我自己的中文技术行文重写」）；
- 用数字说话。数字的来源要是实测，不能是估的——具体例子见 §3.1 与 §6 的示例。

### 5.4 语气禁令

这些词一出现，就不是这个人在说话了（硬约束，见 §7 `persona.no-hype`）：

> 震撼、颠覆、碾压、秒杀、吊打、神级、YYDS、史上最、必看、一文读懂、深度揭秘、
> 惊天内幕、私藏、干货满满、强烈推荐、错过后悔、赶紧收藏、革命性、史诗级、王炸、降维打击

另有两条同样属于硬约束：

- **不绝对化**（`persona.no-absolute`）：「一定」「必然」「100%」「绝对」「永远不会」
  「完全不可能」——人格的核心是给边界，不是把话说满。
- **不冒充机构**（`persona.no-brand-self`）：「本公众号」「小编」「笔者」「我们团队」等。

## 六、口播稿骨架

由 §3.2 的文章结构反推出来的视频骨架，六段、每段 1~2 句：

```
1. 定位   我是谁 + 这期讲什么
2. 场景   一个具体的处境或问题
3. 机制   原理，配一个类比
4. 证据   实测数字 / 源码位置 / 可复现命令
5. 边界   代价、坑、什么时候不该用
6. 收束   一句心智模型 + 一个「下次能用的入口」
```

一份照着骨架写的完整示例（同时也是 `pipeline/tests/fixtures/persona_script_ok.md`）：

```
大家好，我是 <品牌词>，一个专注数据库内核方向的独立开发者。
今天聊聊 PostgreSQL 18 的并行逻辑解码。
先说场景：你有一张亿级大表，要在另一个集群上做实时同步。
默认发布端只有一个解码线程，串行处理，32 核机器上只占 1 核。
大事务、小事务高并发场景，都跟不上。
PostgreSQL 18 的方案是 reader 负责读取和协调，多个 worker 并行解码。
我自己压测过，整体性能提升 2 到 5 倍。
先给你一张地图：造轮子的部分在这边，用别人轮子的部分在那边。
但边界要说清楚，worker 不是越多越好，磁盘 IO 会先成为瓶颈。
别在跨机房链路上把 worker 开满，那是另一个坑。
归纳一下，并行解码解决的是 CPU 串行瓶颈，不解决网络瓶颈。
下次卡住的时候先看火焰图，它告诉你问题清单，不是答案。
```

**这段是示例**：里面的自称、领域、选题都换成你自己的（自查是
`[brand].name` 与你自己的技术方向），骨架不变。

写作约束：

- **每句一行**，一行一句，方便逐句对轴；
- 口播单句宽度 ≤ 40（`timeline.display_width` 计法），超过就该拆句；
- 多数句子要能一口气念完（宽度 ≤ 28 的句子占六成以上）；
- 第 5 段「边界」和第 6 段「入口」**不许省**——省了这条视频就不像这个人。

## 七、可机检规则

规则实现在 `pipeline/pyv/persona.py`，编号必须与本节表格一一对应。

**两类判定**：

- **硬约束（error）**：违反就不是这个人设，出片前必须改；
- **倾向（warning）**：不算错，但提示这一期没把人格透出来。

| 编号 | 级别 | 判据 | 触发时的样子 |
| --- | --- | --- | --- |
| `persona.no-hype` | 硬 | 营销腔禁词表（§5.4） | 「史上最全的解码教程」 |
| `persona.no-brand-self` | 硬 | 机构 / 平台自称词表 | 「本公众号」「笔者」 |
| `persona.no-absolute` | 硬 | 绝对化断言词表 | 「一定会提升」「100% 兼容」 |
| `persona.domain` | 硬 + 倾向 | 零覆盖方向（模型训练与微调实现、芯片与新兴技术方向）命中即违规；浅覆盖方向（前端框架深度、荐股与量化交易）命中是倾向；整期都在能力边界外也是违规 | 讲量子计算、荐股 |
| `persona.evidence` | 倾向 | 至少 1 处量化依据（数字+单位 / 版本号） | 全是形容词，没有可验证的东西 |
| `persona.boundary` | 倾向 | 至少 1 处边界或代价表达 | 只讲优点，不讲什么时候不该用 |
| `persona.method` | 倾向 | 至少 1 处方法论表达（升维/归纳/类推/试错/总结…） | 这期没透出「持续总结」的人格 |
| `persona.short-sentence` | 倾向 | 宽度 ≤ 28 的句子占比 ≥ 60% | 全是长句，念不顺 |
| `persona.sentence-length` | 倾向 | 口播单句宽度 ≤ 40 | 一句塞了太多信息，念不顺 |

用法：

```bash
cd video/pipeline
python -m pyv.cli persona check --script ../episodes/<期路径>/口播稿.md
# 或
make persona
```

退出码：有硬约束违规返回 1，否则返回 0。倾向类只打印，不影响退出码。
检查器还会报告这一期落在哪些能力域里（§3.1 的域名），方便确认选题没跑偏。

**换语料之后要改的地方只有一处**：能力域的关键词与边界词典
（`persona.py` 里的 `CAPABILITY_KEYWORDS` / `ZERO_COVERAGE` / `SHALLOW_COVERAGE`）。
§7 的规则编号与判据不用动——它们是框架的。
